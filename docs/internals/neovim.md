# The Neovim config

Plugins, lazy loading, the startup budget, languages, layouts, debugging and the UI modules.

**Settings screen** (`bud.settings`, JGA-94): `<leader>,`, `:BudSettings` or `s` on the dashboard. `M.sections` lists the rows (bool/choice/number/list); it reads `bud config ls` and changes things only through `bud config set`, `bud lang enable|disable` (in a terminal, since it can ask) and `bud tools enable|disable`. `tests/lua/settings_test.lua` swaps `M.run`.

**Dashboard.** `bud.dashboard` (D37) opens for bare `bud` from the VimEnter autocmd in `core/autocmds.lua`. `dashboard/view.lua` is a pure layout (`build(data, width, height)` returns lines and highlights) and is what `tests/lua/dashboard_test.lua` mostly covers; `dashboard/init.lua` gathers data, draws into a `bufhidden=wipe` scratch buffer with buffer-local keys, and runs git and `bud doctor --quick --json` in the background via `BUD_BIN`. Shared Lua modules: `bud.config` reads machine config, `bud.cli.bin()` finds the bud that launched nvim (`BUD_BIN`) for calling back into the CLI (the only writer of bud's state files), `bud.icons` holds the Nerd Font glyphs (the editor's accent with the robot; never emoji), and `bud.sessions` saves and restores per-project sessions. `bud.open` (D39) is the two-key open: `project()`, `file()`, `go(path)`; the dashboard's `p`/`f` and `<leader>p`/`<leader>f` all call it, and it reaches fzf-lua through `bud.pack.deferred["fzf-lua"]`.

**Neovim config.** `nvim/init.lua` turns on `vim.loader` (D93, byte-compiled modules cached in `~/.cache/bud/luac`), sets the leader (`<Space>`), then loads `bud.core` (options, keymaps, autocmds) and `bud.pack`, which adds plugins with Neovim's built-in `vim.pack` (D27, needs 0.12). Specs are lists returned by modules under `nvim/lua/bud/plugins/` (`{ src = "owner/repo", version = ..., config = fn }`, see the top of `pack.lua`); `plugins/init.lua` gathers them. Nothing updates plugins in place: versions change only by regenerating `nvim/nvim-pack-lock.json` and shipping a release. Generate that file with `vim.pack` itself and commit it byte for byte, or every sync will look like a change. Lazy loading is built into `bud.pack` (JGA-107): a spec with `event`, `ft`, `cmd` or `keys` stays off the runtimepath until its first trigger (commands and keys get stubs; the triggering event is replayed only to the autocmd groups the plugin just added), and `init` always runs at startup, for keymaps that should exist before loading (diffview's). A plugin that's on the runtimepath but slow to `require` can instead use `bud.pack.on_first_use(module, setup)` (fzf-lua). The smoke test loads every lazy and deferred plugin to check it, and `tests/lua/pack_test.lua` covers the loader with throwaway local git repos. Measure before making something lazy: `--startuptime` appends to its log file, so delete it between runs. The budget is 50 ms to the first screen, empty or opening a file of any language (D35); `bud doctor` measures both (`nvim.StartupTime`: `nvim --embed` with a bare UI attached over msgpack-rpc, read from `--startuptime`'s "first screen update", with `BUD_STARTUP_PROBE=1` skipping what comes after it, D92), and the dashboard shows `bud.startup`'s number, from the bud CLI's start (`BUD_LAUNCHED`) to the end of the first redraw. A headless `--startuptime` stops before UIEnter and the first draw, so it reads low. `event = "UIEnter"` loads on the next tick, since Neovim runs UIEnter before it draws, and nothing may touch `vim.lsp` before the first screen (the statusline checks `package.loaded`). Per-buffer work that's slow the first time (tree-sitter highlighting, `vim.lsp.enable`, linting) starts on `vim.schedule` in `plugins/lang.lua`; `bud.lang.highlight` (JGA-184, `tests/lua/highlight_test.lua`) sets `b:ts_highlight` on FileType so Neovim's `syntaxset` skips the regex syntax tree-sitter would throw away, and puts it back when tree-sitter can't start; and Neovim's providers are off in `core/options.lua`, which also leaves `clipboard` empty over SSH (D95). `bud.bigfile` (D94, `tests/lua/bigfile_test.lua`) gives a file over 1.5 MB, or with lines averaging over 1000 characters, filetype `bigfile`, so nothing per-filetype starts on it, with the real filetype's regex syntax (`bigfile.filetype(buf)`, which the bridge's `languageId` and `tools.review` use; lockfiles Neovim matches by name are in `bigfile.named`); render-markdown stops at 250 KB (`max_file_size` in `bud.markdown.config()`). Keymaps go in each spec's `config`. A spec can also have a `restore` hook that runs (and may block) at the end of `bud.pack.restore()`, after the lockfile checkout; blink.cmp downloads its prebuilt matcher there. `bud install`/`bud update` start that restore with `BUD_PACK_RESTORE=1`, which makes `bud.pack.setup` skip every `config`.

**Languages (D30).** `bud.lang` (`nvim/lua/bud/lang/`) reads each spec in the synced `languages/` (fields documented in `languages/_template.lua`, unknown fields are errors), picks the enabled ones from `config.json` (`languages`, else the profile's preset: all for full, `minimal = true` specs for minimal) and answers queries (`servers()`, `by_ft(field)`, `collect(field)`, `filetypes()`). The wiring lives in the plugin specs in `plugins/lang.lua`: nvim-lspconfig + `vim.lsp.enable`, mason.nvim, nvim-treesitter (`main`, highlighting on enabled filetypes), conform (format on save unless `format_on_save: false`, or when the spec's `format_markers` aren't found; prettier only with a Prettier config; `<leader>cf`), nvim-lint. Parsers and Mason packages install only in their `restore` hooks. Mason's hook then trims them (`bud.lang.trim`, D67): prunes unused files, hard-links packages built from one source, and uninstalls ones only disabled specs name; `tests/lua/trim_test.lua`. `tests/lua/lang_test.lua` covers the engine with fixture specs. The smoke test enables no languages (installing their tooling takes minutes), so after changing a spec or `plugins/lang.lua` run `just lang-check`, which installs everything and checks each language on a sample project (`scripts/lang_check.lua`; add a case there for a new language).

**Layouts (D45).** `layouts/*.lua` at the repo root (embedded and mounted like `languages/`) list panes; `bud.layout` (`nvim/lua/bud/layout/`) validates them, opens each pane through the provider registered for its kind (`layout/panes.lua`: `tree` is `bud.explorer`, oil in a narrow split with `<leader>e`/`<leader>E`, D79, `tests/lua/explorer_test.lua`; `git` is neo-tree's `git_status`; later modules call `bud.layout.register`; a pane with `focus = true` takes the cursor), skips kinds with none, and sets `bud.terminal.height`. `bud <dir>` passes `BUD_OPEN=project` (`nvim.Launch`), and the VimEnter autocmd calls `layout.open_project` on `vim.schedule` for that or for files: the saved session wins unless `--layout` (`BUD_LAYOUT`) was given. `bud.open.go` does the same. `:BudLayout [name|reload]`. `layout.default(dir)` picks `BUD_LAYOUT`, then the project's `layout` in `projects.json`, then `config.json`'s, then `default`; `bud layout` (`internal/cli/layout.go`) lists them (descriptions read from the file's text) and sets the last two. `open` refuses a `--layout` the synced `layouts/` doesn't have. `tests/lua/layout_test.lua` uses fake providers.

**Debugging** (D66): `plugins/debug.lua` (nvim-dap + nvim-dap-view, lazy on the debug keys) and `bud.dap.adapters` (definitions by Mason name; a spec's `dap` field picks one, and Mason's restore installs it). `tests/lua/dap_test.lua`. Dialogs, menus, inputs and panels are `bud.ui` on nui.nvim (JGA-136, `nvim/lua/bud/ui/`): `float`, `dialog` (actions with keys, `cancel` on any other close), `menu`, `input`, `panel` (a nui Layout), each dimming the editor behind it (a backdrop window, `backdrop = false` to skip; JGA-160); `bud.ui.hook` (from nui's spec) points `vim.ui.select`/`input` at it without loading it at startup; the permission prompt and `bud.ai.issue`'s floats use it. Tests that need nui `dofile("tests/lua/lib/nui.lua")` (bud's copy, else a clone at the locked rev). Key hints are mini.clue (JGA-140, lazy on `UIEnter`, leader group names in its `clues`; add one there for a new `<leader>` prefix), in a panel at the bottom right as wide as its keys but at most 40% of the editor (30 to 60 columns). Notifications are mini.notify (JGA-138, lazy on `UIEnter`, `vim.notify` replaced, `<leader>un` history); the command line and messages are Neovim's own ui2 (`bud.messages`, JGA-137, `ui.messages`), and `messages.float` (D86, `ui.cmdline_float`) moves ui2's command-line window into a centered float while it's open, with `vim.g.ui_cmdline_pos` putting blink's menu under it (`tests/lua/messages_test.lua`, a fake ui2). `;` and `:` are swapped in Normal and Visual mode (D85, `core/keymaps.lua`). Breadcrumbs are dropbar.nvim in `plugins/ui.lua` (JGA-139, lazy on `UIEnter`, file buffers only, `ui.breadcrumbs`, `<leader>;` picks). Markdown files render in place with render-markdown.nvim (D88, also in `plugins/ui.lua`, lazy on `UIEnter`, where `bud.markdown.open()` attaches the markdown files already open, configured through `vim.g.render_markdown_config` from `bud.markdown.config()` in its `init`, file buffers only via `ignore`); `bud.markdown` (`nvim/lua/bud/markdown.lua`) decides per buffer: text while any of its windows is a diff (the plugin draws per buffer, and Claude's edit review shares the editor's buffer), else what `<leader>um` (mapped from `on.attach`) or `ui.markdown`, read at attach, chose. `tests/lua/markdown_test.lua` swaps `M.api`. The statusline is mini.statusline driven by `bud.statusline` (JGA-133: one global statusline, `laststatus=3`; the file relative to the project via `file()`, attached language servers via `lsp()`, `tests/lua/statusline_test.lua`); modules add their own section with `require("bud.statusline").add(fn)`, drawn in the `BudStatuslineAI` block. `bud.marks` is bud's own pinned-files module (four slots per project, `~/.local/state/bud/marks.json`), tested headless in `tests/lua/`.
