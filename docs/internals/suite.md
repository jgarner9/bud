# Bud Suite architecture

This is the current direction for the public Suite repository. The external Suite decision log retains the history, and `BASE.md` covers the IDE and CLI. Suite D48–D61 take precedence where they revise earlier decisions. The November 19 Herdr decision supersedes Suite D6 and the Tauri-specific client and distribution choices in D50 and D56.

## Components

```text
Desktop Herdr workspace → Bud Neovim and local OpenCode sessions
iOS Herdr workspace     → SSH → home-server herdr-core → agent terminals
Home server             → Hermes, planning OpenCode and Bud services
```

Bud owns the Neovim configuration, server bootstrap, device profiles, signed updates, privacy policy, memory and action approvals. Herdr owns the agent workspace and terminal connections. Hermes runs home-server assistant sessions. OpenCode runs local coding and home-server planning sessions. Bud's profiles select components and update channels, and the model registry assigns models to roles. The public tree contains examples. Real device configuration and personal content live in a private overlay, with credentials resolved from 1Password references at the point of use.

## Resolved boundaries

- **Memory writes.** Suite D48 stages routine captures with provenance for review. Retrieval serves approved records within the client's privacy scope. Curated Markdown stays in a separate private Git repository. The local memory service owns SQLite, FTS5, sqlite-vec and migrations behind a Unix-socket API. The Go CLI remains standard-library-only.
- **Recovery.** Suite D60 prevents a normal channel update from replaying older signed content. `bud sync --rollback` is explicit local recovery to a compatible saved version. The binary updater has a separate recovery path that restores the previously installed binary if sync or quick health checks fail after an update. [Content verification](content.md) · [Sync recovery](sync.md) · [Binary updater](updater.md)
- **Client ownership.** Bud manages installed versions, configuration and local update policy. Phase 7 targets Herdr desktop and mobile. The workspace integration must establish how Herdr's updater and Bud's update and rollback policy work together.

## Final-dispatch approval contract

The shared Go approval package in `internal/approval` builds on PR #46's lifecycle store. The helper freezes the invocation, verifies the one-time reply and consumes the approval before invoking the executor. Runtime adapters must authenticate replies and enforce policy. OpenCode 2.3.2 and Hermes v0.23.2 still need integration.

1. Evaluate Bud policy after the last hook or middleware that can rewrite the invocation. Bind each approval request to an authenticated runtime, profile, session, surface and actor, plus its final action, resolved target, arguments and expiry. Include execution context that can change the effect, such as a shell working directory or MCP server.
2. Present the frozen invocation on the authenticated surface that owns the turn. OpenCode should use its native permission request and route ACP replies through the owning connection. Hermes should keep its request-specific card and authenticated Signal reactions and codes. Accept one-time approval or denial. If essential details cannot be reviewed, offer denial only. Agent tools must be unable to impersonate the reviewer or access the decision channel and store.
3. Keep native guardrails in force. At final dispatch, consume the matching approval atomically and execute the frozen invocation. In OpenCode 2.3.2, `tool.execute.before` is followed by schema decoding, which can transform the input. Even a gate after decoding is not sufficient for shell calls: `shell.create.before` can subsequently change the command, working directory, shell and environment before spawn. Bind the final effect at the leaf, and audit the other leaves and Code Mode paths. In Hermes v0.23.2, `_dispatch_authorized_once` follows middleware and `_pre_tool_block` rewrites, but is not the only dispatch path: code execution, connectors and the tools MCP transport can call `model_tools.handle_function_call` directly. Cover each path at its final dispatch or refuse it. A failed execution still spends the approval.
4. Deny approval-required actions when the authenticated surface is unavailable, the turn is unattended or canceled, or the earlier of the turn and review deadlines elapses. Treat store failures and uncertain acknowledgements as denial and require a fresh request for any retry. Keep raw arguments and credentials out of the audit log.

Test both pinned runtime paths with synthetic calls. Verify review sees the last rewrite, modified arguments or scope invalidate approval, and replay, concurrent use, always-allow replies, cancellation, expiry, unattended calls, restart and store failures cannot permit execution. Preserve the authenticated Signal flow. A command-only pre-approval needs the full final invocation binding before it can satisfy this gate.

Hermes's terminal path also resolves execution context after the outer tool dispatcher and retries `env.execute` after some exceptions. An exception does not establish that the backend performed no side effect. An approved call must not retry after an uncertain acknowledgement; test a backend that performs a side effect and then raises as well as ordinary failures.

The native surfaces alone do not establish this contract. OpenCode's ordinary permission evaluation can use saved allows, and its server reply endpoint checks the session rather than ownership by a reviewer connection; plugins also have a permission reply capability. Hermes's ordinary approval flow permits modes and cached decisions that are broader than one call. A final gate needs a one-shot decision tied to the owning authenticated surface, without an agent-accessible reply path. Mode 0600 does not isolate the store from tools running under the same user. Establish and test process, filesystem and network isolation, or fail closed when it is unavailable. In-process runtime plugins are trusted code and must not be treated as isolated agent tools.

Bud currently installs upstream OpenCode and does not install a patched Hermes runtime. A runtime patch must be built and identified reproducibly, and the launcher must reject a stock or mismatched runtime before claiming this contract is enforced. Do not modify a live Hermes installation in place to test it. The shared Go helper is not yet connected to either runtime.

The synthetic stock-runtime probes in `scripts/opencode-approval-probe.sh` and `server/hermes/tests/test_pinned_dispatch.py` record the rewrite and dispatch gaps above; passing them is not evidence that the approval contract is enforced. They require trusted, disposable source checkouts and dependencies, not credentials or a live service. The OpenCode probe takes its v2.3.2 checkout as an argument and requires Bun 1.4.4; its README explains the test isolation limits. The Hermes probe's docstring gives a sanitized invocation using its v0.23.2 checkout's editable environment. Both probes pin the upstream commit and reject tracked modifications, but do not authenticate untracked files or dependencies. The normal `just hermes-plugin-test` separately checks the Signal plugin without Hermes.

### Where approvals are enforced (Suite D97)

This is the intended boundary; none of it is wired yet. The `internal/approval` helper isn't connected to the gateway, ops, Bud's commands or the Signal plugin, and the ops `approvals` tool is still a placeholder. Bud will enforce final-dispatch approvals only at leaves it owns: the MCP gateway and its servers, the ops server, Bud's own commands and the Signal plugin. It ships no patched Hermes or OpenCode, so the runtime-patch requirements above apply only if that changes. An approval-tier action through a runtime's native shell or tools is to be refused by that runtime's permission config rather than approved (not rendered yet). The probes above are why: a stock runtime can rewrite the call after its hooks, and has dispatch paths a plugin can't cover, so a gate inside it can't bind the final invocation.

The socket reviewer (`approval.SocketReview`, slice 1 of the wiring) is the Go side of the review channel. It dials the unix socket at `paths.ReviewSocket()` (`$XDG_RUNTIME_DIR/bud/review.sock`), sends one JSON line `{id, summary, expires_at, secret}`, holds the connection and reads one line `{id, choice}` (at most 64 KiB). It fills `Reply.Scope` from the scope the adapter passed in, never from the reply, and closing the connection when the context ends withdraws the prompt. It reads the secret file (`paths.ReviewSecret()`, mode 0600 or stricter) on every call. It denies on every failure: no runtime dir (then `ReviewSocket()` is empty and there is no fallback to `/tmp`), a failed dial, a bad or oversized line, an id mismatch, an unknown choice, EOF before a reply, a reply carrying `error`, or a missing or loose secret. The reviewer server in the Signal plugin and the callers are later slices.

### Unattended sessions (Suite D99)

An editor "ask" prompt and Hermes's Signal approval prompt stay where Jason is present. An unattended session must refuse an approval-tier action (a send, a push to main, spending, infrastructure or a secret), never approve it and never wait forever. Bud renders "ask" for those actions in both runtimes: the OpenCode `shell` rules for `git push` and `git commit`, the `linear_*` and `github_*` tool rules and `.env` reads, and Hermes's `bud hermes-gate` tiers, which answer `ask` for the same shell rules and for any tool without a tier, and Hermes's own trust handling, which asks before any tool on a server marked untrusted in `content/env/server.jsonc` that isn't read-only (the gate allows `mcp__*`, so that prompt is Hermes's, not the gate's). What each runtime does with an ask when nobody can answer was checked against upstream source in November 2026.

- **OpenCode `opencode run`: refuses. Meets D99.** The non-interactive path answers every `permission.asked` event with `reject` and prints "permission requested: ... auto-rejecting", unless `--auto` (hidden aliases `--yolo` and `--dangerously-skip-permissions`) is passed, which replies `once`. The source is `packages/opencode/src/cli/cmd/run.ts` in [anomalyco/opencode at e23586af](https://github.com/anomalyco/opencode/blob/e23586af/packages/opencode/src/cli/cmd/run.ts); that file was not retrievable at the pinned 2.3.2 commit, so the 2.3.2 behavior is inferred from this newer revision and from [issue 10411](https://github.com/anomalyco/opencode/issues/10411): "Now `opencode run` auto-rejects tool calls if they would lead to a permission prompt." The [CLI reference](https://opencode.ai/docs/cli/commands.md) documents the flag as "Auto-approve permissions that are not explicitly denied." Never pass `--auto`, `--yolo` or `--dangerously-skip-permissions` in a job or script.
- **OpenCode server with no client attached: blocks forever. Gap against D99.** At the pinned 2.3.2 commit, [`packages/core/src/permission.ts`](https://github.com/anomalyco/opencode/blob/c0ad18b402eb2827fc1ee71c171b1177b3fc02d1/packages/core/src/permission.ts) creates a `Deferred`, publishes `permission.asked` and then runs `Deferred.await(item.deferred)` with no timeout. Only a reply from a client ends the wait. The maintainers' own tracker agrees: [issue 61504](https://github.com/anomalyco/opencode/issues/61504) says "A rule that resolves to `ask` waits forever" and lists the headless-server hang reported in [issue 14473](https://github.com/anomalyco/opencode/issues/14473), "the Promise never resolves and the session is permanently frozen". A per-rule timeout is only a proposal there. The pinned release cannot refuse an unattended server session, so such a session would sit on the prompt until someone attaches or replies, and a stray client that can reach the server's reply endpoint could answer it (see D97). Until that is fixed, a server session must not hold an `ask` rule for an approval-tier action: render the action as `deny` for sessions that run without an attached UI.
- **Hermes cron jobs, `hermes chat -q` and unattended platforms: refuse, as bud configures them. Meets D99.** `approvals.cron_mode`, `single_query_mode` and `unattended_mode` each default to `deny`, and bud's rendered config sets all three to `deny` explicitly. In `tools/approval.py` at [v0.23.2](https://github.com/NousResearch/hermes-agent/blob/v0.23.2/tools/approval.py), `_run_approval_gate` clears the presence flags for cron and `-q`, then returns `_blocked(...)` ("BLOCKED: ... cron jobs run without a user present to approve it") when the mode is `deny`, and `request_tool_approval` (what a `pre_tool_call` `approve` directive from `bud hermes-gate` reaches) passes `fail_closed_when_no_human=True`, so a headless context with no approval bridge is blocked too. The [security guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.2/website/docs/user-guide/security.md) says `deny` "blocks the command (the agent must find another path)" and that `approve` "auto-approves everything in cron context". The same file documents that an `api_server` session whose client can answer the card still gets the request, which is the intended attended case. Changing any of the three modes to `approve`, `--yolo` or `approvals.mode: off` would auto-approve; bud's sync keeps those keys managed so an edit is replaced.
