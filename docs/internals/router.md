# The router

`bud router` (`internal/router`, `internal/cli/router.go`) is the home server's one OpenAI-compatible endpoint over the model registry's providers (Suite D70, D71, D98). Its unit is in `server/router/`. It routes, proxies, enforces privacy tiers, tracks spend and caps the month's top-up. It also tracks provider health and falls back when a model is down (Suite D104). The privacy rules are built (Suite D112), and the MCP gateway applies the same ones to tool-call arguments (`docs/internals/mcp-gateway.md`). Not built yet: the classifier, ranking, and Lemonade behind it (Suite D98).

## Endpoints

- `GET /v1/models` lists the registry model ids the request's tier allows (`owned_by` is the provider) and one `bud/<role>` entry per role with an eligible member (`owned_by` is `bud`).
- `POST /v1/chat/completions`, `/v1/completions` and `/v1/embeddings` forward to the model's provider.

## Resolving a request

The body is read up to 10 MiB (413 past it) and decoded into `map[string]json.RawMessage`, only to find `model`; every other field is re-encoded as it came, without HTML escaping. `model` is a registry model id, or `bud/<role>`, which is the pin if it allows the request's tier, else the first `Role.Members()` entry that does. It's replaced by the Model's `name`, and the request goes to the provider's `endpoint` with the same path after `/v1` (`<endpoint>/chat/completions`). An unknown model is a 404 that names it and points at `GET /v1/models`; a body that isn't a JSON object or has no model is a 400.

## Privacy tiers

The tier comes from `X-Bud-Privacy` (`registry.RequestTier`, shared with the MCP gateway): P0, P1 or P2, and a missing header is P0, so an unconfigured client fails closed (Suite D23, D81). Any other value is a 400 naming the valid ones. A model serves a request only if the tier is in its `privacy` list (`Model.Allows`); otherwise an explicit model id, or a role with no eligible member, is a 403 that points at `GET /v1/models` with that header. The header is stripped before forwarding, and every proxied response carries `X-Bud-Model: <registry model id>`, replacing any upstream header of that name. As at the gateway, the header is a guard against private text leaking by accident, not authentication: a caller on the tailnet can send any tier, and the tailnet is the authentication (Suite D72). Devices get their header from `bud sync`.

## Privacy rules

`registry.privacy_rules` (Suite D23, D112, D118) can only raise the tier, never lower it. A rule may carry `entropy`, `validate` and `keywords` (`docs/registry.md`): `CompiledRule.Matches` checks a keyword first (`Raise` lowercases each text once for that), then the pattern, then the entropy and validator on every match, so a text full of near misses never counts as a hit. The shipped pack costs about 1.5 ms for a 40-message chat (`BenchmarkTheShippedRulesOverAChat`), and `TestTheShippedRulesStayInBudget` fails past 20 ms. `New` compiles them (`Registry.CompileRules`, sorted by name; a pattern that doesn't compile fails `New`). `ServeHTTP` applies them right after the header is read and the body decoded, before `model` is looked at, so the explicit-model 403, role picking and the P0 fallback all use the raised tier. `texts` (`rules.go`) lists what they read: every chat message's `content` of any role (a string, or the text of each `{"type":"text"}` part), a completion's `prompt` and an embedding's `input` (a string or an array of strings; token arrays are skipped). Whatever it can't read is skipped, since the upstream rejects a malformed body anyway. Each text is matched on its own. `registry.Raise` returns the most private tier and the first rule, by name, that gave it. A raised request's response carries `X-Bud-Privacy-Raised: <rule>`, also on a 403 or 503, and an upstream header of that name is deleted; a request no rule raised carries none. The log line is `router: rule <name> raised a <tier> request to <tier>`, and no request text is ever logged. `GET /v1/models` has no body, so no rule applies there. The classifier (Suite D67), which would raise a tier by judgement, is still not built.

**Provenance (Suite D119).** A chat whose history holds a call to a tool of a P0-only MCP server (the calendar, mail) is raised to P0 after the rules, with `X-Bud-Privacy-Raised: provenance` (a rule that already raised it to P0 keeps its own name). The result of that call is somewhere in the conversation, so where the data came from decides, not only what the text looks like. This is the taint gate D95 couldn't build inside Hermes, whose `pre_llm_call` hook fails open; the router is a Bud-owned leaf (D97). `tainted` (`provenance.go`) reads the tool names in the assistant's `tool_calls[].function.name` and the older `function_call.name`, and the `name` a `tool` or `function` message carries, so a history trimmed of the call still counts. `fromServer` matches a name with or without the runtime's prefix: OpenCode's `calendar_list_events`, Hermes's `mcp__calendar__list_events` or `mcp_calendar_list_events`, any case, with a server's `-` read as `_` too. The servers come from `router-p0-servers.json`, which `bud sync` renders from the env fragments' `bud.mcp.*.privacy` (`env.Resolved.P0Only`), so the list isn't written twice; `ReadP0Servers` refuses a missing or damaged file, and `bud router` won't start without one, saying to run `bud sync`. Once raised, the request is P0 on every path: a named cloud model is refused (403), a role picks only P0 members, a retry after a transport error does too, and when the local model is down the D104 fallback asks Jason before anything leaves (or answers 503 with `--no-p0-fallback`). `TestACalendarCallInTheHistoryKeepsTheConversationLocal` checks a fake cloud gets zero bytes on each of those paths. Not covered yet: the rules don't read `tool_calls[].function.arguments`, only message content.

**A recalled private memory record (JGA-389).** Bud memory allows every tier, so a call to it says nothing by its name; what counts is whether a P0 record came back. memory-mcp puts `registry.P0Marker` (`bud-p0-record-7c41`) as the first field of each P0 record in a `memory_search` result, and `recalled` (`provenance.go`) raises a request whose `messages` hold it anywhere to P0, after the provenance check, with `X-Bud-Privacy-Raised: memory`. The marker is letters, digits and `-` only, so it reads the same whether a runtime quotes the result as a JSON string, as content parts or as plain text. The raise holds the conversation like any other, so a later compressed history that has lost the marker stays local too. Hermes's private profile reaches memory at P0 for this (`marks_p0`, `sync.md`), so its chats can recall every tier; a P1 chat that recalls only P1 and P2 records stays on Go.

**A raised conversation stays P0 (Suite D117, D119).** Once a rule or the provenance check raises a request to P0, the conversation it belongs to stays P0 for 30 days after its last raise, by the conversation id Hermes sends in `x-opencode-session` (`SessionHeader`), and its later requests get `X-Bud-Privacy-Raised: conversation`. The evidence doesn't always travel with the data: Hermes's context compression and title calls send the conversation as plain text, without the `tool_calls` the provenance check reads, and once a history is compressed its later turns don't hold them either. Hermes sends the id on those auxiliary calls too, so they stay local. A request that arrives as P0 isn't remembered, since a P0 header says nothing about the conversation, and a request with no id can't be held. `sticky.go` keeps the list as SHA-256 hashes of the ids in `router-p0-conversations.json` (`paths.RouterP0Conversations`, mode 0600), dropping expired ones on each write, so a restart (an update, say) doesn't forget a conversation; a damaged file stops the router, saying to check it and delete it to start empty. Reading and updating the list is one step under one lock (`decide`). A held conversation is written again only once its expiry would move by a day (`stickyRefresh`), so a busy conversation doesn't write the file on every request. A failed write fails closed: every request that carries a conversation id is P0 until a write succeeds, logged once each way. `sticky_test.go` checks a compression-shaped request after a calendar call, the marker, a restart, expiry, a failing disk, the write interval and concurrent requests under the race detector. What it can't hold: a delegated subagent's requests carry their own conversation id, so P0 data the parent puts in a subagent's task prompt reaches the cloud at P1 unless a rule matches it (JGA-390).

## Keys and headers

A provider's key comes from the environment variable the OpenCode adapter names for it (`registry.KeyVar`: the `{env:VAR}` it names, or `BUD_<PROVIDER>_API_KEY` for an `op://` reference). `New` fails when a keyed provider's variable is empty, so a unit started outside `op run` stops at once. The key goes out as `Authorization: Bearer`; the client's `Authorization` and `Cookie` are dropped, as are hop-by-hop headers and `Accept-Encoding`. Without the client's `Accept-Encoding` the transport asks for gzip itself and decodes the body, so the spend meter always reads plain JSON. Key values are never logged or returned. Every forwarded request carries `x-opencode-session`, which OpenCode Go requires (it answers 400 `MissingSessionID` without it) and uses for routing and prompt caching. Only the client knows which conversation a request belongs to, so its own value is kept: Hermes sends one because its router provider entry sets `session_affinity_header`. A request without one gets a random `oneshot-` id, so unrelated requests are never taken for one conversation. Other providers ignore the header.

## Proxying and errors

`httputil.ReverseProxy` with `FlushInterval: -1` passes SSE through as it arrives. Errors are OpenAI-shaped (`{"error":{"message":...,"type":...}}`). An unreachable provider is a 502 with a generic message; the transport error is not echoed, since it names the upstream's address (as in the MCP gateway).

## Listening

`--listen` (default `127.0.0.1:8795`) must be a loopback or tailnet IP, checked by `internal/tailnet.Inside`, which the MCP gateway uses too (Suite D72); `localhost` is refused. `--registry` reads one file; without it the router loads the synced content's registry with the overlay's merged over it, as `bud doctor` does.

## Spend and the top-up cap

The router keeps a spend ledger (`internal/router/spend.go`, Suite D24, D64): for the current UTC calendar month, the dollars spent on each registry model and the month's top-up total. It is a JSON file, `router-spend.json` in bud's state dir unless `--spend` names another, written atomically with mode 0600 after every charge. It also holds `cap`, the `--topup-cap` of the router that wrote it, so `bud mcp-ops`'s `spend` tool can report the month against it (`router.ReadSpend` reads the file without changing it). A missing file is an empty ledger. A corrupt one stops the router at start with an error naming the file, which you move aside. When the month changes, the old month's numbers stop counting and only the new month is kept. Beside the dollars it keeps, per model, the month's charged requests and their prompt and completion tokens (`tokens`), and the dollars of each UTC hour over the last 7 days (`hours`, keyed like `2026-11-24T15`), which outlive a month change because Go Plus's 5-hour and weekly limits run across months. Each charge drops hours older than 7 days. `ReadSpend` sums them into `Last5h` and `Last7d`, counting every hour that overlaps the window, so a window may read up to an hour's spend high (JGA-391). Only traffic through the router is in the ledger: OpenCode on a device talks to Go directly, and reads its own spend with `opencode stats --cost --models --json` (whether it should go through the router is JGA-393).

A request's cost comes from the `usage` object in the response: prompt tokens times the model's input price plus completion tokens times its output price, per million tokens. C0 models are never charged. The part of a charge that goes past a C1 model's monthly allowance, and all of a C2 model's charge, is added to the top-up total. A model with no price, or a response with no usage, is charged nothing, and the router logs one line per model per process saying so. Nothing about it reaches the client.

The router reads the response body as it passes through, without delaying or changing it. A JSON body is buffered up to 10 MiB and charged when it ends; past that, only its last 64 KiB is kept, and the last `usage` object in it is charged. An event stream is scanned for a `data:` chunk with a non-null `usage`, and charged at the end. So that a stream carries usage, the router adds `"stream_options":{"include_usage":true}` to a `POST /v1/chat/completions` body that has `"stream": true` and no `stream_options` of its own; a caller's own `stream_options` is left alone. The client then sees one extra final chunk with empty `choices`, which the OpenAI spec defines.

For a `bud/<role>` request, the router takes the first eligible member (the pin, then the pool order) that spends no top-up, meaning a C0 model or a C1 model with allowance left. Only if there is none does it take the first eligible member that would spend top-up, and only while the month's top-up is under `--topup-cap`. An explicit model id is served when its tier allows it, unless serving it would spend top-up and the cap is reached. At the cap the router answers 402 with an `insufficient_quota` error saying that spending past the cap needs approval, which isn't built yet, and that C0 and in-allowance models still work. A cap of 0 means no top-up ever. `--topup-cap` must be a finite amount of 0 or more.

Top-up requests run one at a time: a request that would spend top-up waits until the one before it has been charged, then is checked against the cap again, so requests admitted together can't all land past it. The cap can still be passed by the one request that crosses it. If a ledger write fails, the charge is kept in memory but no top-up is admitted until a later write works, since a charge that isn't on disk would be lost on restart; those requests get a 503 saying the ledger couldn't be saved. C0 and in-allowance requests keep working. `GET /v1/models` keeps listing every model the tier allows, so nothing disappears silently.

Every proxied response carries `X-Bud-Spend`, such as `topup=1.23/10.00`: the month's top-up so far, before this request is charged, over the cap. An upstream header of that name is replaced.

## Health and fallback

Hermes's private profile reaches this through `bud.router` (docs/internals/sync.md): it asks for `bud/manager` at P0, so when the local model is down this is the path that holds the request for Jason's approval.

`internal/router/health.go` keeps each provider's up or down state behind a mutex, with the time it changed, and logs one line per change (`router: provider X is down` or `is up again`; never an address). The router probes every provider that serves at least one model allowing P0 (the local ones): `GET <endpoint>/models` with the provider's key, every 10 s with a 2 s timeout. Any 2xx is up; a transport error, a timeout or a 5xx is down. `Start(ctx)`, which `bud router` calls before serving, runs the first probe synchronously so state is known at once, then probes until the serve context ends. Besides probing, any provider is marked down when a proxied request to it gets a transport error. A probed provider comes back only on a good probe; one that isn't probed counts as up again 30 s after it was marked down. `Options` carries the probe interval, timeout and clock, so tests run fast.

`pickSpend` skips members whose provider is down, so a `bud/<role>` request goes to the next eligible member: the pin, then the pool order, with the spend rules as before. `pick` ignores health, since it decides the 403 and what `GET /v1/models` lists, which still lists every model. If a proxied request fails with a transport error before any response bytes (the proxy's error handler only records it; `ServeHTTP` decides), the provider is marked down and a `bud/<role>` request is retried once on the next eligible member, re-resolved and re-encoded since name, URL and key may differ. Only a 2xx body is charged, so a retry never charges twice. With no next member, the answer is the 502. An explicit model id is never retried, and one whose provider is known to be down gets a 503 `api_error` saying to use `bud/<role>`. If every eligible member of a role is down at P1 or P2, that is a 503 too.

## P0 when the local model is down

A P0 request can be served only by members that allow P0. When every one is down, the router doesn't fall back on its own. This loosens "P0 is local only" only through a one-time approval per turn (Suite D104). Without approvals (`Options.Approvals` nil, or `--no-p0-fallback`) the answer is at once a 503 `api_error`: "no local model is available for a sensitive (P0) request; the local model is down".

With approvals wired, the router picks the fallback: the first member of the role (pin, then pool order) that is up and allows P1, never one that allows only P2, under the usual spend rules (a blocked cap is the 402). With no such member it answers the 503 without asking. Otherwise it holds the request and goes through `approval.Store.Dispatch` as `bud mcp-ops` does, with action `router:p0-fallback`, target the fallback's model id, and arguments `{"role","endpoint","body_sha256"}`. Nothing of the prompt is in them, and nothing is sent upstream before approval. The reviewer sees only the action, target and these arguments, since `approval.SocketReview` builds its summary from them. The scope is fixed, as ops': Runtime `router`, Surface `router`, Actor `tailnet`, Session `request`, Profile `unknown`, because the router can't learn the calling device's session or profile and its only authentication is the tailnet; the binding that matters is the action, the fallback and the body's hash.

The wait is `--p0-fallback-wait` (default 10m, over 0 and at most 1h) and also ends when the client's request does. On allow-once the buffered request is forwarded to the fallback at P1 with `X-Bud-Model` set to its id and `X-Bud-Fallback: p0-approved`. On a denial, expiry, an unavailable reviewer or any error, the answer is the 503 with "; Jason didn't approve sending it to <model>" and the reason. An explicit model id at P0 has no override: a down model is the 503 above. At most 4 P0 requests are held for approval at once; a fifth gets the 503 at once, so held bodies can't pile up. Once approved, the forward runs on the client's own request context, not the approval wait's: the wait bounds only how long the router asks, and a long answer isn't cut when it ends.

One approval covers the rest of its turn. An agent's tool loop sends several requests for one message, each with a new body, and Jason approved the message, not one request of it. So after an allow-once, the router remembers the turn for 10 minutes (`p0TurnTTL`), keyed by a hash of the client's conversation id (`x-opencode-session`, which Hermes sends), the latest user message and how many user messages the conversation has, the role and the fallback model, so the same words sent again later are a new turn. The window runs from Jason's answer. A request of that turn goes to the same fallback without asking, and one that arrives while the turn's prompt is still open waits for that answer instead of sending a second prompt. The next user message is a new turn, and asks again. A request with no conversation id or no user message always asks. Nothing is kept on disk, so a restart forgets the turns.

The prompt is plain text for a phone (`approval.summarize`): a line saying what is asked, then the arguments worth reading as `key: value` lines, with hashes and the endpoint left out and each value kept to one line (so an argument can't pass for another field), and the expiry time. For the fallback it reads "The local model is down. Send this private (P0) chat to <model> instead?", then `role: <role>` and "Expires at HH:MM." Signal adds the code to answer with.
