# The Claude Code session, bridge and AI features

`bud.ai.claude` and everything built on it: the headless session, the TUI pane, the IDE bridge, permissions, chat, inline actions, tools, the generator, filing issues and working them.

**Claude Code session.** `bud.ai.claude` (`nvim/lua/bud/ai/claude.lua`, BASE.md 4.2, D49/D50) is the only thing that talks to Claude Code. `setup()` runs from VimEnter on `vim.schedule` (not headless): `:BudClaude status|restart|stop`, `<leader>ar` restart, a statusline section, and a session for `bud <dir>` (`BUD_OPEN=project`) or for files (mentioned as `@file` with the first message); `bud.open.go` calls `opened(path)`. Each session is a `claude -p --input-format stream-json --output-format stream-json --verbose` job in its root (`--continue` first, `--resume <its id>` after a stop), started only after `claude auth status` says logged in, otherwise status `missing`. `handle` turns stream-json into `message`, `tool_use`, `done`, `exit` and `status` events (`on(event, fn)`); `interrupt` sends a `control_request`. At most `max_sessions` (3) run, least recently used goes first, and a timer `reap`s ones idle past `ai.claude.idle_minutes`; a stopped one restarts on the next `send`. A project session keeps its conversation id per root (`M.ids_file`, `saved_id`) and resumes it; `--continue` only when there's none and the config dir isn't `~/.claude` (`M.shared()`), and `handback` picks the conversation the TUI last wrote to (JGA-147). An AWS credential error in a failed `result` (or the stderr of a process that died; `M.aws_expired`) sets status `auth` with `M.aws_fix()` in its `why` and a notify; the next `send` lets go of that job (`on_exit` ignores a job that isn't the session's current one) and starts a new one (JGA-150). Linear on Bedrock (no claude.ai connectors) is a `linear` MCP server in Claude Code's own config (clod's since D77), logged in once via `/mcp` in the TUI. On Bedrock the first `api_retry` with `authentication_failed` sets `auth` and interrupts the turn (`M.bedrock(s)`), and `claude.Status.Cloud()` keeps Headroom from being offered there (doctor's `claude command` check warns, JGA-149). Print mode ignores `outputStyle` in `settings.json`, so `M.output_style()` reads it from the config dir and `argv` passes it as `--settings` (D75). `ai.claude.command` (D60) replaces `claude` at the front of every command line (`M.prefix`; `bud agent` too). `tests/lua/claude_test.lua` drives it with a fake `claude` shell script (swap `M.bin` and `M.check_login`). `bud.ai.term` (D48) is Claude Code's own TUI in a terminal pane: `open` calls `claude.handover` (stops the headless job, status `term`, `send` refuses) and the TUI's exit calls `handback` (the next start uses `--continue`, since the TUI may have moved on); `<leader>ac` toggles it, `:BudClaude term` opens it, it's the layout's `chat` pane (`layout/panes.lua`), `send(text)` types a prompt in (opening it without the cursor, waiting for it to draw), and hidden idle ones are reaped like sessions. Its pane is a side pane (`vim.w.bud_side`): `bud.terminal.arrange` (D82) keeps side panes beside the editor and the `<leader>t` terminal under them, right of the full-height explorer. `bud.escape` (D84) makes `jk` leave Insert mode and, in the terminal, this pane and chat (`escape.attach`), go to Normal mode: only `k` is mapped, `vim.on_key` records the last non-`k` key, a `k` within `escape.window` ms of a `j` backspaces it and leaves; Esc isn't mapped (`tests/lua/escape_test.lua`); `<leader>w` is `<C-w>` (`core/keymaps.lua`). `bud.quit` (D83) ends Claude Code's panes and chat (`stop_all`) and an idle shell (`terminal.job()`, no children via `nvim_get_proc_children`) on `ExitPre`, so `:wqa` isn't refused (E948), but nothing while unsaved files make a `:qa` fail (`settles` reads the command from history); `<leader>qq`/`qw`/`qQ` quit, save all and quit, quit without saving. `tests/lua/quit_test.lua`. `tests/lua/claude_term_test.lua` covers it. `bud agent [path]` (`internal/cli/agent.go`) execs the same TUI from the shell in the project root, with `BUD_BIN` set (`agentEnv`), as nvim's sessions have it, so bud-ide's SessionStart hook adds its notes on working inside bud (D77).

**IDE bridge** (D51): `bud.ai.bridge` (`nvim/lua/bud/ai/bridge/`) starts on the first session (`claude.bridge_env`): `websocket.lua` is the RFC 6455 server on vim.uv (own SHA-1 for the handshake) that also answers plain HTTP POSTs, `init.lua` writes the `~/.claude/ide/<port>.lock` (`lock_dir`, swapped in tests), dispatches MCP JSON-RPC (`handle`), sends `selection_changed` and gives headless sessions `headless_args()` (`--mcp-config` over HTTP plus the read-only tools in `--allowedTools`), and `tools.lua` holds the tools, with `openDiff` answering only when the diff is accepted (`ga`/`:w`) or rejected (`q`, or closed any other way: either diff window closing or the proposal wiped answers no at once; `:w`/`:wq` (and `:x`, rewritten to `:wq` there, and `ZZ`) answers and closes the tab a tick later, by number, so `:wq`'s quit stays in the review and a queued review keeps the cursor; a write from another tab (`:wa`) doesn't accept). `<leader>as` shares the selection (`claude.share`: an `at_mentioned` to the TUI, else `@file#L` context for the next message). `tests/lua/bridge_test.lua` is a real WebSocket and HTTP client.

**Permissions** (D52): headless sessions get `--permission-prompt-tool mcp__bud-ide__approve` (the `approve` tool exists only for HTTP clients, `ctx.http` in `bridge.handle`; the session's root rides in the MCP URL's `?root=`), which calls `bud.ai.permissions.request`: edit tools go through `tools.review` (the same diff UI `openDiff` uses), others a float (`y`/`a`/`n`/`r`), queued one at a time, with `a` remembered per project and command. `tests/lua/permissions_test.lua` covers it.

**Chat** (D81, JGA-165; bud's own chat UI is gone): `bud.ai.chat` opens Claude Code's own TUI in its own tab (dashboard `c`, `<leader>ch`, `:BudChat [resume]`) in `~/.local/state/bud/chat/` (`M.dir`), as bud-ide's `chat` agent (`--agent bud-ide:chat`, defined in bud-plugins, read-only tools) when `claude.plugin_file("bud-ide", "agents/chat.md")` finds it in `installed_plugins.json`, else plain Claude Code with a hint to run `bud kit sync`; `BUD_BIN` is left out of its env, and its exit closes the tab. It uses no `bud.ai.claude` session. `bud chat [--resume]` (`internal/cli/chat.go`) execs the same from the shell (`claude.PluginFile`, `tuiArgv` shared with `bud agent`, `paths.Chat`). `tests/lua/chat_test.lua`, `internal/cli/chat_test.go`. Sessions are keyed (`claude.session(root, { key = ... })`, `get`, `drop`), and `extra = true` keeps one (issue, work, gen) from counting against the project sessions; `claude.project_dir` encodes a dir the way Claude Code's store does.

**Inline actions** (`bud.ai.actions`, JGA-90): `<leader>ae`/`af`/`at` type explain/refactor/write-tests for the selection (`@file#La-b`) into the project's TUI (`term.send`), whose edits arrive as the bridge's diffs; `<leader>am` in a gitcommit buffer (or `:BudCommitMessage`) sends the staged diff and recent subjects and puts the `done` reply above git's comments. `tests/lua/actions_test.lua`.

**Tools** (D54): `bud.tools` loads `tools/` (embedded, mounted like `languages/`, `paths.Tools`) and `user-tools/<name>/` after the first screen; `bud tools ls|enable|disable [--reason]|rm|promote` (`internal/cli/tools.go`) owns `tools.disabled` in `config.json` and `tools.json` in the state dir. Tests: `tests/lua/tools_test.lua`, `internal/cli/tools_test.go` (swap `runGit`).

**Generator** (D55): `bud.gen.run(request)` (`:BudGen`, or `bud tools gen` via `BUD_OPEN=gen`/`BUD_GEN`) runs session key `gen` in `user-tools/` with `gen.prompt`, snapshots the dir, shows the conversation in a log buffer (`gen.buf()`, `i` asks for changes), and after each `done` load-tests what `gen.changed` finds (`gen.load_test`, a headless nvim) and enables or disables it through the CLI. `tests/lua/gen_test.lua`.

**Filing issues** (D70, JGA-125): `bud.ai.issue` (`<leader>ai`, `<leader>aB`, `:BudIssue [bud]`, `:BudIssues`) takes a report in a float with `context()` attached, runs `bud-ide:file-issue` in a keyed session (`start`; `skill_installed` looks for the `bud-ide` plugin in Claude Code's `plugins/installed_plugins.json`, from any marketplace), parses the reply's fenced `bud-issues`/`bud-filed` blocks (`parse`), and shows the review (`review_lines`); `policy` (in `bud.ai.permissions.policies`) denies Linear writes until the reviewed proposal is sent. `tests/lua/issue_test.lua` (swap `M.bud`). `bud.ai.work` (D71, `w` in `:BudIssues`, `<leader>aw`, `:BudIssue work ID`) has Claude fix one in `<repo>.worktrees/<id>` (`prepare`), with `policy` accepting edits `inside` it; `tests/lua/work_test.lua`. **Issue targets** (JGA-123): `bud issue target [--bud] [--json] [dir]|set --team T [--project P] [--global] [project]|unset` (`internal/cli/issue.go`) say where an issue filed from the editor goes: a project's `issues` in `projects.json`, else `ai.issues.team`/`project`, and `ai.issues.bud` (bud's own tracker) for issues about bud, whose root is the dev-linked checkout.
