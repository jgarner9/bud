# Release tooling

Bootstrap, the nightly build and release signing. The release flow itself is in CLAUDE.md.

**Bootstrap.** `bud bootstrap [--config] user@host` (`internal/cli/bootstrap.go`) runs the install.sh one-liner over `ssh -t` with `--profile` (default minimal), `--yes` and `--version` of this bud (`releaseVersion`); `--config` pipes `config.json` into the remote state dir first. Tests swap `runSSH`.

**Nightly.** `.github/workflows/nightly.yml` runs daily (and by hand): when main moved since the `nightly` tag, GoReleaser builds a snapshot named `X.Y.Z-nightly.YYYYMMDDHHMM` (one patch past the newest stable tag, via `NIGHTLY_VERSION` in `.goreleaser.yaml`'s snapshot template) and the `nightly` prerelease is deleted and recreated with the same archive names, so `releases/latest` never sees it. `.goreleaser.yaml`'s `git.ignore_tags` leaves the `nightly` tag out when GoReleaser picks the previous release, so a release's changelog starts at the last `vX.Y.Z`. Content releases tag main too (`content-YYYY.MM.DD.N`, `content-channel`), and GoReleaser's `ignore_tags` takes globs only in Pro, so `scripts/release-plan.sh` also outputs `previous`, the newest stable tag older than the one being built, and the release workflow passes it as `GORELEASER_PREVIOUS_TAG`.

**Signing.** Rotating the key is `scripts/rotate-release-key.sh start|finish` (D64), run by hand, never by you: it creates a real key, writes to 1Password and sets the Actions secret. `just rotate-test` covers it with fakes. The release workflow runs `scripts/sign-release.sh` only when the `BUD_RELEASE_KEY` Actions secret is set; it signs `dist/checksums.txt` under namespace `bud-release`, refuses if the key isn't one of install.sh's `RELEASE_KEYS`, and uploads `checksums.txt.sig`. It takes an optional namespace after the file (`bud-release`, the default, `bud-content` or `bud-channel`), which is how the content workflow signs with the same key.

**Content releases.** `.github/workflows/content.yml` (Suite D60, D61; build plan task 1.10) runs `scripts/content-release.sh` on a push to main that changes `content/`, after `go test ./...`, the leak check and `bud registry check`. `edge` numbers the day's cut from the `content-*` tags (`YYYY.MM.DD.N`), runs `bud content pack`, signs `content.json` under `bud-content`, and creates the `content-<v>` release with the bundle, `content.json` and its signature. It then downloads `channel.json` from the `content-channel` release, and `bud content channel --from` moves edge to the new version, refusing the file unless its signature verifies and refusing to move a channel backwards; the result is signed under `bud-channel` and uploaded over the old one. The first release, when there's no `content-channel` tag yet, starts from `--new` instead, so a failed download can never wipe the stable entry. A run by hand with `promote <version>` moves stable to a version edge has had. Every release it makes is a prerelease, so none becomes the repo's latest and install.sh's `releases/latest/download` keeps finding the code archives. A re-run on a commit that already has a content tag reuses that version and only moves the channel. Nothing is published until `BUD_RELEASE_KEY` is set. `just content-release-test` covers the script with fake `gh`, `bud` and signer. The two channel files are uploaded one after the other, so a sync in that moment can see a new `channel.json` with the old signature; it fails that run and succeeds on the next.
