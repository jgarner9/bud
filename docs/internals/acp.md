# The agent over ACP

How bud talks to OpenCode: the Agent Client Protocol over `opencode acp` (D131-D138, BASE.md 4.4). OpenCode is the only agent bud starts (Suite D139, BASE D154), so there is no backend to choose and `ai.backend` is never read. The chat in the IDE is opencode.nvim (D150); this transport is the programmatic session behind `:BudGen`, issue filing, working an issue, inline actions and commit drafts. Checked against the ACP v1 schema (`@agentclientprotocol/sdk` 2.6.0, `schema/v1/schema.json`).

**The protocol.** ACP is JSON-RPC 2.0 over the agent's stdin and stdout, one message per line, with requests going both ways. bud speaks v1 (`initialize` answers with the version it speaks; OpenCode speaks 1). `bud.ai.acp` (`ide/nvim/lua/bud/ai/acp.lua`) is the protocol and nothing else: `connect(argv, opts)` starts the agent with `vim.fn.jobstart` and returns a connection with `request(method, params, cb)`, `notify(method, params)`, `running()` and `close()`; `opts.on_notification` gets `session/update`, `opts.on_request(method, params, respond)` answers the agent's own requests, and `opts.on_exit(code, stderr)` runs when it stops, after every waiting request has failed with "the agent stopped (exit N)". Messages decode with nulls as `nil`; anything that must go out as a JSON object while empty is `vim.empty_dict()` (an empty Lua table encodes as `[]`, which is what `mcpServers` wants).

**A session's calls**, in order:

| Call | Direction | Shape |
| --- | --- | --- |
| `initialize` | bud to agent | `{ protocolVersion = 1, clientCapabilities = { fs = { readTextFile, writeTextFile }, terminal = false }, clientInfo }`; the answer has `agentCapabilities` (`loadSession`, `promptCapabilities.embeddedContext`, ...) and `authMethods` |
| `session/new` | bud to agent | `{ cwd, mcpServers = {} }` returns `{ sessionId, modes?, configOptions? }` |
| `session/load` | bud to agent | `{ sessionId, cwd, mcpServers }`, only when `loadSession`; the history replays as `session/update`s before the answer |
| `session/prompt` | bud to agent | `{ sessionId, prompt = { ContentBlock... } }`; answers when the turn ends with `{ stopReason }`: `end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled` |
| `session/cancel` | bud to agent, notification | `{ sessionId }`; the open prompt then answers `cancelled`, and bud answers any open permission request `cancelled` |
| `session/update` | agent to bud, notification | `{ sessionId, update }`, `update.sessionUpdate` one of `agent_message_chunk`, `agent_thought_chunk`, `user_message_chunk`, `tool_call`, `tool_call_update`, `plan`, `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update` |
| `session/request_permission` | agent to bud | `{ sessionId, toolCall, options = { { optionId, name, kind } } }`, `kind` one of `allow_once`, `allow_always`, `reject_once`, `reject_always`; answered `{ outcome = { outcome = "selected", optionId } }` or `{ outcome = { outcome = "cancelled" } }` |
| `fs/read_text_file` | agent to bud | `{ sessionId, path, line?, limit? }` returns `{ content }`; bud reads the buffer when the file is open, so the agent sees unsaved changes |
| `fs/write_text_file` | agent to bud | `{ sessionId, path, content }` returns null; bud writes through the buffer when it's open |

A prompt's blocks: `text`, `resource_link` (`{ uri, name }`, a file the agent can read itself) and `resource` (`{ resource = { uri, text, mimeType } }`, embedded text such as a selection, only when `promptCapabilities.embeddedContext`). A tool call is `{ toolCallId, title, kind, status, content, locations, rawInput, rawOutput }`; `kind` is `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode` or `other`, and its `content` items are `content` (a block), `diff` (`{ path, oldText, newText }`) or `terminal`. `acp.text(content)` and `acp.diffs(tool_call)` pull those out.


**OpenCode.** bud runs `opencode acp` (`agent.argv()`), which starts a private local server and speaks ACP on stdio; it signs in with OpenCode's own providers. Checked with OpenCode 2.2.7 (a scripted model; the 2.3.2 setup pin has not been validated for this ACP behavior): `loadSession`, streaming, and an edit that runs without asking by default and finishes with a `diff` item of the whole file plus its own patch in `rawOutput.metadata`; with `permissions: [{ action: "edit", resource: "*", effect: "ask" }]` it asks first, the request carrying the `diff` (so bud's review shows it before the write) and options `allow_once`, `allow_always`, `reject_once`. Tools run where `opencode acp` runs, on this machine. bud keeps one session per project (D139): `agent.ids_file` (`agent-sessions.json` in the state dir) saves `{ [root] = { backend = "opencode", id } }` when `session/new` answers, and the next start sends `session/load` with it (falling back to `session/new` when OpenCode no longer has it). A start refused after the process is up (`fail_start`) answers each waiting message not sent and lets the next send start it again. The pane (`agent.session_id`, which starts the session and returns its id only once OpenCode has opened it) and `bud agent` open that session.

**Tests.** `ide/tests/lua/lib/fake_acp.lua` is a fake ACP agent run as `nvim --clean --headless -l`, so tests need nothing installed. The prompt's first word picks a scripted turn (`hello`, `think`, `echo`, `edit <path>`, `read <path>`, `slow`, `fail`, `crash`; see its header), any other word gets `$FAKE_ACP_REPLY` when that is set, and it logs every message it receives to `$FAKE_ACP_LOG`. `ide/tests/lua/acp_test.lua` drives the protocol through it, `agent_test.lua` the session. A test that needs OpenCode's TUI puts a fake `opencode` on `PATH` (`term_test.lua`, `chat_test.lua`, `actions_test.lua`).

**The session** (`bud.ai.agent`, `ide/nvim/lua/bud/ai/agent.lua`, `ide/tests/lua/agent_test.lua`). One OpenCode process per project root, started after the first screen, with the calls `session(root, { key, extra, env })`, `send(text, { root, key, context, selection })`, `on`, `interrupt`, `status`, `stop`, `restart`, `drop`, `get`, `list`, `stop_all`, `reap` and `statusline`. Its events: `status` (`starting`, `ready`, `busy`, `stopped`, `missing`, `error`, with `why`), `chunk` (each piece of the reply as it streams), `thought`, `message` (the whole reply when the turn ends), `tool_use` (`id`, `name`, `kind`, `input`, `diffs`), `tool_update`, `plan`, `permission_request`, `done` (`ok`, `text`, `stop_reason`, `error`) and `exit` (`code`, `crashed`). A send while a turn runs waits its turn, since ACP takes one prompt at a time. `agent.argv()` is `opencode acp`, `agent.tui(root)` is OpenCode's own TUI on a project, and `agent.command` is what tests swap for the fake. `agent.permission(req, respond)` answers permission requests through `bud.ai.permissions.acp`: the same queue, policies, "allow for this session" memory and dialog as every other bud prompt, naming the agent. `permissions.acp_tool` turns the request into what the prompt knows: a diff becomes a `Write` of the whole file as it would be (the diff's `oldText` replaced once in the file, or `newText` for a new file), which opens in the review (`bud.ai.review`); an `execute` call becomes `Bash` with its command. The answer is the agent's own `allow_once`/`allow_always` or `reject_once`/`reject_always` option id. ACP's answer carries no edited version, so changing the text in the review doesn't reach the agent. `interrupt` answers an open permission question `cancelled` before sending `session/cancel`. File reads and writes go through the buffer when the file is open: a read sees unsaved changes, and a write sets the lines and saves. Both go through `agent.resolve(root, path)`, which turns the request into the one string bud then checks and uses: an absolute path (ACP's rule), `..` and symlinks resolved, inside the session's project, and not through a symlink that points nowhere. The buffer is found by exact name or real path, never `vim.fn.bufnr`, which reads its argument as a pattern. So the agent can't read or write the rest of the machine through bud. A diff in a permission request is refused the same way before the review opens, and the review escapes `%` in its winbar title (`review.escape`), since a winbar runs `%{...}`.

**Who uses it.** `bud.ai.session` is `bud.ai.agent` (D139) and nothing else: `ai.backend` is never read, and the commit message, the generator, issues and work require it. Until JGA-402 removes `bud.ai.claude`, `bud.ai.agent.backend()` is a one-line stub that answers `"opencode"` for it. `agent.setup` (from VimEnter) adds the status line, the idle reap (`ai.agent.idle_minutes`) and a session for `bud <dir>` or files. The AI pane (`bud.ai.term`) runs `agent.tui(root)`, `opencode <root>`, and `<leader>ac` opens opencode.nvim (`bud.ai.opencode`, D150) whatever the config says. Inline actions type into the pane's TUI, naming the place in words (`actions.mention`: `main.go lines 3-4`). `<leader>as` (`agent.share`) types the place into the TUI without pressing Enter when it's running, else keeps the lines as the selection sent with the next message. Chat (`<leader>ch`, `bud.ai.chat`) runs OpenCode's TUI in a dir of its own. `done.text` is the text after the turn's last tool call; `message` has the whole reply.

**The CLI side** (`internal/agent`, `internal/cli/ai.go`). The Go side builds the same commands for `bud agent` and `bud ai`, but it still carries the old backend switch until JGA-403 drops it; the Lua side no longer reads it.

**bud's own chat** (D138, `bud.ai.view`, `ide/tests/lua/view_test.lua`). A markdown buffer (`bud://chat/<project>`) holds the conversation and a `buftype=prompt` buffer under it sends (`<CR>`; `<C-c>` interrupts). It listens to the agent's `chunk`, `tool_use`, `tool_update`, `done` and `status` for its session's key: replies stream in under a `## opencode` heading, each tool call is one `> <state> <name>` line updated in place (`○ ◐ ✓ ✗`), a completed edit's changes follow as a `diff` block (`view.patch`: one `vim.diff` makes from the ACP `diff` items OpenCode sends), thoughts are one `> thinking…` line per turn, a plan is a `> - [x]` checklist, the history `session/load` replays shows under `## you` and `## opencode`, `<C-x><C-o>` after a `/` completes the slash commands the agent listed (`available_commands_update`, kept as `session.commands`), and the winbar shows the agent, project and status. It opens as a pane (`bud_side`, beside the editor and above the terminal) or a tab of its own, both windows locked to `<leader>av`; `view.full` switches between them. `ai.agent.chat_ui = "bud"` makes `term.toggle`, `term.full` and the layout's chat pane use it. The conversation survives closing and reopening within a Neovim, but not a restart yet.

**Settings and errors.** `session/new` (and `session/set_config_option`, and `config_option_update`) carry the session's `configOptions`, kept as `session.options`. `agent.set_option(root, id, value, cb)` sends `{ sessionId, configId, value }` (with `type = "boolean"` for a boolean option) and `:BudAgent option [id value]` drives it. An agent may answer a refusal as `Internal error` with the reason in `data.details`; `acp.why(err)` joins the two, and every error bud shows goes through it.
