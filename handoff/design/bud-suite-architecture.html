1. The one-paragraph version

Bud Suite is Jason's personal manager and knowledge keeper. An agent runtime runs around the clock on the home server and is the only place where agent logic lives. It talks to two kinds of model: a local Qwen 35B MoE on a separate machine in the house, which does the routine and private work, and a paid cloud plan for the harder work. It keeps a long-term memory and a categorized knowledge base, both stored as Markdown and served as a site on the tailnet. Thin clients connect to that one server: a chat app for iOS, macOS and Linux for planning, brainstorming, learning and improving Bud itself, and a fast Neovim terminal IDE for coding. Code and content ship from one Bud repo, so every client shows an update banner when something new lands.

2. Guiding principles

  1. Jason drives, Bud supports. In use, Bud is an assistant. Jason does the legwork, the decision-making and the thinking; Bud gathers, drafts, remembers and lays out options, and does not take over the work or decide for him. Its features are judged by how well they support his thinking, not by how much they automate.
  2. Full insight into the architecture. Jason is vibe coding Bud for now, so this document has to stay complete and explanatory: every component, decision and trade-off is written down with its reason, so he can understand and steer the system without reading its code.
  3. Wrap, don't build. Bud uses an existing agent runtime and adds configuration and glue around it, rather than writing its own agent loop (D1).
  4. No lock-in to one model vendor. The runtime and every client must keep working if the cloud plan changes (D2).
  5. Private by default. Anything that has not been classified is treated as private and stays in the house (proposed, see routing).
  6. The server is smart, the clients are thin. Routing, memory, skills and tools live on the server; clients render and send (D6). Coding is the exception: the dev machine runs its own OpenCode beside the IDE (D15).
  7. One source of truth per concern. The Bud repo for configuration and content, one Markdown store for memory and the knowledge base, one tracker for project status.
  8. Local first, cloud on escalation. Qwen handles everything it can, and the paid plan is spent only where it earns its cost (D4).

One registry for providers and models D46

Jason wants the architecture adaptable by nature, so a provider, model or runtime can be swapped as the AI landscape changes. Decided (D46): one source of truth that every runtime's config is generated from, instead of each config naming providers by hand.

  • Where it lives. content/env/registry.jsonc in the public repo holds the generic entries; bud-overlay/env/registry.jsonc overrides them with personal endpoints (tailnet hosts, the Qwen box URL). Keys are only op:// references (D7).
  • What it holds. Providers (name, endpoint, API style, key reference, region), models (provider, context size, cost, privacy tiers allowed), and roles (D58): manager, coding, planning, classifier, FIM, embedding, fallback, curator and vision. Each role lists a model and its fallbacks. The routing tiers (D23, D24) and the route table point at roles, never at model names.
  • How it reaches runtimes. bud sync renders the registry into each runtime's native config: opencode.jsonc for OpenCode today, the manager runtime's config too (whichever Q-runtime picks), minuet's provider settings, and the llama.cpp model list on the Qwen box. Swapping a model for a role is one edit in one file.
  • How it stays honest. bud doctor re-renders and diffs against what each device actually has, flags drift, and pings each endpoint for the roles that device uses.

Runtime adapters. The same idea applies one level up. Each runtime (OpenCode for coding, the manager on the home server) sits behind a thin adapter in internal/: render config from the registry, install and pin, start and health-check, map Bud's permission tiers onto the runtime's own rules, and point the clients at it. Swapping a runtime means writing one adapter, not rewriting clients or content. Skills, agents and commands stay in portable Markdown so they move with it.

6. Routing policy D4

Every request goes through one router before any model sees it. The router answers three questions in order: may this leave the house, how much is it worth spending, and which model is best at it. The fact that this policy exists is decided (D4). The specific tiers, rules and defaults below are proposals for Jason to adjust.

Auto model selection by topic D4

Qwen is the classifier, because it is free and private. For every request it returns a small structured tag: privacy tier, topic (coding, planning, learning, Bud-improvement, personal, admin), difficulty, and which tools it will need. A route table in the Bud repo maps those tags to a model, so changing the policy is a content update, not a code change. Jason can always override the choice in a client, and the reply shows which model answered.

When the Qwen box is off proposed

  • The router notices through a health check and switches to a rules-based classifier (paths, project tags, keywords).
  • Anything the rules cannot place is treated as P0, so the system fails closed.
  • P0 work is queued and resumes when Qwen comes back. Jason sees a banner saying the queue exists.
  • Heartbeats and background memory extraction pause, rather than spending cloud budget.
  • P1 and P2 interactive work may use C1, so the chat app and IDE keep working.
  • Wake-on-LAN (D26). When P0 work is queued, the home server wakes the Qwen box, and the box sleeps again after an idle timeout. proposed A 30-minute idle timeout, counted from the last request to either model; the IDE asks the server for a wake when it starts, so inline completion is ready by the time it's needed, and completion stays off while the box is waking (it never falls back to the cloud).

Serving Qwen D25

llama.cpp's llama-server serves the models (D25), on an AMD RX 6700 XT (12 GB VRAM) with 32 GB DDR5. The setup below is proposed.

  • proposed Vulkan backend. ROCm doesn't officially support the 6700 XT (gfx1031) and needs HSA_OVERRIDE_GFX_VERSION=10.3.0 to run at all; Vulkan works on it out of the box. Measure both once and keep the faster.
  • proposed Experts on the CPU. A Q4 35B MoE is about 20 GB, more than the card holds. With --n-cpu-moe (or -ot exps=CPU) the expert weights stay in system RAM while attention and the KV cache sit on the GPU, which keeps a MoE fast because only a few experts run per token.
  • proposed A small FIM coder model beside it, entirely on the GPU, as a second llama-server for inline completion (mapping G4). The general 35B isn't known to support fill-in-the-middle.
  • proposed A moderate context. About 20 GB of experts in 32 GB of RAM leaves little for the OS and a large KV cache, so the context is capped (for example 32K) and the KV cache quantized; long jobs go to C1.

7. Memory and knowledge base D9

Jason wants the knowledge base to be human-readable and well organized, covering his projects and how his systems are configured, and to update itself and drop information that is no longer relevant. Agents also produce a lot of loose material (observations, session summaries, half-facts) that would clutter a readable KB. The proposal below separates the two, with a curator job as the only bridge between them.

The KB and Linear D8

Linear is where development TODOs and project management live. The KB is reference documentation: what each of Jason's systems and projects is, and how it is configured. proposed The KB does not mirror Linear issues. A project page links to its Linear project, so status lives in one place and the KB stays about how things are, not what's left to do.

The curator job D9

A scheduled job, for example nightly on the local Qwen so it costs nothing and stays private, compares working memory with the KB and makes three kinds of change:

  • Promote. A fact that has come up at least twice, or that Jason explicitly asks to be doc-committed (which promotes it at once), is written into the right project or system page (D33).
  • Rewrite. A page whose facts have changed, for example a reconfigured service, is updated in place, with the reason in the commit message.
  • Retire. Stale content moves to an archive rather than being deleted, so nothing is lost and it can be restored.

Staleness needs evidence, not a guess. A page section counts as stale only when nothing has referenced it within a set window, or when a newer fact contradicts it. When the curator finds a contradiction it cannot settle from evidence, it puts it on a short review queue that Jason clears from the chat app, instead of picking a side.

Working memory lives in SQLite with full-text and vector search (D13). Standard data goes stale after six months to a year without use, and long-standing information is refreshed rather than archived (D33). A page section is flagged for review after 6 months with no reference, and archived at 12 months if nothing refreshes it (D39); any reference or confirmation resets its clock. Pages marked evergreen (system configuration, long-standing facts) get a refresh check at 12 months instead of being archived.

8. Updates and sync proposed

Pushes to the Bud repo carry two different kinds of change, and they should not travel the same way.

  • iOS distribution. Jason has access to a paid Apple developer account (shared with his dad), so TestFlight is available for the iOS app and the macOS app can be signed and notarized. When a new build is waiting, the app shows a banner that opens TestFlight.
  • Content updates (skills, instructions, agents, commands, plugins, connectors, the route table) never need a new app build. Since OpenCode also runs on each dev machine alongside the IDE (D15), content syncs to every device that runs OpenCode, not only the server. How is in the next subsection.
  • Code updates ship as tagged releases and reach each platform through its normal channel.

How a device picks what it needs

A profile names the device's components and which content it takes. Real profiles live in the private overlay; the public repo carries only examples. Globs default to everything, because skills cost only a name and a description per request (OpenCode loads bodies on demand), so carrying all of them is not bloat. Per-device values such as the Qwen URL or the server's tailnet name stay out of the repo: they are 1Password references (D7) or a local override file.

{
  "name": "laptop",
  "components": ["ide", "harness", "app"],
  "channel": "stable",
  "content": {
    "skills": ["*"], "agents": ["*"], "commands": ["*"],
    "plugins": ["approvals"],
    "env": ["base", "coding", "laptop"]
  }
}

The home server's profile has ["server", "harness"] and the server env fragment; the Qwen box has only ["qwen"] (the llama.cpp service and the pinned models) and takes no content.

The private overlay D21 D59

D59 Name: bud-overlay (jgarner9/bud-overlay, private). It says exactly what it is and sorts next to bud and bud-kb. Alternatives: bud-home (reads well, but could be confused with the home server) or bud-private.

  • D59 How it layers. bud sync merges the overlay over the public repo by path and ID: an overlay profile replaces the public example of the same name, overlay env fragments apply after the public ones (so they win), and an overlay skill, agent or command with the same ID replaces the public one. The ledger records which layer each file came from, so bud doctor can say "this skill is your override".
  • proposed How the installer finds it. Optional, so Bud also works for someone with no overlay. install.sh and bud install ask for an overlay URL once (or take --overlay <git url> or BUD_OVERLAY), save it as overlay.repo in the config, and clone it to ~/.local/share/bud/overlay. Then the device profile is chosen from the overlay's profiles/.
  • proposed How it authenticates. The overlay is a plain git repo over SSH, and no token is stored by Bud. On a dev machine, git uses the credentials already there; with 1Password's SSH agent the key never sits on disk. On the home server, which has no desktop agent, a read-only deploy key for the overlay repo is kept in the Bud vault and read by the service account (D7) for each fetch. A deploy key can read only that one repo and can't push, so a stolen server loses nothing else.
  • proposed How it updates. bud sync fetches the overlay alongside the public content check, records the overlay commit in the ledger, and counts an overlay change as a content update for the banner. It is never signed by the release key: trust comes from it being Jason's private repo.
  • proposed What CI guards in the public repo. A check that fails when a public file names a tailnet host, a private hostname, an op:// path outside the examples, or a personal path, so personal details can't leak back into the public repo by accident.

Self-improvement loop D47

Bud improves itself through a loop it owns, built on the registry and sync, rather than a runtime that rewrites its own config. It follows principle "Jason drives": Bud notices and proposes; Jason decides; nothing changes silently.

  1. Observe. The manager records failures and retries, steps Jason repeats by hand, cost and quality per role (from the router's log and Jason's thumbs-up or thumbs-down), approvals that are always granted, and new models and tools that appear.
  2. Propose. It drafts a change: a new or edited skill, a role swap in the registry, a run-alone addition, a config tweak. Each proposal says what it saw, what it would change, and how to tell if it worked.
  3. Review. Each proposal lands as a diff or pull request against content/ (public) or bud-overlay (personal), in a review queue in the app and the digest. It is never applied on its own.
  4. Approve. Jason approves under D10, the same as any push.
  5. Roll out. bud sync ships it on the edge channel first, then stable, and every change has a one-step revert (the previous content version stays on disk).
  6. Check. After a set period the loop compares the role's numbers before and after, and proposes a revert if it got worse.

Landscape scan. A weekly digest of notable new models and tools, each mapped to the role it could fill and how it compares with the current pick on price, context and privacy. A candidate Jason likes becomes a registry proposal and goes through the same loop. The scan uses only public sources, so it can run on P2 models.

9. Trust boundaries and secrets

An always-on agent with tools on the home server needs two written rules: where secrets live and how they reach the tools that need them, and which actions it may take alone.

Secrets D7

1Password holds every secret. The system passes values to the place they are needed without the model ever reading them (D7). Nothing secret lives in the Bud repo, the working memory or the KB. The mechanics below are proposals.

  • References, not values. All config uses op:// secret references, so the Bud repo holds nothing secret. proposed
  • A scoped service account. The home server holds one 1Password service account that can reach only a dedicated "Bud" vault, not Jason's personal vaults. proposed
  • Resolve at launch. op run or op inject fills in values when a tool starts, inside that tool's own process. proposed
  • Create and rotate blind. The agent can create and rotate items through the service account (for example, generating a new password straight into the vault) without seeing the values, and only after phone approval. proposed

The caveat. Once a secret is in a process's environment, anything that can run a shell in that process can read it. So secret-holding tools run as separate processes the model cannot shell into, and every tool's output passes through a redaction filter before the model sees it. This narrows the risk rather than removing it: a tool that echoes its own credentials back is still a leak the filter has to catch.
