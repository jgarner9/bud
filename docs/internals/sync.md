# bud sync

`internal/syncer` is `bud sync` (build plan task 1.8; Suite D46, D57, D59, D60, D61). It brings one device's content and runtime config up to the channel its device profile follows. `internal/cli/sync.go` only reads the config and prints the report.

## Where things come from

| Input | From |
| --- | --- |
| The device profile | config `device`, looked up in the overlay's `profiles/` first, then bud's examples |
| The overlay | `BUD_OVERLAY`, else config `overlay.repo`; empty means none |
| Content releases | config `content.mirror`, else `https://github.com/jgarner9/bud/releases/download` |

A release host serves two kinds of path, so a mirror is a plain file server laid out the same way:

```
<base>/content-channel/channel.json        newest content and code version per channel
<base>/content-channel/channel.json.sig    signed under bud-channel
<base>/content-<v>/content-<v>.tar.gz      the bundle
<base>/content-<v>/content.json            the manifest
<base>/content-<v>/content.json.sig        signed under bud-content
```

The content release workflow (`.github/workflows/content.yml`, described in [release.md](release.md)) publishes exactly these. Content releases are GitHub prereleases, or one of them would become the repo's "latest" release and `install.sh`'s `releases/latest/download` would stop finding the code archives.

## What a sync does

1. Takes the device's sync lock (an `flock` on `~/.local/state/bud/sync.lock`, dropped when the process exits), so a timer and a hand run never interleave; a second run fails at once. A dry run takes no lock. Then reads the ledger, `~/.local/state/bud/sync.json`. Missing means this device has never synced.
2. Fast-forwards the overlay with `overlay.Fetch` (never forced; it stops on local changes or divergence), then finds the profile.
3. Downloads `channel.json` and checks its signature. The offered version is the profile's channel's `content`.
4. Picks the version to use. The installed one again when it's what's offered; the installed one when the offer is a version `--rollback` left; otherwise the offer, which `content.CheckNewer` must find newer than the installed one, so an old signed bundle can't roll a device back.
5. Unless that version's dir is already on disk, downloads its `content.json`, checks the signature and that it names that version, and unpacks the bundle into `~/.local/share/bud/content/<version>/` with `content.Unpack` (every file checked against the manifest; the dir is complete or absent). Deleting the dir makes the next sync fetch it again.
6. Layers the overlay over that dir with `overlay.Layer` and keeps what the profile selects. The registry is the content's `env/registry.jsonc` with the overlay's merged over it, validated; it is never treated as an env fragment.
7. Builds the active link set. `~/.local/share/bud/active` links to `active.d/<hash>`, which holds `skills/<id>` and `plugins/<id>` links into the content version or the overlay. The hash is of the links themselves, so an unchanged selection keeps the same dir.
8. If the profile runs OpenCode (`harness` or `server`), renders `opencode.jsonc` with `adapter/opencode`: skills from `active/skills`, instructions from `content/current/AGENTS.md` then the overlay's, plugins from `active/plugins/<id>`, env fragments public first and the overlay's last. After every fragment's rules come `external_directory` allows for the content versions and the overlay (`opencode.Input.Reachable`, from the resolved data dir), so a fragment that asks before leaving the project still lets skills and instructions load. Agents and commands are copied to `~/.config/opencode/{agents,commands}/<id>.md`. Provider keys that are `op://` references, and the fragments' `bud.opencode_secrets`, go in `~/.local/state/bud/opencode.env` (mode 0600, references only) for `op run --env-file`. If the profile runs `server`, it also renders Hermes's `~/.hermes/config.yaml` and the tier gate's `~/.local/state/bud/hermes-tiers.json` (both mode 0600) with `adapter/hermes` from the registry and the same fragments (see "Hermes" below), and after the switch locks every synced skill in Hermes. It also renders `~/.local/state/bud/mcp-gateway-approvals.json` (mode 0600), the approval tiers and `read_only` flags of every enabled gateway server in the merged bud block, left-out ones included since the gateway still serves them; `bud mcp-gateway` lays it over the servers of `mcp-gateway.json` that set neither (see `mcp-gateway.md`). And it renders `~/.local/state/bud/router-p0-servers.json` (mode 0600), every server in the merged bud block whose `privacy` is only `P0`, left-out and disabled ones included, which `bud router` reads for its provenance rule (Suite D119, see `router.md`). The fragments' bud block becomes both runtimes' MCP servers (see "Tools and MCP servers" below), and each server left out is named in the report's notes.
9. Plans each file against the disk and the ledger, builds the link set, then switches `content/current` and `active` (each a new link renamed over the old, so readers see one or the other; if `active` can't follow, `current` is put back), writes and deletes the files, saves the ledger, and removes unused `active.d` dirs.

Before switching, bud verifies that the content directory and every active link target exist and that the built link set is intact. If either link switch fails, it restores the prior links, or removes a newly created `current` link.

## Tools and MCP servers

The tool map (Suite D72-D79, D81, D85-D87, JGA-358) reaches each runtime through its env fragments. A fragment's top level is OpenCode's own config, so the built-in tool settings sit there as OpenCode reads them: `websearch` off on dev machines and on Exa on the server, permission rules for each MCP server's tools, and so on. The `bud` key is bud's, never passed through to a runtime. `internal/adapter/env` takes it out of the merged fragments and resolves it, and each adapter renders it in its runtime's shape.

```jsonc
{
  "bud": {
    "gateway": "http://<tailnet IP>:8790",   // the MCP gateway; the overlay sets it
    "privacy": "P1",                          // the tier this device's sessions send it
    "mcp": {
      "linear": { "gateway": true, "privacy": ["P1", "P2"] },
      "context7": { "url": "https://mcp.context7.com/mcp", "privacy": ["P1", "P2"] },
      "serena": { "command": ["uvx", "..."], "privacy": ["P0", "P1", "P2"] },
      "memory": { "privacy": ["P0", "P1", "P2"] }  // url from the overlay
    },
    "hermes": { "web": { "keyless_fallback": false } }  // laid over config.yaml as it is
  }
}
```

| Key | What it is |
| --- | --- |
| `gateway` | The MCP gateway's base URL. Its host must be a loopback or tailnet IP address with a port, since the gateway refuses any `Host` that isn't one (its DNS-rebinding guard), so a MagicDNS name would never get through. Empty leaves every gateway server out. |
| `router` | The model router's base URL (Suite D70, D104), for the home server's overlay. Like `gateway`, a loopback or tailnet IP with a port and no path, since bud adds `/v1`. When set, Hermes's private profile names one provider, the router, and one model, `bud/manager`, with no fallbacks of its own. On a P1 device (the server's `bud.privacy`) its chats start at P1 (Suite D117, superseding D95's P0-only models): the provider's `extra_headers` sends `X-Bud-Privacy: P1` on every request, auxiliary calls such as compression included, and the router raises a chat to P0 and keeps it on the local model when a rule matches, a calendar or mail call is in its history, or an earlier request of the same conversation was raised (see `router.md`). A P0 device sends no header, so the router takes every chat as P0. `session_affinity_header` makes Hermes send its conversation id as `x-opencode-session`, which OpenCode Go needs and the router uses to keep a raised conversation P0. A P0 chat is served from a local model and moves to a P1 member of the manager role only once Jason approves (`router:p0-fallback`). The context Hermes is told is the smallest of the manager members allowed P0 or P1. `extra_headers` is Hermes's per-provider header map (merged upstream in July 2026); a Hermes without it sends no header, which the router takes as P0, so it fails closed. The cloud profile still names its providers itself. Empty keeps Hermes on the providers directly. |
| `privacy` | The tier sent in `X-Bud-Privacy` to gateway servers. Empty sends no header, which the gateway takes as P0, so only P0-safe servers would answer. |
| `mcp.<name>` | One server. Names are lowercase letters, digits and `-`; OpenCode names its tools `<name>_<tool>`, which the permission rules match. |
| `.gateway` | `true` reaches it at `<gateway>/<name>/mcp` with the header. It takes no headers or env, since the gateway adds the key. |
| `.url`, `.headers` | A remote server reached directly. |
| `.command`, `.env` | A local server over stdio, its arguments after it. |
| `.hermes_only` | A P0-only MCP server reached directly over a literal loopback URL. Only the private Hermes profile gets its entry. Use the private overlay, for example the [contacts worker](../../server/contacts-mcp/README.md). |
| `.privacy` | The session tiers that may use it. The private agent is denied every server that leaves out `P0`. |
| `.marks_p0` | The server tags each P0 record it returns with `registry.P0Marker`, as Bud memory does (JGA-389), and the router keeps a chat that receives one local. Hermes's private profile then reaches it, when it's a gateway server, at `P0` instead of the device's tier, so it saves at P0 by default and can recall every tier; the cloud profile keeps the device's tier. Needs `P0` in `privacy`, and content format 9. |
| `.approval` | A gateway server only: `{"tools": {"<name>_<glob>": "allow" or "ask"}}`, the gateway's approval tiers (Suite D97, D103). Keys carry the runtime's `<name>_` prefix, as the permission rules do, and `bud sync` strips it, since the gateway matches the upstream's own tool names. A tool no key names asks. A later fragment replaces the whole block, unless it sets only `when`. `when` lists argument rules (Suite D116; see `mcp-gateway.md`, "Argument rules"), their tool globs with the same prefix, effect `allow` or `ask`; a block that sets only `when` adds its rules after the earlier ones and keeps the tools. Needs content format 4, and 7 for `when`. |
| `.read_only` | A gateway server only: every tool only reads, so the gateway needs no `approval` block for it. Not with `approval`. Needs content format 4. |
| `.disabled` | Leaves it out, such as to turn off a public server from the overlay. |
| `hermes` | Laid over Hermes's config as it is: `platform_toolsets`, `web`, `secrets.onepassword.env`, and extras for a server's entry under `mcp_servers.<name>` (such as `trust: untrusted`). It may not set what bud renders for the registry and the D48 changes (see "Hermes" below). |
| `opencode_secrets` | Environment variables `op run` fills for OpenCode, each an `op://` reference: the fragments' own keys, such as `EXA_API_KEY` for websearch and `GITHUB_PERSONAL_ACCESS_TOKEN` for GitHub's MCP server. `bud sync` writes them to `opencode.env` beside the registry's provider keys, and refuses one that names a provider's key variable with a different reference. They name the vault, so they go in the overlay; a later fragment sets a variable over an earlier one's. |
| `sandbox_shell` | Hermes's terminal rules (Suite D114): a list of `{resource, effect}`, a command glob as in the `shell` permission rules and `allow`, `ask` or `deny`, last match wins. When any fragment sets it, the tier gate uses these instead of the permission rules' `shell` rules, which stay the coding devices'. Lists append, so the overlay's rules come after the public ones. Needs content format 5. |
| `tiers_when` | Argument rules over Hermes's own tools (Suite D116), in the shape of an approval block's `when` (see `mcp-gateway.md`, "Argument rules") with Hermes's tool names and `allow`, `ask` or `deny`. A rule whose conditions hold decides over `tiers`, the strictest winning, and nothing loosens a `deny` there; a field the gate can't read asks. It can't name `terminal` or `*`. Lists append. The public one lets `cronjob_manage` with `action: "list"` run alone. Needs content format 7. |
| `tiers` | Hermes's tools by action tier for the tier gate: a tool name or pattern (MCP tools are `mcp__<server>__<tool>`) to `allow`, `ask` or `deny`, with `*` for the rest. A later fragment sets a key over an earlier one's. Needs content format 3. |

A server needs exactly one of `gateway`, `url` and `command`, and one with none is left out until a later fragment sets one; that's how the public fragments list Bud memory while only the overlay knows its address. Fragments merge before the block is read, key by key, so the overlay's `env/personal.jsonc` fills in `gateway`, `mcp.memory.url` or a whole server of its own. A server's `privacy` and `command` are replaced by a later fragment rather than appended to, so the overlay can narrow a server's tiers (taking P0 away) or swap its executable. Values a runtime fills from its environment are `{env:VAR}`, which the Hermes adapter writes as Hermes's `${VAR}`; a `url` may hold them, and the rest of it is still checked. A fragment's own `mcp.servers.<name>` (OpenCode) or `hermes.mcp_servers.<name>` adds fields to a server the block declares (such as `codemode` or `trust`), and is dropped when the server was left out. It may not name a server the block doesn't declare, since that server would have no tiers for the private agent to deny, nor set the transport (`type`, `url`, `headers`, `command`, `environment`; for Hermes `url`, `headers`, `command`, `args`, `env`, `transport`), which comes from the block. A fragment that sets `agents.private` is refused too, so nothing changes the private agent's model or adds a rule after its denies.

The P0 tool rule (Suite D81) is the OpenCode adapter's `private` agent: a primary agent on the first model of the coding role (then the fallback role) allowed P0, whose rules deny `webfetch`, `websearch`, `experimental_image_generate`, `subagent` (a subagent runs under its own rules, not its parent's) and `<name>_*` for every server not allowed P0. OpenCode applies agent rules after every global one, so no fragment's allow outranks them. With no P0 model there's no agent, and a note says so.

## Hermes

`adapter/hermes` renders Hermes's config for Hermes v0.23 (Suite D46, D48), checked against Hermes's own `hermes_cli/config_defaults.py` and docs at tag `v0.23.2`. YAML comes from a small emitter in the package (D1): strings double-quoted, keys sorted, lists of scalars or maps. Both profiles can write their own `onboarding` block and `gateway.service_install_choice`. For a tracked config, sync and doctor compare the remaining bytes with the ledger, and sync carries those values over when it writes an updated render. Explicit values from an env fragment take precedence.

**Two profiles (Suite D95).** Hermes runs as two profiles, each a Hermes home of its own with its own memory, sessions and skills. The default profile, `~/.hermes/config.yaml`, is private: it owns Signal, the calendar and reminders, and its config lists only models allowed P0, so no chat in it can reach a cloud model, by fallback or by `/model`. The cloud profile, `~/.hermes/profiles/cloud/config.yaml`, which Jason reaches with `hermes -p cloud`, lists every chat model and none of the servers only private sessions may use: those P0 may use and neither P1 nor P2 may, whatever the device's own tier. It sets `gateway.standalone: true`, since Hermes otherwise serves every profile from the default profile's gateway process, and the cloud profile has no bot to run. Hermes's hook context doesn't say which model a turn uses before a tool runs, and its `pre_llm_call` hook fails open, so tracking which chats have read P0 data couldn't be made safe; a profile that has no cloud model at all is safe by construction. Both profiles get the same D48 settings, gate and synced skills.

**Models.** In the private profile, each registry provider with a chat model allowed P0 becomes `providers.<id>` (`api` is the endpoint, `transport: chat_completions`, `key_env`, and `models.<name>.context_length`), listing only those models. A provider with none is left out whole, and so is its key, and a note names the models left out. `model` is the manager role's first model allowed P0, and `fallback_providers` its other P0 models, then the fallback role's. A registry whose manager and fallback roles have no P0 model is refused. A fragment that loads a left-out provider's key through `bud.hermes.secrets.onepassword.env` is refused. Hermes's built-in providers read their keys from its environment (`OPENCODE_GO_API_KEY` among them) whatever the config lists, so bud sync also refuses, before writing anything, a `~/.hermes/.env` that sets a left-out provider's key variable or any of the built-in providers' key variables (`hermes.BuiltinKeys`, taken from Hermes v0.23.2's provider plugins and checked again with each pin) that no listed provider uses, byte order mark or not, and names `~/.hermes/profiles/cloud/.env` as its place. The cloud profile lists every provider with a chat model and all their chat models; its `model` and fallbacks are the manager role's members in order, then the fallback role's, whatever their tier. Naming the provider also stops Hermes's auxiliary tasks (compression, titles, vision) from guessing another logged-in provider: they use the main model. A key that is `{env:VAR}` becomes `key_env: VAR`, which Hermes reads from its `.env`; an `op://` key becomes `BUD_<PROVIDER>_API_KEY` in `secrets.onepassword.env`, which Hermes resolves with `op read` at start, so no key is in the file.

**The tier gate.** Both profiles run the same gate on the same tiers file. `bud hermes-gate <tiers file>` reads one call from stdin and answers in Hermes's hook protocol: `{}` runs it alone, `{"action": "approve"}` sends it to Hermes's approval gate (Jason answers in the chat it came from; on Signal by reaction or code, see [signal.md](signal.md)), and `{"action": "block"}` refuses it. The gate does not send a `rule_key`; Hermes v0.23.2 falls back to the tool name, so an `always` decision on another approval surface can grant broader scope. The Signal adapter's reaction and code handling answers `once` or `deny`, but that does not enforce one-call scope across all surfaces. The hook runs before all argument modifications are merged, so its input does not establish that the final executed arguments were approved. Do not rely on this gate for JGA-348's shared one-shot, exact-argument guarantee. A terminal call's approval reason starts with `bud: run` and the whole command as a JSON string, then says why it asks, since Hermes shows a plugin's approval with a label in place of the command (bud-signal reads the command from it, see [signal.md](signal.md)). A `terminal` command is split at `;`, `&`, `|`, `&&`, `||` and new lines outside quotes, each part is matched against the shell rules (OpenCode's globs, last match wins, no match asks), and the strictest part wins. The rules are the bud block's `sandbox_shell` when a fragment sets it, else the permission rules' `shell` rules. Each part is matched as written and again as it runs: from every word after a variable assignment or a wrapper (`env`, `command`, `exec`, `nohup`, `time`, `sudo`, `xargs`, `nice`, `timeout`, `stdbuf`), since a wrapper's options can take values (`sudo -u root git push`) that can't be told from the command without knowing each wrapper, with quotes and backslashes removed, and with a path-qualified program (`./git`, `/usr/bin/git`) read by its base name too; the strictest match wins, so a path never gets the bare name's `allow` but can't dodge its `ask` either (the lesson of Codex issue #28732). `sh -c`, `bash -c` (and `zsh`, `dash`, `ksh`, with any options before it, such as `--noprofile` or `-o pipefail`; any short-option cluster holding `c` counts) and `eval` run their argument as a line of its own, tiered the same way, four layers deep at most, deeper asks. A line with `$( )`, backticks, `( )`, `<` or `>` asks at least when the rules' default (the last `*` rule) is `ask`, since the parts don't show what it runs. When the default is `allow`, as in Hermes's sandbox, the line is split again at those characters too, so a command inside a substitution or subshell is tiered like any other part, and the line asks only when one of them does. Why the sandbox runs alone (Suite D114): Hermes's terminal is a Docker container that can't reach the host, the vault or bud's files, and `execute_code`, which can run the same commands, already ran alone, so asking for `ls` or `curl` bought nothing. `content/env/server.jsonc`'s `sandbox_shell` asks only for effects that leave the sandbox: `git push`, `ssh`, `scp`, `sftp`, `rsync` and publishing (`npm`, `pnpm` and `yarn publish`, `cargo publish`, `twine upload`, `docker push`, `gh release`), and refuses `op`. Nothing from the host is mounted into the sandbox (`docker_mount_cwd_to_workspace: false`), so there are no host paths to list; an overlay that mounts one adds its own rules. The ask list is a speed bump, not a wall: a script the agent writes can still push, which is why pushes and sends that matter are also guarded where they land (the gateway, for Linear, calendar and mail). Hermes's manual mode still asks about any command it deems dangerous, so the gate only ever adds approvals. Every other tool is tiered by the bud block's `tiers`: its exact name, then the longest pattern that matches (the strictest of equally long ones), then `*`, and with none of those it asks. The bud block's `tiers_when` (Suite D116) then looks at the call's arguments: a rule whose conditions hold decides instead, the strictest winning, except that nothing loosens a `deny` from `tiers`, and a field the gate can't read asks. The gate reads the call with its numbers as written, so `equals` tells two large ids apart. Hermes's hook input isn't proof of the arguments that finally run (above), so a `tiers_when` allow is for calls whose worst case is harmless, such as a cron listing. An unreadable tiers file or call is refused, saying to run `bud sync`. Before any of that, a tool on a server only private sessions may use (the tiers file's `private` patterns, `mcp__calendar__*`) is refused unless the call's `profile` is `default`, the private profile; the cloud profile has no such server, so this is a second guard (Suite D95). `content/env/server.jsonc` holds the picks: reads and sandboxed tools run alone, skill writes run alone because Hermes stages them, Hermes's own `memory` is refused (JGA-313, it uses Bud memory's MCP tools instead), cron jobs and the browser ask (one tool both reads and writes each), except a cron listing, which `tiers_when` lets through by its `action`, the browser vault and computer use are refused, and MCP tools run alone because the gateway asks for the writes of each server it reviews and Hermes asks before any tool on an untrusted server (GitHub) that isn't marked read-only.

**One prompt per gateway write (Suite D115).** A server reached through the gateway with an `approval` block is rendered `trust: full` in Hermes, so Hermes doesn't ask before its writes: the gateway does, bound to the exact argument bytes and consumed once (D103), and that is the stronger check. Before, Linear, calendar and mail writes asked twice. GitHub doesn't go through the gateway, so it stays `untrusted`, and a fragment's `bud.hermes.mcp_servers.<name>.trust: untrusted` still wins for any server. The tiers file's `trusted` lists the gateway servers Hermes ends up trusting (an unset trust is Hermes's default, `full`), and `bud doctor` fails when the gateway doesn't review one of them (see "What bud doctor checks").

**Locked skills.** On a `server` device, bud sync copies each synced skill's regular files (not its links) into `~/.hermes/skills/<id>/` (`paths.HermesSkills`, kind `hermes-skill` in the ledger), and the same into the cloud profile's `~/.hermes/profiles/cloud/skills/<id>/`, so the manifest rule applies: a skill the profile drops is removed and a hand-edited copy is skipped and named. Whether bud may write a skill is decided for the whole skill (`hermesSkill`): a skill dir holding files bud doesn't track (Hermes's own, or Jason's) and a path through a link (`~/.hermes/skills`, the skill dir or a subdir) each leave the skill alone, unlocked, with a note, while an empty dir left by a removed skill is reused. Copies keep their source's permission bits. After the files are written, bud runs `hermes curator lock <id>` (and `hermes -p cloud curator lock <id>`) for every skill it copied (idempotent, so new skills are covered too). Hermes keeps the lock in its own `skills/.usage.json`; while it holds, `skill_manage`, `write_file`, `patch` and `terminal` refuse to change the skill. Without `hermes` on `PATH`, or when a lock fails, the report's notes say so.

**Signal and bud-signal.** On a `server` device bud sync also installs `bud-signal`, the Hermes plugin that lets a Signal reaction or code answer an approval, from the binary into `~/.hermes/plugins/bud-signal/` (`hermesPlugin`, kind `hermes-plugin`, layer `binary`; decided for the whole plugin the way a skill is), and renders `plugins.enabled: [bud-signal]` and `platforms.signal` (signal-cli's loopback URL, unknown senders ignored). Both keys are bud's. A plugin dir bud can't write leaves the plugin out of `plugins.enabled`, so Hermes's own Signal adapter, with typed `/approve`, is used. The details are in [signal.md](signal.md). Only the private profile gets them: the cloud profile renders no `platforms.signal` and enables no plugin (Suite D95).

Hermes's built-in `memory` toolset is off in the server content (JGA-313): each profile remembers through Bud memory's `memory_search` and `memory_stage`, which the overlay reaches through the gateway with the profile's own tier, so every runtime shares one store and a staged record waits for Jason's review. The 300 ms recall check remains future work. Cron jobs run in the private profile, which has the gateway process that ticks them. The shared approval service and Herdr approval integration have separate [validation gates](suite.md#build-time-validation). The sandbox uses Hermes's default `nousresearch/hermes-sandbox:desktop` image until a digest is pinned.

## The manifest rule

| On disk | Ledger | What happens |
| --- | --- | --- |
| missing | any | written |
| what bud would write | has it | left, recorded |
| what bud would write | doesn't | left, never recorded, so a later release can't overwrite or delete it |
| what bud last wrote | has it | rewritten |
| anything else | has it | skipped and named as a hand edit; the ledger keeps bud's hash, so `bud doctor` keeps flagging it |
| anything else | doesn't | skipped and named as not bud's; never recorded |

A file the ledger has that the sync no longer wants is deleted when it's still what bud wrote, and otherwise left, named and dropped from the ledger. A step that fails leaves the file's old ledger entry in place, and the ledger is saved either way, so it always matches what's on disk.

## The ledger

`format`, `device`, `channel`, `content` (the version `current` points at), `rolled_back` (versions a rollback left), `overlay` (`repo` and `commit`), `active` (the `active.d` dir) and `files` (each written file's `path`, `sha256`, `kind` and `layer`: `public`, `overlay`, or `rendered` for one built from both). It holds no times, so a sync that changes nothing writes nothing.

## Rollback

`bud sync --rollback` takes the newest version dir on disk older than the ledger's, and runs steps 6 to 9 on it with the overlay as it is on disk (it isn't fetched). The version it left goes into `rolled_back`. A later sync stays put while the channel offers anything no newer than a rolled-back version, so going .1 to .3, rolling back, then being offered .2 and .3 again never brings .3 back; an offer newer than all of them is taken and clears the list. Old version dirs aren't pruned yet.

## Dry run

`--dry-run` does steps 1 to 8 without changing anything: the overlay isn't fetched (the clone on disk is used, or none), and a new bundle is downloaded, verified and unpacked into a temp dir that's thrown away. It reports the same changes a real sync would make.

## What bud doctor checks

`internal/doctor/sync.go` (build plan task 1.9, Suite D46) adds these checks once config `device` is set; a device with none gets none of them. They only read, and of them only the `--net` ones go online. They hold the sync lock while they read (`syncer.TryLock`), because a sync switches the links before it saves the ledger; while a sync runs they are skipped with one warning, so a sync in progress never looks broken (which could roll back a `bud update`).

| Check | OK | Warn | Fail |
| --- | --- | --- | --- |
| device profile | found and valid (overlay's `profiles/` first, `syncer.ProfileDirs`) | | not found or invalid |
| approval reviewer | on a `server` profile only: the review socket (`paths.ReviewSocket`, in the runtime dir) exists and the secret file (`paths.ReviewSecret`) is not empty. It looks at files and never dials | the socket or secret is missing, or `XDG_RUNTIME_DIR` is unset; gateway and ops calls that need approval are refused until the bud-signal plugin runs | never |
| gateway approvals | on a `server` profile only, `--quick` too: every server the tiers file's `trusted` names (the gateway servers Hermes calls without its own prompt, Suite D115) is in the gateway's config (`mcpgateway.Read`, with the approvals file over it) with an approval block or `read_only` | no tiers file yet (never synced), or one from a bud before D115 with no `trusted` key (a warning, so the doctor run right after `bud update` doesn't roll it back) | a trusted server the gateway doesn't review, or a gateway config that can't be read while Hermes trusts servers to it, since a write would then run with nobody asked |
| signal-cli | on a `server` profile only, `--quick` too: `GET /api/v1/check` on signal-cli's daemon at `hermes.SignalURL` (loopback, 2 s timeout). Nothing leaves the machine and nothing is sent on Signal | the daemon doesn't answer 200, so Hermes can't reach Signal and nothing can be approved from the phone; the fix names the `bud-signal-cli` unit | never |
| Hermes version | on a `server` profile, not with `--quick`: the first line of `hermes --version` (the process is stopped after it, so Hermes's update check never runs), compared with the `requires_hermes` pin in the embedded bud-signal `plugin.yaml` | Hermes isn't on PATH, its version can't be read, or it isn't the pinned release, so the plugin doesn't load: approvals need a typed `/approve` and the reviewer socket never starts | never |
| OpenCode harness | executable on PATH reports the pinned version | missing or different version | |
| sync ledger | `current` points at the ledger's version, its dir is there, every file matches its hash (`Ledger.Drift`) | never synced; a file missing or changed by hand | unreadable ledger; `current` gone or pointing elsewhere; the version dir gone |
| registry | the content's, with the overlay's over it, validates (`syncer.LoadRegistry`) | | doesn't validate |
| content layers | names every item the profile takes and its layer: the overlay's (marking each that replaces a public one), the public ones, and the files the sync rendered (`overlay.Layer` over the overlay on disk; a device with no OpenCode lists only skills and plugins) | the overlay is set but not cloned, or the content can't be layered | |
| synced config | `syncer.Check` finds nothing to change (that includes Hermes's `config.yaml` on a `server` device, so a hand edit that turns a tool setting back on, like Hermes's keyless search fallback, is named) | a sync would write or delete something; a file bud would write isn't bud's | rendering fails; a skill or plugin link in the active set is gone or points elsewhere |
| content channel (`--net`) | the newest on the channel, or held there by a rollback | newer content is out; nothing offered; the channel offers an older version; the host can't be reached | |
| model endpoints (`--net`) | every provider a role uses answers `GET <endpoint>/models` | one doesn't answer, or its model list lacks a name the registry uses | |
| embeddings (`--net`) | each model in the embedding role answers `POST <endpoint>/embeddings` with a vector as long as its registry `dims` (JGA-294) | the server doesn't answer or sends no vector, or the vector's length differs, which means it runs other weights than the registry names and memory needs a re-embed | |
| search endpoint (`--net`) | `BUD_SEARXNG_URL`, when set, answers a JSON search | it does not; this only warns, and is checked whether or not a device is set | |

The OpenCode harness check runs for device profiles with the `harness` component in a full doctor run. The ledger check stops there when it fails or the device hasn't synced, the layers check needs a profile, and the render check needs a profile and registry that validate. `syncer.Check` is a dry run of steps 6 to 8 on the version in use with the overlay as it is on disk, so it catches what a hand edit can't: an overlay pull that changed what's rendered, or a `bud update` whose adapter renders differently. It leaves out files the ledger check already named. Drift only warns, since `bud update` rolls back on a check that newly fails, and a hand edit is never the new release's fault; a broken render does fail, since a new release can cause that.

Endpoints get a key only when theirs is an `{env:VAR}` that's set; an `op://` key is never read (Suite D7), so those providers show only that they answer (any HTTP status counts), and a model list is checked only when one comes back (an empty list lacks every name). Down only warns, since the Qwen box sleeps when idle (Suite D26). Tests swap `syncCheck`, `fetchChannel` and `netClient`.
