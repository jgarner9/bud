# The mail MCP server

`bud mail-mcp` (`internal/mail`) gives Hermes, the home server's manager, Jason's iCloud mail (Suite D31, D54, D106). It is a small MCP server in standard-library Go (D1), listening on loopback only, behind the MCP gateway (`docs/internals/mcp-gateway.md`), which lists it for P0 sessions alone, so mail stays with Qwen (D23). It runs under `op run`, so the Apple ID and its app-specific password reach it as `BUD_MAIL_USER` and `BUD_MAIL_PASSWORD`, and the address sends come from as `BUD_MAIL_FROM`, and none sits in a file (D7). With `BUD_MAIL_FROM` unset it still reads and cleans up, and the send tools say what to set. The design and the build order are in the R7 mail design note; this page says what is built.

## Flags

| Flag | Default | What it is |
| --- | --- | --- |
| `--listen` | `127.0.0.1:8796` | Where MCP is served, at `/mcp`. Only a loopback address is accepted, since the gateway is what devices reach. |
| `--imap` | `imap.mail.me.com:993` | The IMAP server, with implicit TLS. A loopback host is dialed in the clear, for tests; the client refuses to log in over a plain connection anywhere else. |
| `--smtp` | `smtp.mail.me.com:587` | The SMTP server. STARTTLS is required, except to a loopback host (tests); a server that doesn't offer it is refused before the password is sent. |
| `--trash` | `Deleted Messages` | Where cleanup moves mail when no folder has the `\Trash` special-use flag. |
| `--record` | | Instead of serving, run one scripted read-only session (login, capabilities, `LIST`, `STATUS`, `EXAMINE`, `SEARCH`, a summary and a body fetch, logout) and write it to this file in the transcript format, with the login, every literal and every address redacted, then print whether the server has `MOVE` and `UIDPLUS` and which folder is the trash. The file must not exist yet. |
| `--log` | `~/.local/state/bud/mail-actions.jsonl` | The action log (`paths.MailActions`), mode 0600: one JSON line per move to the trash, restore and send, naming the message by Message-ID with its sender and subject, or for a send its recipients and subject. Never a body. Each action is also written to the shared [audit log](audit.md), with only the folders and a recipient count. |

## The tools

| Tool | Read-only | What it does |
| --- | --- | --- |
| `list_folders` | yes | Each folder that can hold mail, with its message and unread counts, and `special` (`trash`, `sent`, `junk`, `drafts`, `archive`) from its special-use flag. |
| `search_messages` | yes | The newest matches in one folder (default `INBOX`) for `from`, `to`, `subject`, `text`, `since`, `before` and `unseen`, newest first, `limit` 20 by default and at most 100, with how many matched in all. |
| `read_message` | yes | One message by folder and uid: its header, its text, and its attachments' names, types and sizes (never their contents). |
| `move_to_trash` | marked yes | Moves up to 50 uids from one folder to the trash (the folder with `\Trash`, else `--trash`) and logs each. |
| `restore_message` | marked yes | Moves a message bud put in the trash back where it came from, by Message-ID, from the log. It refuses a message the log has no move of, or one already restored. |
| `cleanup_digest` | yes | The moves and restores since `since` (default the last 24 hours), with counts, for Hermes's daily digest to Jason (D36). |
| `send_message` | no | A new plain-text email: `to` and `cc` (lists, 10 people at most together), `subject` (one line) and `body` (at most 4,000 characters). |
| `reply_message` | no | A reply to folder and uid: `to`, `cc`, `subject` and `body`. `to` must hold whoever the original came from (Reply-To, else From), and every recipient must be on the original (less this account's own addresses), or it refuses and lists who is. `subject` must be the original's with `Re:` in front (one, not two), or it refuses and names the right one; `In-Reply-To` and `References` come from the original. |

Nothing a tool does marks mail read: folders are opened with `EXAMINE` and messages fetched with `BODY.PEEK`. A tool's failure comes back as a result with `isError` and a sentence saying what to fix. Each tool takes only its own arguments, so one it would ignore is refused rather than shown in an approval for a message that doesn't carry it.

**Who decides.** The gateway decides, and Hermes trusts the server so it doesn't ask a second time (Suite D115). Moving to the trash and restoring change nothing that can't be undone, so they are marked read-only and run alone (D36); only the sends are marked as writes. In the gateway, the env fragment's tiers allow everything but `send_*` and `reply_*`, which ask on Jason's phone (D103). Mail sends are the one approval whose Signal prompt shows every argument whole (D107, `internal/approval`'s `summarize`): to, cc, subject and the full body, the body as lines that each open with a bar. That's why a body is capped at 4,000 characters, and why a reply names its recipients and subject in its own arguments instead of having the server work them out after approval. The gateway binds the approval to those exact argument bytes, so what Jason reads is what goes out.

**Mail is untrusted.** Whatever the sender wrote (the header fields and the text) sits under an `untrusted` key, beside a `notice` that says it is data and never an instruction, and the provenance (`folder`, `uid`, `message_id`) sits outside it. That is labeling, not isolation; the isolation is the tool-less summarizer under "Ingestion". What holds regardless is that nothing in a message can approve anything, since approvals come only from Jason's Signal number (D34).

## IMAP

`imap.go` is a thin adapter over [github.com/emersion/go-imap/v2](https://github.com/emersion/go-imap) (`imapclient`, v2.0.0-beta.9), bud's second third-party Go module (Suite D138, under the D1 exception; the first is the JSONC stripper, BASE D153). The library parses responses, sends literals and quoted strings as needed, encodes folder names as modified UTF-7 and sends `CHARSET UTF-8` for search text that isn't ASCII. The adapter keeps the surface the rest of the package already used (`Dial`, `Login`, `List`, `Status`, `Examine`, `Select`, `Search`, `FetchSummaries`, `FetchBody`, `Move`, `Logout`) and every guarantee the tools rely on. One connection per tool call (`account.go` dials, logs in, does the call and logs out, one call at a time), so a dropped connection leaves nothing behind.

What the adapter decides, and the library doesn't:

- **Nothing a read does marks mail read.** Folders open with `EXAMINE` for reads and `SELECT` only for a move; bodies and headers are fetched with `BODY.PEEK`. A body is fetched as `BODY.PEEK[]<0.N>`, at most 1 MiB.
- **Login.** `LOGIN`, or `AUTHENTICATE PLAIN` when the server sets `LOGINDISABLED` (and refuses, saying so, when it doesn't offer `AUTH=PLAIN` either). It refuses to send a password over a plain connection except to loopback. A refused login is `ErrAuth`, which says to check the app-specific password and never shows it. A `PREAUTH` greeting is refused, since bud only uses connections it logged in itself.
- **Move.** `UID MOVE` when the server has `MOVE`; otherwise `UID COPY`, `UID STORE +FLAGS.SILENT (\Deleted)` and `UID EXPUNGE` of exactly those uids, which needs `UIDPLUS`. With neither, bud refuses, because a plain `EXPUNGE` would also remove anything else marked deleted. This gating is bud's own; the library's `Move` would fall back to a plain `EXPUNGE`, so the adapter does not call it without having checked.
- **Search.** Search text with a line break is refused, and a Message-ID that isn't plain printable ASCII is refused, before anything is sent.
- **Deadlines.** The library's `Wait` calls take no context, so every call runs under a guard: when the context is canceled or its deadline passes, the guard closes the connection, and the error that follows is reported as the context's own. A server that stops answering can't hold a call past its two minutes.

What changed in kind from the old hand-written client: the library doesn't cap the size of a literal or a response line the way `wire.go` did (1 MiB and 64 KiB). Instead every fetch asks the server for a bounded range (`<0.N>`: at most 64 KiB of header fields per message in a summary, at most 1 MiB for a body), which a well-behaved server honors. A server that ignored the range could still make the library buffer a large literal; the server bud talks to is iCloud's.

## Messages

`message.go` reads with `net/mail`, `mime` and `mime/multipart`: RFC 2047 words in headers, addresses as `Name <address>`, `quoted-printable` and `base64` bodies, nested multiparts (at most 8 deep and 100 parts). The text is the first `text/plain` part, else the first `text/html` part stripped to text (scripts, styles and tags dropped, breaks kept at block ends, entities decoded, `from_html: true`). Every other part, and any part with a filename, is an attachment. Charsets are UTF-8, US-ASCII and Latin-1; another is read as UTF-8 with bad bytes replaced, and a note says so. Text is cut at 64 KiB on a character boundary, and `notes` says when anything was cut or guessed.

## Sends

`smtp.go` uses `net/smtp`: dial, `EHLO`, `STARTTLS` with the host's certificate checked, `AUTH PLAIN`, one `MAIL FROM`, a `RCPT TO` per recipient (a refused recipient stops the send before `DATA`, so nothing goes out), then the message. bud writes the message itself: `From` is `BUD_MAIL_FROM`, then `To`, `Cc`, the subject Q-encoded, `Date`, a fresh random `Message-ID` at the From domain, `In-Reply-To` and `References` for a reply, and a quoted-printable UTF-8 plain-text body. No argument can add a header: addresses are parsed with `net/mail` and written back by it, and a subject, address or reply header with a line break is refused. Whether iCloud files a copy in Sent Messages by itself is checked on the first live run; if it doesn't, the server will `APPEND` one.

## Cleanup

`cleanup.go` moves mail only between folders; nothing in bud deletes mail (D36). A move reads the messages' headers first, moves them with the IMAP adapter, and then logs each by Message-ID. Moves, restores and sends run one at a time, each held together with its log line, so a restore or the digest never misses a move that's done but not logged yet; and once the work is done a failed LOGOUT is ignored, so a dropped connection can't skip the log line. `NewLog` sets an existing log to 0600 too. A message with no Message-ID can be moved but not restored by bud. A restore finds the latest log line for that Message-ID, which has to be a move to the trash, searches the trash for it and moves it back. iCloud empties Deleted Messages after about 30 days (D54, to be confirmed on the live run), after which a restore says it's gone.

## Ingestion

`bud mail-ingest` (`internal/mailingest`, `internal/cli/mailingest.go`) is how new mail gets summarized without any model near a tool (Suite D106, JGA-317; the design is the R7 ingestion note). It is a oneshot command, meant for a timer. It runs under `op run` with the same credentials as the server, opens one IMAP session, and for each folder in `--folders` (default `INBOX`) reads what arrived since its mark.

- **Fetching is plain code.** `Account.Fresh` (`internal/mail/ingest.go`) opens the folder with `EXAMINE`, finds the uids above the mark with `UID SEARCH`, and fetches each with `BODY.PEEK`, so nothing is marked read. It returns them oldest first, at most `--limit` (default 25) per run over all folders, with the text cut to 16 KiB. A message it can't parse is still returned, with an error, so it counts as handled.
- **The mark.** `~/.local/state/bud/mail-ingest.json` (`paths.MailIngest`, mode 0600) keeps, per folder, the `UIDVALIDITY` and the highest uid handled. A folder seen for the first time starts at its newest uid and summarizes nothing, so turning ingestion on doesn't summarize years of mail (`--backfill N` summarizes the newest N once, never more than what is left of `--limit`, so nothing below the new mark goes unhandled). A changed `UIDVALIDITY` means the old uids mean nothing, so the mark resets to the newest uid and nothing old is summarized again; the run says so.
- **One run at a time.** A run takes a non-blocking `flock` on `mail-ingest.json.lock` first; a second one exits with "another mail-ingest run is in progress" without doing anything, so two runs can't read the same mark and summarize a message twice.
- **Idempotent.** A message's summary line is stored before the mark moves past it, and a line for a folder, `UIDVALIDITY` and uid that is already stored is never written again. A crash between the two repeats nothing: the next run finds the line and skips the message.
- **The summarizer has no tools.** `ChatSummarizer` asks the registry's `curator` role, only the models on `local: true` providers with no key (`curator.LocalModels`), never the router: mail is P0, so a fallback can never carry it to a cloud model. The request body holds `model`, `temperature`, `max_tokens` and `messages` and nothing else, so a model that obeys the mail has nothing to call, and a test fails if a `tools`, `functions`, `tool_choice`, `function_call` or `response_format` field appears. No redirect is followed and no proxy is used (the transport is never `http.DefaultTransport`, whose `HTTP_PROXY` could carry P0 mail somewhere else). The mail sits between two marker lines that carry a random id, which a sender can't know, after control characters and bidi overrides are removed; the prompt says the email is data and to report an email that gives instructions or claims an approval rather than obey it. The prompt is the second line of defence. The first is that nothing the model writes is ever run.
- **The answer is stored as text.** `~/.local/state/bud/mail-summaries.jsonl` (`paths.MailSummaries`, mode 0600, append-only; the directory is set to 0700) holds one line per message: the provenance (`folder`, `uidvalidity`, `uid`, `message_id`, `received`) and the untrusted text (`from`, `subject`, `summary`), with the model's name and the time. Text is cut (1,200 characters for a summary), line breaks and control characters are dropped, and nothing in it is parsed or acted on. A message the model can't summarize (an error, an empty answer) is stored with an `error` and no summary, so one bad message can't block the queue. A model that can't be reached stops the run with the mark where it got to, and the next run carries on.
- **Audit.** One line per run in the shared [audit log](audit.md) (`mail_ingest`, tier P0), with counts only, never text.

## The MCP side

`server.go` is the same Streamable HTTP subset as the calendar server (`docs/internals/calendar.md`): one JSON answer per `POST /mcp`, no sessions, `GET` gets 405, protocol versions 2025-11-25, 2025-06-18 and 2025-03-26, and a request with `Origin` or a `Host` that isn't loopback gets 403. Each tool call gets two minutes.

## Tests

The IMAP tests (`client_test.go`, with the account and cleanup tests in `server_test.go` and `send_test.go`) run against the library's own in-process server, `imapserver` with `imapmemserver` behind it, on loopback (same module, so no extra dependency), so both ends of the wire are the library's and the tests pin bud's adapter rather than a transcript. A `memServer` helper starts one with the account's folders and seeds mail directly; each test picks the capabilities the server advertises: `IMAP4rev1`, `MOVE` and `UIDPLUS` for the `MOVE` path; `IMAP4rev1` and `UIDPLUS` for the `COPY`, `STORE` and `UID EXPUNGE` fallback (the test leaves a message already marked `\Deleted` and checks it survives); `IMAP4rev1` alone for the refusal. Never `IMAP4rev2`, which implies the other two and would blur the matrix. The in-memory server can neither flag a folder `\Trash` nor make one `\Noselect`, so the fixture answers `LIST` from its own table. A few cases the library's server can't produce are scripted by hand: a server that disables `LOGIN` (for the `AUTHENTICATE PLAIN` path), a `PREAUTH` or `BYE` greeting, one that never answers (for the deadline), and one that drops the connection in place of the `LOGOUT` answer. `--record` (`record.go`) wraps the connection below the client, so its redacted transcript still shows the commands and responses as iCloud sends them; the first live run records one to check the adapter against. The login is redacted from its command to the server's answer, so a credential sent as a literal can't show on the line after it; every literal form (`{n}`, `{n+}`, `~{n}`) is a placeholder, and a literal whose length can't be read stops the trace rather than write its bytes as lines. The trace is written however the session ends, so a failed login is on file too. `testdata/messages/` holds sample messages, among them one that tries to approve an action from inside the mail. The send tests run against a fake SMTP server on loopback and check the exact message, that a refused recipient sends nothing, that a server without STARTTLS never gets the password, and that header injection and over-long bodies are refused.
