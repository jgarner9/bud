# Approval hook investigation

Inspected on 2026-11-19 on the current machine, without starting or changing either production service; the only thing started anywhere was the isolated, localhost-only OpenCode probe server described under "Synthetic API probes and limitations", stopped again after its tests. These are observations, not a compatibility promise for other installations.

## Hermes

The installed checkout identifies as `v0.23.2`, commit `ae2a81ccc00e9b7c06301523e5bb09608397149c`. The launcher could not report its version in the read-only sandbox because it tried to create an installation lock. The findings below come from the checkout's `agent/shell_hooks.py`, `hermes_cli/plugins.py`, `agent/tool_executor.py`, and `tools/approval*.py`.

| Question | Finding |
| --- | --- |
| Pre-execution hook | `pre_tool_call` receives the tool name and argument object. It can block with a message, request the human approval gate, or modify arguments. Shell hooks receive JSON on stdin; Bud's gate uses this interface. Shell hooks can be configured fail-closed. The enclosing plugin dispatch otherwise catches hook exceptions and proceeds. |
| Identity | The hook receives session, task, tool-call, turn and API-request identifiers where available; shell hooks place the non-top-level fields in `extra`. These can be empty, and a tool-call ID alone is not necessarily unique. The gateway approval queue separately creates a fresh request ID; a card is resolved by session key and request ID, with optional actor authorization. Do not assume the hook's tool-call ID is the approval request ID. |
| Exact arguments | The hook sees the parsed tool argument object at that point, not necessarily the original serialized bytes or final execution arguments: other hooks can return modifications. The approval raised by a hook carries a synthetic `<tool> (plugin approval rule)` label and the hook's reason, not the argument object. Bud includes the terminal command in its reason; this does not provide arbitrary tool arguments. |
| Cancellation | Gateway waits end without execution on timeout, interruption, session teardown or withdrawal. `withdraw_gateway_approval` targets a pending request; settle observers can learn when it ends. Cancellation is distinct from a user denial. Pending entries are in process memory and do not survive a restart. |
| Resume | The executing thread waits for a decision. Resolving the matching live request with `once`, `session`, `always` or `deny` wakes it; approval allows the existing call to continue through the remaining checks, denial blocks it. A late or unknown card ID resolves nothing. `once` covers the leader of a coalesced request, while followers need their own prompt. Reconnection can inspect pending requests while the process remains alive; this is not durable resumption after restart. |

There is a scope caveat: `hermes_cli/plugins.py` supplies the tool name as the fallback `rule_key` when the hook omits it. Thus an `always` answer can create a standing approval at tool-name scope; omitting `rule_key` does not itself enforce one-call approval. Bud's Signal adapter deliberately answers only `once` or `deny`, but other approval surfaces offer broader choices. The existing gate should not be treated as enforcing one-call scope across all surfaces.

## OpenCode

After the initial inspection, OpenCode `v2.3.2` was installed from `@opencode/cli@latest` in the user-local npm prefix. Its version was checked with isolated XDG directories. Its hooks and approval lifecycle have not been exercised against a running session.

The current upstream [plugin documentation](https://opencode.ai/docs/build/plugins/server/) describes a V2 `permission.evaluate` hook that sees session ID, action, resources, optional metadata and tool source, and can set allow, ask or deny. It also describes `tool.execute.before` for inspecting or replacing tool input. The [permissions documentation](https://opencode.ai/docs/permissions/) says MCP permission resources are `*`, so resources alone do not establish exact arguments. The current [API documentation](https://opencode.ai/docs/api) describes experimental endpoints to list pending requests, get one by session and request ID, and reply with `once`, `always` or `reject`. The request schema includes ID, session ID, action, resources and optional metadata. These upstream descriptions do not establish complete argument coverage or cancellation and restart semantics for the installed binary. Inspect matching source and exercise cancellation, concurrent requests, late replies and restart before selecting an integration.

## Follow-up: version-matched investigation (2026-11-19)

OpenCode package `@opencode/cli` is `2.3.2`; upstream tag `v2.3.2` resolves to commit `c0ad18b402eb2827fc1ee71c171b1177b3fc02d1`. Source examined: `packages/core/src/{tool.ts,tool/mcp.ts,permission.ts,permission/saved.ts}`, `packages/plugin/src/effect/{permission.ts,tool.ts}`, `packages/server/src/handlers/permission.ts`, and `packages/core/test/permission.test.ts`. The Hermes checkout and commit are as above. These are version-specific observations.

### OpenCode hook boundaries and identity

`tool.execute.before` receives `tool`, `sessionID`, `agent`, `messageID`, tool-call `id`, and mutable `input`. Hooks can change both tool and input; the dispatcher executes the resulting values after the hooks finish (`tool.ts`). An individual hook cannot assume another hook will not subsequently modify them. A gate implemented solely as an ordinary before hook therefore has no established final-arguments guarantee without controlling all later hooks or a runtime-enforced final boundary.

`permission.evaluate` receives `sessionID`, optional `agent`, `action`, `resources`, optional `metadata`, optional `source`, and mutable `effect`/`message`; it does not itself receive a universal argument object or permission request ID. Configured deny is applied before the hook. Tool source contains `messageID` and tool-call `id`; nested calls can be attributed to a parent call by `row()`, so retain the session and request ID as well and do not assume source always uniquely identifies a nested call. A pending request has its own ID, session, action, resources, optional metadata and source. Concurrent requests need separate request IDs; never correlate by action alone.

For MCP tools specifically, `tool/mcp.ts` calls permission assertion after before-hooks with `metadata: { input: input ?? {} }`, `resources: ["*"]`, and `save: ["*"]`, then passes that input to `mcp.callTool`. Thus the permission hook can inspect the post-before-hook argument object on this path, and the pending request includes it. This is not a universal guarantee for other tools or arbitrary plugins, and it is not evidence that the downstream MCP server will interpret the object in a particular way. Bind a canonical immutable snapshot, identity and decision at a runtime-enforced boundary and prevent later mutation or revalidate immediately before dispatch.

`permission.ts` appends saved project rules before calling the evaluation hook. A hook can force `ask` for matching calls even when a saved allow would otherwise apply, but a reply of `always` saves the request's `save` patterns and reevaluates pending requests, potentially allowing other matching requests. This is unsafe as a one-call policy unless the runtime enforces one-call-only choices and prevents any standing grant from satisfying that policy. For MCP the saved pattern is `*` for that action. `--auto`/unattended settings also deserve explicit fail-closed treatment.

### Synthetic API probes and limitations

Started the installed binary with isolated XDG directories and a localhost-only server; no real model, tools, MCP server, contacts or messages were used. Created synthetic sessions and permission requests through the v2 API. Two same-action requests had distinct IDs. `once` returned 204 and left the other pending; repeating that reply returned 404. An `always` reply returned 204, persisted a project action/resource rule and caused the next matching synthetic request to return `allow`. Three requests with explicit tool sources showed that rejecting one also rejected its same-session, same-message sibling, while a different-message request remained pending. Deleting that session left the remaining **API-created** request in the global pending list; restarting the test server cleared it. These are API `ask` requests, not executing tool calls: they do not demonstrate cancellation, timeout, or teardown of an active tool's `assert` waiter. The isolated server was stopped after testing.

Source evidence: `assert` removes a pending request in an `ensuring` finalizer when its waiting fiber ends; `close` rejects pending entries, and pending state is an in-memory map. Unknown or already-settled replies return not found. `reject` without feedback fails the step; with feedback it propagates a corrected error; it also rejects same-session, same-message siblings. No expiry timer appears in this permission service; a one-hour expiry must be supplied and enforced by Bud. Cancellation timing, live tool execution, hook ordering under concurrent real calls, teardown of a running call, and late replies after cancellation remain unverified in a running session. In particular, the synthetic API deletion result must not be generalized to all running-session teardown paths.

### Hermes enforcement gap

In `hermes_cli/plugins.py`, all pre-tool hook results are collected; `modify` directives are shallow-merged, while the first approval directive retains its own message and rule key. `_dispatch_pre_tool_call_hooks` resolves that approval before returning the merged arguments to `agent/tool_executor.py`. Therefore a hook's own view/reason cannot prove it approved the merged final arguments, including modifications returned by another hook. The executor then applies further checks and invokes execution middleware; a final immutable authorization boundary must be placed after all argument-changing middleware and hooks, immediately before dispatch, with a fail-closed recheck if arguments can change later.

The native approval gate is insufficient for mandatory one-call scope across all surfaces: `_run_approval_gate` short-circuits on YOLO, `approvals.mode: off`, and existing session grants; its human decision supports session and permanent choices, and unattended configuration can auto-approve. A random per-call `rule_key` would limit collisions but does not disable these bypasses or bind the final arguments. Restricting only Signal responses is insufficient. A runtime change should provide a mandatory, non-bypassable one-shot gate with only approve-once/deny across CLI, gateway, desktop, API and unattended paths; ignore or reject broader replies and prior grants, fail closed on missing authority, timeout, cancellation and restart, and validate the final immutable arguments and live session at dispatch. Bud must own durable expiry, replay protection and audit transitions; pending Hermes gateway entries themselves remain in memory. This is a proposed requirement, not a verified existing API.
