# CLI internals

The Go side of bud, one paragraph per area. CLAUDE.md keeps the registry, prompts, errors, embedded config and paths.

**Colour** (`internal/cli/color.go`, JGA-109): `paint(w, style, s)` adds ANSI codes only when `w` is a terminal `*os.File`, `TERM` isn't `dumb` and `NO_COLOR` is unset, so tests (buffers) and pipes stay plain. Pad text before painting it, or the codes break the columns: `cell(w, style, s, width)` does both. The list and status commands share one palette (JGA-159): names bold, kinds, paths and descriptions dim, on/enabled green (`onStyle`), attention yellow, broken red; `config ls`/`get` bold the JSON keys (`paintJSONKeys`). `TestListsColourLikePlain` forces `colorOn` and checks that stripping the codes gives back the plain output byte for byte.

**Completion** (`internal/cli/complete.go`, JGA-96): `bud completion bash|zsh|fish` prints a few lines that call the hidden `bud __complete <words> <current>` (left out of help), which walks `CommandRegistry`, flags (`valueFlags` for flag values) and `argValues` (layouts, languages, tools, kit entries, config keys, projects, all read from files, never through nvim). Nothing printed means the shell completes file names.

**`bud config`** (`internal/cli/configcmd.go`, JGA-93): `ls [--changed]`, `get`, `set [--force]` (value parsed as JSON, else a string; unknown keys refused unless `--force` via `config.Known`; the whole file must pass `Settings()` before it's saved), `unset` (`File.Unset`), `edit` (bud's nvim, then checked; tests swap `editFile`), `path`. `File.Effective` is a key's value with defaults filled in.

**Uninstall.** `bud uninstall` removes the synced files in `~/.config/bud` (manifest-tracked only, via `nvim.RemoveConfig`), the whole data, state and cache dirs (`--keep-config` spares `config.json` and `user-tools/`), and any app bundle `bundle.Find` says bud built. First it takes the kit out of the Claude Code dir in the ledger (`kitRemoval`, a `kit.Unsync`) unless that's bud's own, inside the data dir (JGA-151); a kit it can't list is reported as kept, never blocking the rest. It removes the binary only when `install.sh` recorded installing it in `~/.local/state/bud/install.json` (`installer.ReadReceipt`, D20); self-update will use the same record. It always lists what it will remove and asks first, unless `--yes`.

**Launching.** `open` resolves its args into a workspace: no args is the cwd, one dir is a project, and files open from the root found by walking up to `.git` (else the first file's dir). Then `nvim.Launch` `chdir`s and replaces the bud process with nvim via `syscall.Exec`. Nothing runs after that, which is why plans for in-editor processes (like the Claude Code session in BASE.md 4.2) live in Lua, not Go.

**Launch.** `bud launch [--terminal] [--layout] [path ...]` (`internal/cli/launch.go`, D46) opens a new terminal window running this binary as `bud ... open <abs paths>`, after checking the paths, layout and terminal up front. `internal/launcher` has one file per terminal (`kitty.go`, `ghostty.go`) registering a `command` that builds the argv; on macOS both go through `open -n -a <app> --args`, and the inner command carries the caller's `PATH` via `/usr/bin/env`. Terminals are found with `installer.Lookup`/`Terminal.Locate`. Tests swap `launchWindow` and `launchTerminals`.

**Installer.** `internal/installer` installs missing system deps through the package manager (D16): Homebrew on macOS; pacman, then apt, then dnf on Linux. `NewPlan(deps)` works out which of some deps are missing (`Needed(profile)` for the base set) and `Plan.Command()` the exact command line (with `sudo` unless running as root); `bud install` prints it, asks y/N (`--yes` skips), then `Plan.Run()` runs it on the terminal and re-checks. With no package manager, or no consent, it returns a `*MissingError` naming the deps and the command. It never upgrades what's installed, with one exception (D107): on Linux, `Dep.Tool` (Neovim and tree-sitter-cli) is a pinned download. `Installed()` then also needs the version on PATH to be at least `Tool.Min`, `Plan.Downloads()` lists what to fetch, `Plan.Command()` leaves it out of the package manager's command, and `Plan.Run()` calls `Tool.Download`, which checks the archive's SHA-256 against the digest pinned in the source before unpacking into `<data>/managed/<name>-<version>/` and linking `<data>/bin/<bin>`. `main` calls `cli.UseManagedBin` so that dir is first on PATH for bud and everything it starts. macOS and CPUs with no pinned build use the package manager. Per-manager package names live in `Dep.Pkgs`, `Dep.Bins` lists alternative binary names (apt's `fdfind`), and `FullOnly` deps are skipped by the minimal profile. Language specs name binaries in `system`; `ForBins` turns them into deps, from `LanguageDeps` (go, python3, node with their package names) or as a package named after the binary. `bud install` asks profile and terminal, then languages (`internal/cli/install.go`, prompts in `prompt.go`), and only writes answers that differ from the defaults into `config.json` (no `languages` key means the profile's preset). The language question needs nvim to read the specs: with nvim present, every question comes first and one install covers base and language deps; on a fresh machine the base deps go in first, then the languages are asked and their deps installed. Under `curl | sh`, `install.sh` runs it with `</dev/tty` so the prompts read the terminal, not the script.

**`bud lang`** (`internal/cli/lang.go`, D34) lists specs and edits `config.json`'s `languages`; `enable` also installs system deps and runs the plugin restore. The user's specs live in `user-tools/languages/` (`Paths.UserLanguageSpecs`), read after bud's own and never part of a preset (`Spec.Builtin`, set from which dir a spec came from).

**Projects.** `internal/projects` owns `projects.json` (D36): `Load`/`Save` keep unknown keys and save atomically, `Add` canonicalizes paths and picks unique names, `Sorted` is pinned, then last opened, then name. `open` registers `ws.Root` when `Workspace.Project` is set (a dir arg, or files inside a `.git` repo) and only logs a failure, so a bad registry never blocks opening. `bud projects` (`internal/cli/projects.go`) edits it; Lua reads it through `bud.projects` (read-only).

**Languages from Go.** `internal/lang.Load(shipped, dirs...)` reads specs by running `nvim --clean --headless -l` on this binary's `lua/bud/lang/dump.lua` (extracted to a temp dir with the engine, so a synced copy never matters), which loads them with `bud.lang` and writes JSON. `shipped` puts the embedded specs first; an earlier dir wins on a name clash. `Set.Preset`/`Enabled` apply the same preset rule as Lua. `bud install` reads shipped plus `~/.config/bud/languages`; `bud doctor` reads the synced dir and fails only for a broken spec the manifest says bud shipped (D33). Its tests need nvim and skip without it, so CI runs them in the smoke job.

**Dev link.** `bud dev link [path]` (`internal/cli/dev.go`, `nvim.Link`) swaps the synced copy in `~/.config/bud` for symlinks into a checkout (each top-level entry of `nvim/`, plus `languages` and `layouts`) and a `.bud-dev-link` marker; `SyncConfig`, `Apply`, doctor and `RemoveConfig` see the marker (`nvim.DevLink`) and leave the links alone. `bud dev unlink` removes them and syncs the shipped config back.

**Migrations.** `migrations/NNNN_name.lua` (embedded, `bud.Migrations()`) run once each from `nvim.Apply`, after the sync and before the plugin restore: `internal/migrate.Run` records each in `~/.local/state/bud/migrations.json` as it succeeds and stops at the first failure, so it reruns next time. A fresh install (no sync manifest yet) marks them all done instead (`MarkAll`). Each runs in `nvim --clean --headless -l` with `BUD_CONFIG_DIR`/`BUD_DATA_DIR`/`BUD_STATE_DIR`/`BUD_CACHE_DIR`; `migrations/0001_example.lua` documents the contract. Never edit or renumber a shipped one.

**Version.** `internal/version.Version` is set by GoReleaser via `-ldflags -X`. Without it, `String()` falls back to the module version Go stamps into the build.
