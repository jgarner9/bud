# The agent over ACP

How bud talks to its AI backend in 1.1 (D131-D138, BASE.md 4.4): the Agent Client Protocol, the backends, and what each one leaves out. Checked against the ACP v1 schema (`@agentclientprotocol/sdk` 2.6.0, `schema/v1/schema.json`) and OpenClaw 2026.11.3's docs and packages on 2026-11-13.

**The protocol.** ACP is JSON-RPC 2.0 over the agent's stdin and stdout, one message per line, with requests going both ways. bud speaks v1 (`initialize` answers with the version it speaks; every backend below speaks 1). `bud.ai.acp` (`nvim/lua/bud/ai/acp.lua`) is the protocol and nothing else: `connect(argv, opts)` starts the agent with `vim.fn.jobstart` and returns a connection with `request(method, params, cb)`, `notify(method, params)`, `running()` and `close()`; `opts.on_notification` gets `session/update`, `opts.on_request(method, params, respond)` answers the agent's own requests, and `opts.on_exit(code, stderr)` runs when it stops, after every waiting request has failed with "the agent stopped (exit N)". Messages decode with nulls as `nil`; anything that must go out as a JSON object while empty is `vim.empty_dict()` (an empty Lua table encodes as `[]`, which is what `mcpServers` wants).

**A session's calls**, in order:

| Call | Direction | Shape |
| --- | --- | --- |
| `initialize` | bud to agent | `{ protocolVersion = 1, clientCapabilities = { fs = { readTextFile, writeTextFile }, terminal = false }, clientInfo }`; the answer has `agentCapabilities` (`loadSession`, `promptCapabilities.embeddedContext`, ...) and `authMethods` |
| `session/new` | bud to agent | `{ cwd, mcpServers = {} }` returns `{ sessionId, modes?, configOptions? }` |
| `session/load` | bud to agent | `{ sessionId, cwd, mcpServers }`, only when `loadSession`; the history replays as `session/update`s before the answer |
| `session/prompt` | bud to agent | `{ sessionId, prompt = { ContentBlock... } }`; answers when the turn ends with `{ stopReason }`: `end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled` |
| `session/cancel` | bud to agent, notification | `{ sessionId }`; the open prompt then answers `cancelled`, and bud answers any open permission request `cancelled` |
| `session/update` | agent to bud, notification | `{ sessionId, update }`, `update.sessionUpdate` one of `agent_message_chunk`, `agent_thought_chunk`, `user_message_chunk`, `tool_call`, `tool_call_update`, `plan`, `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update` |
| `session/request_permission` | agent to bud | `{ sessionId, toolCall, options = { { optionId, name, kind } } }`, `kind` one of `allow_once`, `allow_always`, `reject_once`, `reject_always`; answered `{ outcome = { outcome = "selected", optionId } }` or `{ outcome = { outcome = "cancelled" } }` |
| `fs/read_text_file` | agent to bud | `{ sessionId, path, line?, limit? }` returns `{ content }`; bud reads the buffer when the file is open, so the agent sees unsaved changes |
| `fs/write_text_file` | agent to bud | `{ sessionId, path, content }` returns null; bud writes through the buffer when it's open |

A prompt's blocks: `text`, `resource_link` (`{ uri, name }`, a file the agent can read itself) and `resource` (`{ resource = { uri, text, mimeType } }`, embedded text such as a selection, only when `promptCapabilities.embeddedContext`). A tool call is `{ toolCallId, title, kind, status, content, locations, rawInput, rawOutput }`; `kind` is `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode` or `other`, and its `content` items are `content` (a block), `diff` (`{ path, oldText, newText }`) or `terminal`. `acp.text(content)` and `acp.diffs(tool_call)` pull those out.

**The backends** (`ai.backend`, D131):

| Name | Command bud runs | Signs in with | Leaves out |
| --- | --- | --- | --- |
| `openclaw` | `openclaw acp [--url <ai.openclaw.url>] [--token-file <ai.openclaw.token_file>] --session agent:<ai.openclaw.agent>:bud:<project>-<hash>` | The Gateway token; the models' own logins live on the Gateway host | Diffs, `fs/*`, terminals, model choice, per-session MCP servers (it errors on any), `ask_user` questions; permission requests only for exec approvals during a turn; `session/load` replays only bridge-made sessions |
| `claude` | `claude-agent-acp` (npm `@agentclientprotocol/claude-agent-acp`) | Claude Code's own login and `~/.claude` | Nothing bud uses |
| `codex` | `codex-acp` (npm `@zed-industries/codex-acp`) | Codex's own login (ChatGPT Plus) | Not checked yet |
| `opencode` | `opencode acp` | OpenCode's providers | Not checked yet |
| `custom` | `ai.custom.command` | Its own | Whatever it does |

**OpenClaw** (D132). The Gateway runs on the home server (port 18789 by default, a WebSocket protocol of its own, v4, with Ed25519 device identity and pairing for full clients). bud never speaks that protocol: `openclaw acp` is OpenClaw's own bridge from ACP on stdio to the Gateway, so the CLI handles the token, device identity and reconnects. `--url` doesn't reuse the CLI's implicit credentials, so give `--token-file` with it. Plain `ws://` is accepted only for loopback, private, `.local` and `.ts.net` hosts; use Tailscale or `wss://`. Each ACP session maps to one Gateway session key. bud gives each project its own with `--session` (D139, `agent.session_key`): the key is made on first use and continued after, so the web UI, the apps and `openclaw tui` see the same thread. `--session-label` fails for a label that doesn't exist yet, so bud doesn't use it. Claude Code on the Gateway is the `claude-cli` runtime (set per model: `agentRuntime: { id: "claude-cli" }`), and ChatGPT Plus is the Codex OAuth profile (`openclaw onboard --auth-choice openai-codex`). Anthropic's terms for third-party use of a Claude subscription have moved before; check them when setting up.

**Checked against a real Gateway** (OpenClaw 2026.11.3 on Node 24, loopback, token auth, a scripted OpenAI-compatible model; 2026-11-13). `initialize` answers `openclaw-acp` with `loadSession`, `embeddedContext` and `image`, and `sessionCapabilities` `list`, `resume` and `close`; `session/new` answers with `configOptions` (thought level and the like). A turn streams `agent_message_chunk`s and ends `end_turn`; `session/cancel` ends it `cancelled`. Prompts reach the model prefixed with the time and working directory, and OpenClaw adds a "runtime context" user message after them. An edit is a `tool_call` (`kind` `edit`, `rawInput` the tool's own `path` and `edits`) that runs without asking, and the `tool_call_update` that finishes it carries the unified diff in `rawOutput.details.patch` (`agent.patch(update)`). Exec is `kind` `execute`; with the Gateway's `tools.exec.mode` at `ask` it sends `session/request_permission` with options `allow-once` (`allow_once`) and `deny` (`reject_once`), and a deny fails the tool with "Exec denied (... user-denied)". The default mode, `full`, never asks. The streams are in `tests/fixtures/openclaw/` (paths replaced with `/work`), and the fake replays them.

**Tests.** `tests/lua/lib/fake_acp.lua` is a fake ACP agent run as `nvim --clean --headless -l`, so tests need nothing installed. The prompt's first word picks a scripted turn (`hello`, `echo`, `edit <path>`, `read <path>`, `slow`, `fail`, `crash`, and `replay <log>` for a recorded OpenClaw turn; see its header), and it logs every message it receives to `$FAKE_ACP_LOG`. `tests/lua/acp_test.lua` drives the protocol through it.

**The session** (`bud.ai.agent`, `nvim/lua/bud/ai/agent.lua`, `tests/lua/agent_test.lua`). It has `bud.ai.claude`'s calls (`session(root, { key, extra, env })`, `send(text, { root, key, context, selection })`, `on`, `interrupt`, `status`, `stop`, `restart`, `drop`, `get`, `list`, `stop_all`, `reap`, `statusline`) so a consumer moves over by changing its `require`. Its events: `status` (`starting`, `ready`, `busy`, `stopped`, `missing`, `error`, with `why`), `chunk` (each piece of the reply as it streams), `thought`, `message` (the whole reply when the turn ends), `tool_use` (`id`, `name`, `kind`, `input`, `diffs`), `tool_update`, `plan`, `permission_request`, `done` (`ok`, `text`, `stop_reason`, `error`) and `exit` (`code`, `crashed`). A send while a turn runs waits its turn, since ACP takes one prompt at a time. `agent.argv(backend, get)` builds each backend's command line, and `agent.command` is what tests swap for the fake. `agent.permission(req, respond)` answers permission requests through `bud.ai.permissions.acp`: the same queue, policies, "allow for this session" memory and dialog as Claude Code's, naming the backend. `permissions.acp_tool` turns the request into what the prompt knows: a diff becomes a `Write` of the whole file as it would be (the diff's `oldText` replaced once in the file, or `newText` for a new file), which opens in the review; an `execute` call becomes `Bash` with its command. The answer is the agent's own `allow_once`/`allow_always` or `reject_once`/`reject_always` option id. ACP's answer carries no edited version, so changing the text in the review doesn't reach the agent. `interrupt` answers an open permission question `cancelled` before sending `session/cancel`. File reads and writes go through the buffer when the file is open: a read sees unsaved changes, and a write sets the lines and saves.

**Wired so far.** `bud.ai.session` is the configured backend's session: `bud.ai.claude` for `ai.backend = "claude"` (until task 6 moves it onto `claude-agent-acp`), else `bud.ai.agent`; each call goes to the backend configured at the time. The commit message, the generator, issues and work use it. `bud.ai.claude.setup` hands over to `bud.ai.agent.setup` (the status line, the idle reap, a session for `bud <dir>` or files) when the backend isn't `claude`, and `opened` starts the agent's session instead of Claude Code's. The AI pane (`bud.ai.term`) runs `agent.tui(root)`, the backend's own TUI, for every backend but `claude`: `openclaw tui --url ... --session <the project's key>` with the token from `ai.openclaw.token_file` in `OPENCLAW_GATEWAY_TOKEN` (the TUI takes no token file), `codex`, or `opencode <root>`. Checked against the real Gateway: that TUI shows the same thread the ACP session wrote. Inline actions type into whichever TUI runs. Chat (`<leader>ch`) runs `agent.chat_tui`, OpenClaw's TUI on `agent:<agent>:bud:chat`. From the shell, `bud agent` and `bud chat` exec the same TUIs (`internal/agent.TUI`, `SessionKey`, `ChatKey`); the session key is pinned to the same literal in both test suites, so the shell and the editor always open one Gateway session per project. `done.text` is the text after the turn's last tool call, as Claude Code's `result` was; `message` has the whole reply. Tests of the Claude path `dofile("tests/lua/lib/claude_backend.lua")`, which makes `ai.backend` read `claude`; `tests/lua/term_backend_test.lua` covers the pane on OpenClaw.

**The CLI side** (`internal/agent`, `internal/cli/ai.go`). `agent.Argv(settings)` builds the same command lines as the editor, and `agent.Check(settings, quick)` looks the command up, reads its `--version` (blank for adapters without one), and for OpenClaw checks the token file (there, and not readable by others), the URL (`ws://` or `wss://`, plain `ws://` only to the hosts OpenClaw accepts) and, unless `quick`, a TCP dial to the Gateway. Each problem has a fix and says whether it stops the backend (`Hard`). `bud ai status [--json]` prints it, `bud ai setup` installs a missing command with npm and asks for the Gateway's URL and token file, and the doctor's "ai backend" check warns with the same fixes (it never fails: bud works without AI). Tests swap `lookPath`, `versionOf` and `dial`, and the CLI's `aiCheck` and `npmInstall`.
