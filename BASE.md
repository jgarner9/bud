# Bud IDE: BASE plan

> Status: built and released (v0.20.0). Everything in sections 1–5 exists unless it's marked as later; the decision log below records why each part is the way it is, and the user docs are in `docs/`. The name `bud` is settled (D6).
> Date: 2026-10-24, updated 2026-11-06

## 0. The one-paragraph version

One GitHub repo (`jgarner9/bud`) holds everything: a small **Go CLI** (`bud`) that installs, launches, updates and extends the environment, a **Neovim config** that runs in its own isolated namespace (`NVIM_APPNAME=bud`, so it never touches an existing `~/.config/nvim`), declarative **language specs** that drive LSP / lint / format / treesitter, an **AI layer** built on Claude Code (one session per project that its TUI pane, inline help, a tool generator and the TUIs you build in Neovim all share, plus a chat mode outside any project), a **dashboard** you land on when you run `bud` with no arguments, and **app bundles** for macOS and Linux that open your terminal of choice with a custom pane layout. A one-line `curl | sh` grabs the Go binary, and the binary does the rest. The Neovim config, the language specs, layouts, tools and migrations are embedded in the binary, so the binary is the whole release: updating means swapping in a newer `bud` and syncing its embedded config, automatically in the background at boot (D9) or by hand with `bud update`. No repo clone is needed. `git` is still required, but only because Neovim's `vim.pack` uses it to fetch plugins.

### Guiding principles

1. **Fast first.** Lazy-load everything, keep startup under ~50 ms, no blocking work at boot (update checks are async).
2. **One source of truth per concern.** A language is defined in exactly one file. A layout is defined in exactly one file.
3. **Reproducible.** Plugin versions are pinned by a committed lockfile that ships inside the binary, so every machine on the same `bud` version gets the same thing.
4. **Layered config.** Shipped defaults (embedded, bud-owned) < machine-local overrides < generated/user extras. Secrets never live in the repo.
5. **Go does the system stuff, Lua does the editor stuff.** The CLI installs, launches and updates. Neovim configures itself.

### Where things live on a machine (outside the repo)

There's no repo clone on user machines. The `bud` binary carries the shipped files, and everything below is either synced from it or machine-local.

Linux and macOS use the same XDG paths (D13), which is also where Neovim looks on both.

| What                                                   | Where                                                    |
| ------------------------------------------------------ | -------------------------------------------------------- |
| The `bud` binary (holds the embedded config)           | `~/.local/bin/bud` (or `install.sh --bin-dir`)           |
| Previous binary, kept for rollback                     | `~/.local/share/bud/bud.prev`                            |
| Nvim config (synced copy of the embedded `nvim/`)      | `~/.config/bud`                                          |
| Machine config (terminal, channel, langs, `ai.claude.*`) | `~/.local/state/bud/config.json`                         |
| Personal generated tools (not in the repo yet)         | `~/.local/share/bud/user-tools/`                         |
| Bud-managed binaries + Mason packages                  | `~/.local/share/bud/bin`, `~/.local/share/bud/mason`     |
| Project registry (recent files come from Neovim's oldfiles) | `~/.local/state/bud/projects.json`                       |
| Pinned files (`bud.marks`, per project)                | `~/.local/state/bud/marks.json`                          |
| Chat history                                           | Claude Code's own session store (D23)                    |
| Secrets (MCP keys)                                     | none in bud: Claude Code's config (clod) reads them from the environment or the keychain (D77) |

`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` override the defaults when set.

`bud` resolves all of these through `internal/paths`, so nothing else hardcodes a path.

`~/.config/bud` holds a `.bud-manifest.json` listing every file the last sync wrote. Sync overwrites those files, deletes ones a newer release dropped, and never touches anything else in the directory. For working on bud itself, `bud dev link` fills `~/.config/bud` with symlinks into a checkout (one per top-level entry of `nvim/`, plus `languages` and `layouts` → the checkout's own, the same tree the binary embeds; one symlink to `nvim/` would miss them) and a `.bud-dev-link` marker, so Lua edits show up on the next nvim start. Sync sees the marker and leaves it alone until `bud dev unlink`, which removes the links and syncs the shipped copy back. A new top-level file in `nvim/` needs `bud dev link` again.

### Key architectural choices (and why)

- **The binary is the release (D5).** Shipping config inside `bud` means the CLI and the editor config can never drift apart, installs need no `git`, and an update is one verified download. The cost is that a config change needs a release, which is a one-line change to `VERSION` (D80).
- **Languages are data, not code.** Each `languages/<lang>.lua` returns a table. The Lua engine wires it up, and the Go CLI can read the same file by running `nvim --headless` to dump it as JSON (so there's no second format to keep in sync).
- **Mason installs language tooling, Go installs system tooling.** Mason handles LSP servers, linters, formatters and debuggers per language spec. `bud install` handles Neovim itself, git, ripgrep, fd, and runtimes like node/python when a language needs them. A Nerd Font is yours to install.
- **Plugin stack (D29):** `vim.pack` (D27), native `vim.lsp.config` + nvim-lspconfig, mason.nvim, conform.nvim (format), nvim-lint (lint), nvim-treesitter, blink.cmp (completion), fzf-lua (finding things, D28), mini.jump2d and mini.statusline (D68), oil.nvim (file editing as a buffer, and the explorer pane, D79), neo-tree (git pane), aerial.nvim (symbols outline), mini.clue (key hints), mini.notify, nui.nvim (bud.ui), dropbar.nvim (breadcrumbs), render-markdown.nvim (D88), nvim-dap + nvim-dap-view (D66), gitsigns + diffview-plus, catppuccin (D74 has the interface pieces). AI is Claude Code through `bud.ai.claude` (D26), not a chat plugin.
- **The pane layout lives inside Neovim**, not in the terminal. That way it works identically in any terminal and over SSH. An optional tmux/zellij wrapper gives persistent sessions on remote boxes.

## 2. Language specs (the extensibility contract)

A language file answers six questions: what files, what parser, what LSP, what linter, what formatter, what it needs installed.

```lua
-- languages/go.lua (illustrative; languages/_template.lua documents every field)
return {
  filetypes  = { "go", "gomod", "gowork", "gotmpl" },
  treesitter = { "go", "gomod", "gowork", "gosum" },
  lsp        = { gopls = { settings = { gopls = { gofumpt = true } } } },
  lint       = { "golangcilint" },        -- nvim-lint names
  format     = { "goimports", "gofumpt" }, -- conform names
  mason      = { "gopls", "golangci-lint", "goimports", "gofumpt" },
  system     = { "go" },                -- things `bud install` makes sure exist
  root       = { "go.work", "go.mod", ".git" },
  minimal    = false,                   -- true: in the minimal profile's preset (D30)
  dap        = "delve",                 -- optional debug adapter, installed by Mason (D66)
}
```

Adding a language is: `bud lang add <name>` copies `_template.lua` into `~/.local/share/bud/user-tools/languages/`, you fill it in, then `bud lang enable <name>` installs its tools (or let the AI draft it, see section 4). Bud's own specs are in every preset; yours are only on when enabled by name. Removing is `bud lang disable <name>` (or `bud lang rm <name>` for one of yours). Enabled languages per machine are a list in `config.json`, so a small SSH box can run only `bash` and `python` while your laptop runs everything (D34).

## 4. AI layer

Claude Code only, for now (D26). Every part below runs on the project's Claude Code session (4.2) and is drawn by TUIs in Neovim. Three parts:

1. **Assistance:** Claude Code's own TUI in a side pane (`<leader>ac`), "explain / refactor / write tests for selection" (`<leader>ae` / `af` / `at`, typed into that TUI, edits come as diffs to accept, D81) and commit-message drafting (`<leader>am` in a commit message, or `:BudCommitMessage`). Claude Code's own login is the only auth.
2. **Tool generator (`:BudGen` in nvim, `bud tools gen` in the CLI):** you describe what you want ("a command that opens the test file for the current file", "add Zig support"), the AI writes either a **tool** (`manifest.json` + `init.lua`) or a **language spec**, shows you a diff, and on accept it lands in `user-tools/` and loads immediately, no restart.
3. **Lifecycle commands** so generated stuff never rots: list, enable, disable, remove, and **promote** (move from your machine-local `user-tools/` into the repo's `tools/`, commit, push, so every machine gets it).

Guardrails: generated code runs through a headless nvim load test before it's activated, a broken tool is auto-disabled with a notification, and nothing is promoted to the repo without your explicit accept.

### 4.1 Claude Code setup (`bud kit`)

How Claude works (the Bud persona, code style, planning, which tool to use when, the bud-specific skills) lives in one place, the public [`jgarner9/bud-plugins`](https://github.com/jgarner9/bud-plugins), which every Claude surface loads (D77). bud shares `~/.claude` by default, where clod (Jason's private machine setup) keeps the MCP servers, settings and `core.md` rule, so the kit only makes sure Claude Code has bud's plugins.

**In the repo:** `kit/kit.json`, and nothing else:

```json
{
  "marketplaces": { "bud-plugins": "https://github.com/jgarner9/bud-plugins.git" },
  "plugins": ["bud@bud-plugins", "bud-ide@bud-plugins"]
}
```

| Plugin | What it brings |
| ------ | -------------- |
| `bud@bud-plugins` | `bud:code-style`, `bud:planning`, `bud:debugging`, `bud:verify`, `bud:tools` (the lookup ladder and Basic Memory cache), `bud:bootstrap-project`, `bud:release`, `/bud:plan-to-linear`, the `code-reviewer` agent |
| `bud-ide@bud-plugins` | `bud-ide:bud-dev`, `bud-ide:file-issue` (what `:BudIssue` runs), the `chat` agent chat mode runs as (5.5), and a SessionStart hook with the notes on working inside bud, only when `BUD_BIN` is set |

**Sync rules:**

1. Bud only touches what it added. The ledger (`~/.local/state/bud/kit-ledger.json`) records each marketplace and plugin; anything you set up yourself, from any source, isn't in it and is never touched. A plugin already installed (clod's local checkout) is skipped as yours, and so is a marketplace of the same name. Only a copy that loads in every project counts: one at user scope, one claude.ai syncs, or one an organisation's policy installs (managed). A copy installed at project or local scope is named in sync's output, but bud still installs its own at user scope, and it never uninstalls a project or local copy (JGA-183). A plugin claude.ai syncs loads as `name@synced` and counts as yours too; bud uninstalls any copy of its own then, so the synced one loads and updates with claude.ai (JGA-177). Another copy you installed would load instead and keep the synced one's updates out, so `bud kit sync` names every such copy with the `claude plugin uninstall` for its scope (from its project's dir for a project or local one), and the full `bud doctor` warns (`synced plugins`, leaving out plugins in `kit.disabled`; for bud's own copy still there, the fix is `bud kit sync`), but bud never takes out a copy it didn't install (JGA-182). A plugin of the same name installed from another marketplace, not by bud, is yours as well, and bud adds no second copy beside it (D91).
2. Everything goes through `claude plugin` (`marketplace add|update|remove`, `install|update|uninstall --scope user`). A marketplace bud added is refreshed at every sync, since Claude Code doesn't update a git marketplace by itself, and bud's plugins are updated at every sync from whichever marketplace they came from, yours included (JGA-174).
3. bud sets no output style (D78). A style you pick yourself is still passed to headless sessions, which print mode would otherwise ignore.
4. `kit.json`'s `core` (`bud-plugins/core.md`) names the always-on instructions that claude.ai's personal preferences hold a pasted copy of. bud reads it from the marketplace's checkout and, when it changed since `bud kit core --pasted`, says so after each sync and in a doctor warning, which the dashboard shows (JGA-179).
5. `kit.json`'s `expected_mcp` lists the servers bud's sessions rely on Claude Code's config for (clod's); the daily ones only (Basic Memory, Context7, Exa, D102); the full `bud doctor` warns about any missing, and about a missing `core.md` rule (JGA-175).
6. What an older bud synced (MCP servers, skills, agents, commands, output style files and the `outputStyle` it set, the `CLAUDE.md` block) is taken out on the next sync, only where it's still what bud wrote.

**Commands:**

```text
bud kit sync [--dry-run]                       # also runs after bud install and bud update
bud kit status                                 # per item: synced / not synced / skipped and why
bud kit ls
bud kit unsync [--dry-run] [--yes]             # take out what the kit added, forget the ledger
bud kit core [--pasted]                        # print core.md to paste into claude.ai; --pasted records it
bud kit add plugin <name@marketplace>          # in a checkout's kit.json
bud kit add marketplace <name> <source>
bud kit rm <name>                              # the next sync uninstalls it
bud kit enable|disable <name>                  # this machine only (kit.disabled)
```

### 4.2 A Claude Code session alongside the editor (D25)

Opening a project or files in bud also starts Claude Code in the same place. Every AI UI in the config talks to that one session, so Claude already knows which project you're in and what you have open, and you can build your own TUIs in Neovim on top of it.

**Who starts it, and when.** Neovim does, from `nvim/lua/bud/ai/claude.lua`. The Go CLI can't: `bud` hands its process over to nvim with `syscall.Exec`, so there's nothing left to own a child process, and starting things inside the editor is Lua's job anyway (principle 5). The session starts in a `vim.schedule` callback after `VimEnter`, so the editor is on screen before Claude Code begins loading (principle 1).

**Where it runs.**

| How bud was opened              | Claude Code's working directory                                | Context it gets                    |
| ------------------------------- | -------------------------------------------------------------- | ---------------------------------- |
| `bud <dir>`                     | that directory (the project root)                              | the project                        |
| `bud <file>` / `bud a.go b.go`  | the project root found from the files (language `root` markers, then `.git`), else the files' directory | the opened files, as `@file` context |
| bare `bud` (dashboard)          | no session until you open a project from the dashboard         |                                    |
| chat (5.5)                      | Claude Code's TUI in `~/.local/state/bud/chat/`, not tied to code (D81) | whatever you point it at |

**What runs.** One Claude Code process per project root per Neovim instance, run as a job in headless streaming mode (`claude -p --input-format stream-json --output-format stream-json`). Lua owns the conversation, so any UI can render it however it likes. For the times you want Claude Code's own interface, `:BudClaude term` opens it in a terminal buffer on the **same session** (it resumes the session id), and closing it hands the session back to the native UIs. Only one of the two drives the session at a time.

**What it can see in the editor.** bud also runs the IDE bridge (D51), the WebSocket protocol Claude Code uses for editor integrations (the one `claudecode.nvim` implements), and starts Claude Code pointed at it. That lets Claude Code see your open buffers, current selection and diagnostics, and lets its proposed edits show up as Neovim diffs you accept or reject.

**The API your TUIs use.** `require("bud.ai.claude")` is the only way anything in bud talks to Claude Code, so nothing spawns its own process:

```lua
local claude = require("bud.ai.claude")

claude.session()                      -- the current project's session (starting it if needed)
claude.send("explain this", { context = { "lua/x.lua#L10-20" } })
claude.on("message", function(msg) ... end)   -- also: tool_use, permission_request, done, exit
claude.interrupt()                    -- stop the current reply
claude.status()                       -- "starting" | "ready" | "busy" | "stopped" | "missing" | "auth" | "term"
```

The project's TUI pane, the commit draft, `:BudGen`, issues and any TUI you add are all just consumers of this module. Chat (5.5) is the one exception: it's Claude Code's TUI on its own, outside any project, so it needs no session (D81).

**Lifecycle.**

- **Opening a project** from the dashboard or `<leader>p` starts a session for that root, or reuses it if this Neovim already has one.
- **Reopening a project later** resumes bud's last conversation there by default (`ai.claude.resume = "continue"`, D76): its id is kept per project, so it's never one you started yourself or a keyed session's; set `"new"` to start fresh each time.
- **Switching projects** keeps the last three sessions running and stops any idle for `ai.claude.idle_minutes` (D49); a stopped one starts again on the same conversation (`--resume`) the next time it's used.
- **Quitting Neovim** stops every session on `VimLeavePre`. If Claude Code crashes, the status line shows it and one key restarts it on the same session.
- **Starting a session costs nothing.** No tokens are spent until you send something.

**Permissions** (D52). Claude Code's permission questions ("allow this edit?", "run this command?") come through as `permission_request` events and appear as a Neovim prompt, using the hook headless mode provides for that (`--permission-prompt-tool`, pointed at a tool on bud's bridge). bud never loosens Claude Code's permission mode on its own.

**When Claude Code isn't there.** If `claude` isn't installed or isn't logged in, no session starts and the editor works as normal. The dashboard shows a banner with a one-key fix (`c` runs `bud claude setup`, which installs Claude Code and walks you to its login), and `bud doctor` reports it.

**Config** (machine config, D13): `ai.claude.autostart` (default `true`), `ai.claude.resume` (`"continue"` or `"new"`), `ai.claude.idle_minutes` (default 30, D49), `ai.claude.command` (a wrapper such as Headroom, D60), `ai.claude.args` for extra flags, and `ai.claude.config` (share `~/.claude` or use bud's own dir, D77). `docs/config.md` has every key.

Flag names and the bridge protocol details get re-checked against Claude Code's docs when this is built, like the paths in 4.1. The module's interface avoids Claude Code specifics, so another backend could slot in later (D26), but none is planned.

## 5. How the program is used

### 5.1 CLI surface

```text
bud                         # open the dashboard (doesn't register the current dir)
bud <path>                  # open a directory as a project (registers it) or a file; starts Claude Code there (D25)
bud <file1> <file2> ...     # open files, one buffer each
bud --layout focus .        # open with a specific layout (flags before the path)
bud chat [--resume]         # chat with Claude Code in chat mode (--resume picks an earlier chat, D81)

bud install [--profile full|minimal] [--yes]   # system deps + nvim + plugins + language tooling
bud doctor [--quick]        # health checks: versions, missing tools, broken specs, startup time, Claude Code
bud claude status | setup    # is Claude Code installed and logged in; install it, hand over to its login, set up clod
bud update [--check] [--channel stable|nightly]   # self-update the binary, then sync its embedded config + restore lockfile, migrate
bud dev link [path] | unlink                   # point ~/.config/bud at a checkout for live editing
bud uninstall [--keep-config] [--yes]

bud projects ls | add <path> | rm <name> | pin <name>
bud lang ls | add <name> | rm <name> | enable <name> | disable <name>
bud tools ls | gen "<description>" | enable | disable | rm | promote <name>
bud kit sync | status | ls | unsync | core | add | rm | enable | disable
bud issue target | set | unset                 # where issues filed from the editor go in Linear
bud agent [path]            # open Claude Code's own TUI in a project, outside Neovim
bud layout ls | set-default <name> | set <name> [project] | unset [project]
bud config ls | get <key> | set <key> <value> | unset <key> | edit | path
bud completion bash|zsh|fish                  # eval "$(bud completion zsh)" in your shell rc

bud launch [--terminal kitty] [--layout default] [path]   # what the app bundle calls
bud bundle [--macos|--linux]                             # build/install the app bundle locally
bud bootstrap [--config] <user@host>                     # set up a remote machine over SSH
bud version
```

Global flags: `--no-update` (skip boot check), `--verbose`, `--profile`, and `--layout` for the bare open.

**Flag order (D4):** `bud [global flags] <command> [command flags] [args]`. Global flags go before the command (`bud --verbose update --check`), command flags go right after the command name, and positionals always come last. When you type the wrong order, the help text shows the right one.

### 5.2 First-run flow

1. `curl -fsSL https://raw.githubusercontent.com/jgarner9/bud/main/install.sh | sh`
2. The script detects OS + arch, downloads the matching `bud` release binary, verifies the signature on `checksums.txt` and then the archive's checksum (D7), drops it in `~/.local/bin`, and asks before running `bud install` (skip the question with `--yes`, D17).
3. `bud install` asks (or reads flags):
   - profile: **full** (desktop: every language, the app bundle) or **minimal** (SSH/server: no bundle, Python and Bash)
   - terminal emulator (auto-detects what's installed)
   - which languages to enable (defaults from a preset)
   - Claude Code: installs it if missing and checks you're logged in (`claude` runs its own login; skippable, and bud works without it). Then it sets up clod if it's missing (D89, D90: gh's GitHub login, your `<login>/clod` made from `jgarner9/clod-template` if it doesn't exist, a clone into `~/clod`, its installer), and syncs the kit (D77: bud's plugins), once Claude Code is logged in.
4. It installs system deps via the OS package manager, syncs the embedded `nvim/` into `~/.config/bud`, then runs a headless `nvim` to install plugins from the lockfile and Mason packages for enabled languages. No clone. `git` is only there for `vim.pack`.
5. On a desktop profile, it installs the app bundle (`/Applications/Bud.app` or `~/.local/share/applications/bud.desktop`).
6. Ends with `bud doctor` output and "run `bud` to start".

### 5.3 Over SSH / new machines

- Simplest: `ssh host 'curl -fsSL .../install.sh | sh -s -- --profile minimal --yes'`
- Convenience: `bud bootstrap [--config] user@host` runs exactly that from your local machine (`ssh -t`, so a sudo prompt works), pinned to the same release as the local bud (its tag, `nightly`, or latest for a dev build), with `--profile` defaulting to minimal. `--config` first copies your local `config.json` (never secrets) into the remote's state dir.
- On the remote, `bud` works the same in whatever terminal you SSH'd from. Pair with tmux/zellij if you want the session to survive disconnects.

### 5.5 Chat mode

A general-purpose chat that isn't tied to code, for bouncing ideas around. It's Claude Code's own TUI, run as bud-ide's `chat` agent (D81).

- **Opening it:** `c` from the dashboard, `<leader>ch` from anywhere, `:BudChat`, or `bud chat` from the shell. It opens in its own tab, so your editor layout is left exactly as it was; `<leader>ch` goes back and forth, and quitting Claude Code closes the tab.
- **What it is:** a conversational prompt in `~/.local/state/bud/chat/`, so no project's instructions load. It can read files you point it at, search and look things up, but it can't edit files or run commands; for that, open the project (`bud <dir>`).
- **History:** Claude Code's own store for that dir. `/resume` in the TUI, `:BudChat resume` or `bud chat --resume` picks an earlier chat. Per machine for now (D23).

### 5.6 App bundle + layout

- **macOS:** `bud bundle` builds and installs `Bud.app`. With Kitty as the terminal it's Bud's own copy of kitty.app (D97): an app called Bud, with its own bundle id and icon, so the menu bar, the Dock, Cmd+Tab, Cmd+Q and window managers like AeroSpace treat it apart from your kitty, and it uses your `kitty.conf`. With Ghostty, or no kitty.app, it's a tiny AppleScript droplet that runs `bud launch` (D47), which opens the configured terminal (with none set, the first one installed, D11). Either way it opens on the dashboard, and a folder or file dropped on the icon opens directly, a folder as a project.
- **Linux:** `bud bundle` writes `~/.local/share/applications/bud.desktop` (`Exec=env PATH=... /abs/bud launch %F`, the same baked-in bud and `PATH` as Bud.app, D47) and the robot icon into the hicolor theme at 64-512 px. It only replaces an entry with bud's `X-Bud-Version` key. No AppImage: `bud` is already a single binary.
- **Layout files** describe panes in Neovim terms, e.g. default = file tree (left, 24 cols, focused) | editor (center, an empty buffer), terminal (bottom, 35% of the height, hidden until `<leader>t`); chat stays closed until `<leader>ac` (JGA-161), from the dashboard and `bud <dir>` alike. Layouts are chosen per project or per launch (`--layout`).

### 5.7 Update flow

```text
boot (detached, at most once per day, skippable with --no-update, D9)
  └─ ask GitHub releases for the channel's newest version
     (stable = latest release, nightly = rolling prerelease from main) and compare to `bud version`
       ├─ nothing new → silent
       └─ new version → steps 1–2 below in the background, the rest at next launch
                        (nightly, D42, or update.auto = false → dashboard banner instead)

bud update  /  :BudUpdate [args]  /  Settings → Update  /  [u] on dashboard
  1. if a newer release exists:
       download the archive, checksums.txt and its signature; verify the signature, then the SHA-256 (D7)
       keep the running binary as bud.prev, swap the new one in place (rename, so it's atomic)
       re-exec the NEW binary for the rest (the old one still holds the old embedded config)
  2. sync the embedded nvim/ into ~/.config/bud (overwrite managed files, drop removed ones)
  3. run new migrations/ (each once, recorded in state; a fresh install marks them all done)
  4. nvim headless: `bud.pack.restore()` (lockfile) + Mason install for new language specs
  5. set up clod if it's missing, on a terminal, unless you said no (D89); then bud kit sync
     (bring Claude Code's config in line with the kit; a kit never synced is offered on a
     terminal, D87)
  6. bud doctor; on failure → swap bud.prev back, re-exec it to sync its config, report
     (only checks that passed before the swap count, so an unrelated missing tool never rolls back)
  7. rebuild the app bud bundle made, where it is, if it's out of date (D98; not with --no-doctor)
  8. the full bud doctor, listing what isn't OK with its fix (D87; reports only, never rolls back)
```

With no newer release, `bud update` skips step 1 and just re-syncs, which also repairs a config someone edited by hand. Because plugin versions come from `nvim-pack-lock.json`, and that file ships in the binary, "update" means "move every machine to the same known-good snapshot", not "pull the latest of 40 plugins and hope".

## 6. Suggested build order

All eight steps are built; this is the order they were planned in. Step 7's chat became Claude Code's own TUI (D81).

1. **Skeleton:** repo layout, `bud` with `open`, `install` (one OS), `doctor`, isolated `NVIM_APPNAME`.
2. **Editor core:** `vim.pack` + lockfile, navigation set, language engine with 3–4 languages.
3. **Dashboard (both styles) + project registry + the two-key open.**
4. **Updater** (release check, verified download, binary swap + re-exec, config sync, lockfile restore, rollback, `bud dev link`).
5. **One-liner + releases** (GoReleaser and `install.sh` exist; signing is built but off until the key is pinned (D41)).
6. **Launcher + layouts + bundles** (macOS then Linux).
7. **The per-project Claude Code session and `bud.ai.claude` (4.2)**, then **`bud kit sync`**, then **chat mode** (Claude Code's TUI, D81) and the TUI pane, then the **tool generator** with lifecycle commands.
8. Polish: settings UI, more languages, docs.
