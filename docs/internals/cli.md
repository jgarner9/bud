# CLI internals

The Go side of bud, one paragraph per area. AGENTS.md keeps the registry, prompts, errors, embedded config and paths.

**Colour** (`internal/cli/color.go`, JGA-109): `paint(w, style, s)` adds ANSI codes only when `w` is a terminal `*os.File`, `TERM` isn't `dumb` and `NO_COLOR` is unset, so tests (buffers) and pipes stay plain. Pad text before painting it, or the codes break the columns: `cell(w, style, s, width)` does both. The list and status commands share one palette (JGA-159): names bold, kinds, paths and descriptions dim, on/enabled green (`onStyle`), attention yellow, broken red; `config ls`/`get` bold the JSON keys (`paintJSONKeys`). `TestListsColourLikePlain` forces `colorOn` and checks that stripping the codes gives back the plain output byte for byte.

**Completion** (`internal/cli/complete.go`, JGA-96): `bud completion bash|zsh|fish` prints a few lines that call the hidden `bud __complete <words> <current>` (left out of help), which walks `CommandRegistry`, flags (`valueFlags` for flag values) and `argValues` (layouts, languages, tools, config keys, projects, all read from files, never through nvim). Nothing printed means the shell completes file names.

**`bud config`** (`internal/cli/configcmd.go`, JGA-93): `ls [--changed]`, `get`, `set [--force]` (value parsed as JSON, else a string; unknown keys refused unless `--force` via `config.Known`; the whole file must pass `Settings()` before it's saved), `unset` (`File.Unset`), `edit` (bud's nvim, then checked; tests swap `editFile`), `path`. `File.Effective` is a key's value with defaults filled in.

**Uninstall.** `bud uninstall` removes the synced files in `~/.config/bud` (manifest-tracked only, via `nvim.RemoveConfig`), the whole data, state and cache dirs (`--keep-config` spares `config.json` and `user-tools/`), and any app bundle `bundle.Find` says bud built. It leaves OpenCode and its config in place. It removes the binary only when `install.sh` recorded installing it in `~/.local/state/bud/install.json` (`installer.ReadReceipt`, D20); self-update will use the same record. It always lists what it will remove and asks first, unless `--yes`.

**Launching.** `open` resolves its args into a workspace: no args is the cwd, one dir is a project, and files open from the root found by walking up to `.git` (else the first file's dir). Then `nvim.Launch` `chdir`s and replaces the bud process with nvim via `syscall.Exec`. Nothing runs after that, which is why plans for in-editor processes (like the OpenCode session in BASE.md 4.2) live in Lua, not Go.

**Launch.** `bud launch [--terminal] [--layout] [path ...]` (`internal/cli/launch.go`, D46) opens a new terminal window running this binary as `bud ... open <abs paths>`, after checking the paths, layout and terminal up front. `internal/launcher` has one file per terminal (`kitty.go`, `ghostty.go`) registering a `command` that builds the argv; on macOS both go through `open -n -a <app> --args`, and the inner command carries the caller's `PATH` via `/usr/bin/env`. Terminals are found with `installer.Lookup`/`Terminal.Locate`. Tests swap `launchWindow` and `launchTerminals`.

**Device components.** `bud install --device <name>` (Suite D62) picks a device profile with `profile.Find`, from `profileDirs`: the overlay clone's `profiles/` (`paths.Overlay()`) first, then the examples embedded from `profiles/` (`bud.Profiles()`). A new name is saved as the `device` setting, so a later plain `bud install` repeats it; with neither, the components are `ide` alone, which is the install as it was before. `install` then runs `installComponents[c]` for each component the profile names, in `profile.Components` order, and joins their errors, so one failing doesn't stop the rest. `ide` is `installIDE`, the flow described below. `harness` uses the OpenCode pin shared with `bud ai setup`. It checks the executable on PATH and installs the pinned npm package when the executable is missing and the user confirms. The npm command explicitly allows the OpenCode package’s postinstall script, which npm 12 otherwise blocks, and the version check accepts both the bare version and the CLI’s `opencode v` prefix. If the executable reports a different or unknown version, the component returns a version error and leaves the existing installation in place. `app`, `server` and `qwen` still report their build-plan phase. Tests swap `installComponents` for recorders and point the XDG dirs at a temp dir.

**Installer.** `internal/installer` installs missing system deps through the package manager (D16): Homebrew on macOS; pacman, then apt, then dnf on Linux. `NewPlan(deps)` works out which of some deps are missing (`Needed(profile)` for the base set) and `Plan.Command()` the exact command line (with `sudo` unless running as root); `bud install` prints it, asks y/N (`--yes` skips), then `Plan.Run()` runs it on the terminal and re-checks. With no package manager, or no consent, it returns a `*MissingError` naming the deps and the command. It never upgrades what's installed, with one exception (D107): on Linux, `Dep.Tool` (Neovim and tree-sitter-cli) is a pinned download. `Installed()` then also needs the version on PATH to be at least `Tool.Min`, `Plan.Downloads()` lists what to fetch, `Plan.Command()` leaves it out of the package manager's command, and `Plan.Run()` calls `Tool.Download`, which checks the archive's SHA-256 against the digest pinned in the source before unpacking into `<data>/managed/<name>-<version>/` and linking `<data>/bin/<bin>`. `main` calls `cli.UseManagedBin` so that dir is first on PATH for bud and everything it starts. `bud install` first calls `PruneManaged`, which unlinks a download once the system has a new enough one. macOS and CPUs with no pinned build use the package manager. Per-manager package names live in `Dep.Pkgs`, `Dep.Bins` lists alternative binary names (apt's `fdfind`), `Dep.Also` binaries that must be on PATH too and `Dep.Probe` a check a binary can't show (node needs `npm`, python3 needs venv support, which Debian splits into other packages, so a half-installed one counts as missing and `bud install` lists it as "incomplete"), and `FullOnly` deps are skipped by the minimal profile. Language specs name binaries in `system`; `ForBins` turns them into deps, from `LanguageDeps` (go, python3, node with their package names) or as a package named after the binary. `bud install` asks profile and terminal, then languages (`internal/cli/install.go`, prompts in `prompt.go`), and only writes answers that differ from the defaults into `config.json` (no `languages` key means the profile's preset). The language question needs nvim to read the specs: with nvim present, every question comes first and one install covers base and language deps; on a fresh machine the base deps go in first, then the languages are asked and their deps installed. Under `curl | sh`, `install.sh` runs it with `</dev/tty` so the prompts read the terminal, not the script. `bud install` also runs `setupGitHub` (`internal/cli/github.go`, full profile only, through `githubSetup` so `TestMain` can turn it off): it installs `gh` (`ghDep`) and offers `gh auth login` at a terminal, since the dashboard's open-PRs panel needs it; a failure only warns.

**`bud lang`** (`internal/cli/lang.go`, D34) lists specs and edits `config.json`'s `languages`; `enable` also installs system deps and runs the plugin restore. The user's specs live in `user-tools/languages/` (`Paths.UserLanguageSpecs`), read after bud's own and never part of a preset (`Spec.Builtin`, set from which dir a spec came from).

**Projects.** `internal/projects` owns `projects.json` (D36): `Load`/`Save` keep unknown keys and save atomically, `Add` canonicalizes paths and picks unique names, `Sorted` is pinned, then last opened, then name. `open` registers `ws.Root` when `Workspace.Project` is set (a dir arg, or files inside a `.git` repo) and only logs a failure, so a bad registry never blocks opening. `bud projects` (`internal/cli/projects.go`) edits it; Lua reads it through `bud.projects` (read-only).

**Languages from Go.** `internal/lang.Load(shipped, dirs...)` reads specs by running `nvim --clean --headless -l` on this binary's `lua/bud/lang/dump.lua` (extracted to a temp dir with the engine, so a synced copy never matters), which loads them with `bud.lang` and writes JSON. `shipped` puts the embedded specs first; an earlier dir wins on a name clash. `Set.Preset`/`Enabled` apply the same preset rule as Lua. `bud install` reads shipped plus `~/.config/bud/languages`; `bud doctor` reads the synced dir and fails only for a broken spec the manifest says bud shipped (D33). Its tests need nvim and skip without it, so CI runs them in the smoke job.

**Dev link.** `bud dev link [path]` (`internal/cli/dev.go`, `nvim.Link`) swaps the synced copy in `~/.config/bud` for symlinks into a checkout (each top-level entry of `ide/nvim/`, plus `languages` and `layouts`) and a `.bud-dev-link` marker; `SyncConfig`, `Apply`, doctor and `RemoveConfig` see the marker (`nvim.DevLink`) and leave the links alone. `bud dev unlink` removes them and syncs the shipped config back.

**Migrations.** `ide/migrations/NNNN_name.lua` (embedded, `bud.Migrations()`) run once each from `nvim.Apply`, after the sync and before the plugin restore: `internal/migrate.Run` records each in `~/.local/state/bud/migrations.json` as it succeeds and stops at the first failure, so it reruns next time. A fresh install (no sync manifest yet) marks them all done instead (`MarkAll`). Each runs in `nvim --clean --headless -l` with `BUD_CONFIG_DIR`/`BUD_DATA_DIR`/`BUD_STATE_DIR`/`BUD_CACHE_DIR`; `ide/migrations/0001_example.lua` documents the contract. Never edit or renumber a shipped one.

**Version.** `internal/version.Version` is set by GoReleaser via `-ldflags -X`. Without it, `String()` falls back to the module version Go stamps into the build.

**OpenCode launcher.** `bud agent` checks `paths.OpenCodeEnv()` before launching the OpenCode TUI. When sync produced this file, `op run` resolves its references and `--standalone` puts the server in the same environment as the client. With no file, profiles without 1Password references use the normal OpenCode launch. `op run` itself gets the service account token from `internal/optoken` (bud's own environment, then the macOS Keychain item `bud-op-service-account`, then the token file at `paths.OpTokenFile()`; Suite D144), which is why a launch needs no 1Password sign-in. When no source has a token `op` signs in as it always did, and a source that exists but fails stops the launch with an error that never contains the token. The OpenCode child runs under `env -u`, so a session never holds the token (D142).

For an interactive launch, `op run` pipes its child's output for secret masking. Bud puts a pseudo-terminal inside those pipes so OpenCode can measure the window and respond to resizes. Linux uses util-linux `script` with exit-status forwarding and no transcript. macOS uses the system Expect because Apple's `script` does not forward window changes. Both wrappers start after `OP_SERVICE_ACCOUNT_TOKEN` has been removed. Redirecting a stream skips the wrapper.
