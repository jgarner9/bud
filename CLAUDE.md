# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bud is a Neovim-based IDE driven by a small Go CLI (`bud`). The CLI installs, launches, updates and syncs an isolated Neovim config (`NVIM_APPNAME=bud`, so it never touches `~/.config/nvim`). `BASE.md` is the full plan plus a numbered decision log (D1, D2, ...). Most of it isn't built yet, so check the code before assuming a planned feature exists. When a decision changes, update `BASE.md` too.

AI scope is **Claude Code only** (D26): one Claude Code session per project, started and owned by Neovim (D25, BASE.md 4.2), with Neovim TUIs built on the `bud.ai.claude` Lua module. Don't add other harnesses, model providers or an API client unless asked.

## Commands

```sh
just                 # list recipes
just check           # what CI runs: gofmt check, Lua lint, go vet, shellcheck, go test ./..., smoke test
just test            # go test ./...
just test -run TestOpen ./internal/cli   # single test (args pass through to go test)
just run <args>      # go run ./cmd/bud <args>, e.g. just run update
just build           # ./bud (gitignored)
just fmt             # gofmt -w .
just lua-fmt         # stylua over nvim/ and scripts/
just lua-test        # headless Lua tests in tests/lua (plain asserts, no framework)
just install-test    # install.sh's checks against fake releases signed with a throwaway key
just smoke           # sync the config into temp XDG dirs, restore plugins, start nvim headless (needs network)
just lang-check [go] # install every language's tooling in temp XDG dirs, check each on a sample project (slow, needs network)
just snapshot        # local GoReleaser build into dist/, needs goreleaser installed
```

`just lint` and `just check` need `stylua` and `selene` (`brew install stylua selene`); they fail with that hint when either is missing. Lua style is in `stylua.toml` (2 spaces, double quotes, 120 columns) and `selene.toml` + `vim.yml` (Lua 5.1 plus the `vim` global). CI pins stylua, selene and Neovim versions in `.github/workflows/ci.yml`, and runs the smoke test on the oldest supported Neovim (0.12, D19) and the newest.

If the Go build cache isn't writable (for example inside a sandbox), prefix commands with `GOCACHE=$TMPDIR/gocache`.

## Hard constraints

- **Standard library only (D1).** No third-party Go modules. Commands use `flag.FlagSet`, not cobra. Config and data files are JSON (D2).
- **Flags go before positionals (D4):** `bud [global flags] <command> [command flags] [args]`. That's plain `flag` behavior, so don't add interspersed parsing.
- **macOS and Linux only (D22).**

## Architecture

**Command registry.** Each command is one file in `internal/cli/` that calls `RegisterCommand` from `init()`. `App.Run` (`internal/cli/cli.go`) parses global flags. If the first argument names a registered command it runs that command; otherwise it falls back to `open` with the argument as a path, so `bud .` and `bud file.go` work. A command with `Subs` takes one next (`bud lang enable go`); one with `Subs` and no `Run` is only a group, and its help lists them. Each command gets its own `FlagSet` through `Command.Flags`. Global flags (`--verbose`, `--no-update`, `--profile`, `--layout`) are parsed into a `*Globals` that `App.Run` hands to every `Command.Run`; `Globals.Logf` is the `--verbose` logger. Usage text is written by `globalUsage`/`commandUsage`, and `flagOrderHint` explains D4 when a global flag lands after the command.

**Prompts.** `terminalPrompter(yes)` returns a prompter, or nil with `--yes` or no terminal (nil takes every default); `confirmOnTerminal` guards destructive steps and refuses without a terminal, naming the `--yes` command. A command not built yet returns an error saying so, never a silent exit 0.

**Errors and output.** Commands return errors and never print errors or call `os.Exit`. `cli.ExitCode` (`internal/cli/errors.go`) is the only place that prints errors (one `bud: ...` line on stderr) and picks the exit code: 0 for success or `-h`, 2 for a `*UsageError` (build one with `usageErrorf`), 1 for anything else. `App.parse` silences the flag package and prints requested help to stdout, and the error plus usage to stderr. `App.Stdout`/`App.Stderr` let tests capture that output.

**Embedded config (D5).** The root package `bud` (`embed.go`) embeds `nvim/` and `languages/*.lua` with `//go:embed` (a file glob, so `_template.lua` isn't dropped), and `bud.Config()` serves them as one tree: `nvim/` at the root with `languages/` mounted inside. It must stay at the repo root, because embed can't reach parent directories. Later top-level dirs (`layouts/`, `tools/`) get mounted the same way; `bundles/` is embedded but not synced (`bud.Bundles()`). The binary is the release: `internal/nvim.SyncConfig` copies `bud.Config()` into `~/.config/bud` and records them in `.bud-manifest.json`. It overwrites managed files, deletes ones a release dropped, and never touches anything else. After a change it runs `bud.pack.restore()` in headless nvim, so plugins match the committed `nvim/nvim-pack-lock.json`. The target dir comes from `paths.Resolve().Config`, which is `~/.config/bud` on macOS too, because that's where Neovim looks.

**`bud config`** (`internal/cli/configcmd.go`, JGA-93): `ls [--changed]`, `get`, `set [--force]` (value parsed as JSON, else a string; unknown keys refused unless `--force` via `config.Known`; the whole file must pass `Settings()` before it's saved), `unset` (`File.Unset`), `edit` (bud's nvim, then checked; tests swap `editFile`), `path`. `File.Effective` is a key's value with defaults filled in.

**Paths and machine config.** `internal/paths.Resolve` is the only place that builds a bud path (XDG on macOS too, D13); don't hardcode one elsewhere. That includes the language spec dirs (`LanguageSpecs`, `UserLanguageSpecs`). Files bud rewrites (`config.json`, `projects.json`, the sync manifest) go through `internal/atomicfile.WriteFile`. `internal/config` keeps `config.json` as a raw JSON tree so unknown keys survive `Save`, and `File.Settings()` decodes it over `Defaults()`.

**Doctor.** `internal/doctor.Run` returns one `Result` per check (`OK`/`Warn`/`Fail`). Only `Fail` makes `bud doctor` exit non-zero, which the updater will use for rollback. New checks are functions added to `Run`.

**Uninstall.** `bud uninstall` removes the synced files in `~/.config/bud` (manifest-tracked only, via `nvim.RemoveConfig`), the whole data, state and cache dirs (`--keep-config` spares `config.json` and `user-tools/`), and any app bundle `bundle.Find` says bud built. It removes the binary only when `install.sh` recorded installing it in `~/.local/state/bud/install.json` (`installer.ReadReceipt`, D20); self-update will use the same record. It always lists what it will remove and asks first, unless `--yes`.

**Launching.** `open` resolves its args into a workspace: no args is the cwd, one dir is a project, and files open from the root found by walking up to `.git` (else the first file's dir). Then `nvim.Launch` `chdir`s and replaces the bud process with nvim via `syscall.Exec`. Nothing runs after that, which is why plans for in-editor processes (like the Claude Code session in BASE.md 4.2) live in Lua, not Go.

**Launch.** `bud launch [--terminal] [--layout] [path ...]` (`internal/cli/launch.go`, D46) opens a new terminal window running this binary as `bud ... open <abs paths>`, after checking the paths, layout and terminal up front. `internal/launcher` has one file per terminal (`kitty.go`, `ghostty.go`) registering a `command` that builds the argv; on macOS both go through `open -n -a <app> --args`, and the inner command carries the caller's `PATH` via `/usr/bin/env`. Terminals are found with `installer.Lookup`/`Terminal.Locate`. Tests swap `launchWindow` and `launchTerminals`.

**Bundles.** `bud bundle [--macos|--linux] [--dest]` (`internal/cli/bundle.go`) builds the desktop app. `internal/bundle.Mac.Build` (D47) runs `osacompile` on the embedded `bundles/macos/main.applescript` (`bud.Bundles()`), with this bud's path and `PATH` filled in, edits `Info.plist` with `plutil`, writes the icon from `Icon()` (pixel art from the `robot` grid, encoded as `.icns`) and re-signs with `codesign -s -`. It only replaces an app whose bundle id is `MacID`. `TestBuild` needs `osacompile`, which the sandbox blocks, so it skips there. On Linux, `bundle.Linux.Install` writes `bud.desktop` from `bundles/linux/bud.desktop` (`paths.DesktopEntry`, `paths.DesktopIcon`), quoting `Exec` by the desktop entry spec (`execArg`, then `desktopValue`), and only replaces an entry carrying `X-Bud-Version`. The app runs install.sh's recorded binary when there is one (`bundleBin`), whose path a self-update keeps, so updates never need to rebuild it. `bud install` on the full profile runs `bud bundle` after the sync (`installBundle`) and only warns if it fails; `bud uninstall` removes what `bundle.Find` reports (tests stub `findBundles`, so they never see a real `/Applications/Bud.app`).

**Claude Code.** `internal/claude` finds the `claude` binary (PATH, else the native installer's `~/.local/bin/claude`) and reads `--version` and `auth status --json` (`Check`). `bud claude status|setup` (`internal/cli/claude.go`): `setup` runs Anthropic's native installer (`claude.InstallScript`, after showing it and asking, or with `--yes`), then hands over to `claude auth login`, which needs a terminal. `bud install` offers it when `ai.claude.autostart` is on (`installClaude`) and only warns if it fails. Doctor's `claude code` check (`doctor.ClaudeCheck`) only ever warns, with fix `bud claude setup`; the dashboard pulls it out of the doctor count into its own banner, and `c` runs the fix. bud stores no keys (D26). Tests swap `checkClaude` and `runOnTerminal`.

**Claude Code session.** `bud.ai.claude` (`nvim/lua/bud/ai/claude.lua`, BASE.md 4.2, D49/D50) is the only thing that talks to Claude Code. `setup()` runs from VimEnter on `vim.schedule` (not headless): `:BudClaude status|restart|stop`, `<leader>ar` restart, a statusline section, and a session for `bud <dir>` (`BUD_OPEN=project`) or for files (mentioned as `@file` with the first message); `bud.open.go` calls `opened(path)`. Each session is a `claude -p --input-format stream-json --output-format stream-json --verbose` job in its root (`--continue` first, `--resume <its id>` after a stop), started only after `claude auth status` says logged in, otherwise status `missing`. `handle` turns stream-json into `message`, `tool_use`, `done`, `exit` and `status` events (`on(event, fn)`); `interrupt` sends a `control_request`. At most `max_sessions` (3) run, least recently used goes first, and a timer `reap`s ones idle past `ai.claude.idle_minutes`; a stopped one restarts on the next `send`. `ai.claude.command` (D60) replaces `claude` at the front of every command line (`M.prefix`; `bud agent` too). `tests/lua/claude_test.lua` drives it with a fake `claude` shell script (swap `M.bin` and `M.check_login`). `bud.ai.term` (D48) is Claude Code's own TUI in a terminal pane: `open` calls `claude.handover` (stops the headless job, status `term`, `send` refuses) and the TUI's exit calls `handback` (the next start uses `--continue`, since the TUI may have moved on); `<leader>ac` toggles it, `:BudClaude term` opens it, it's the layout's `chat` pane (`layout/panes.lua`), and hidden idle ones are reaped like sessions. `tests/lua/claude_term_test.lua` covers it. `bud agent [path]` (`internal/cli/agent.go`) execs the same TUI from the shell in the project root. **IDE bridge** (D51): `bud.ai.bridge` (`nvim/lua/bud/ai/bridge/`) starts on the first session (`claude.bridge_env`): `websocket.lua` is the RFC 6455 server on vim.uv (own SHA-1 for the handshake) that also answers plain HTTP POSTs, `init.lua` writes the `~/.claude/ide/<port>.lock` (`lock_dir`, swapped in tests), dispatches MCP JSON-RPC (`handle`), sends `selection_changed` and gives headless sessions `headless_args()` (`--mcp-config` over HTTP plus the read-only tools in `--allowedTools`), and `tools.lua` holds the tools, with `openDiff` answering only when the diff is accepted (`ga`/`:w`) or rejected (`q`). `<leader>as` shares the selection (`claude.share`: an `at_mentioned` to the TUI, else `@file#L` context for the next message). `tests/lua/bridge_test.lua` is a real WebSocket and HTTP client. **Permissions** (D52): headless sessions get `--permission-prompt-tool mcp__bud-ide__approve` (the `approve` tool exists only for HTTP clients, `ctx.http` in `bridge.handle`; the session's root rides in the MCP URL's `?root=`), which calls `bud.ai.permissions.request`: edit tools go through `tools.review` (the same diff UI `openDiff` uses), others a float (`y`/`a`/`n`/`r`), queued one at a time, with `a` remembered per project and command. `tests/lua/permissions_test.lua` covers it. **Chat** (D53): `bud.chat` (full screen, own tab, session key `chat` in `store.chat_dir()`, history panel), `bud.chat.pane` (the project's session in a side split; the layout's `chat` pane unless `ai.chat.pane = "term"`) and the shared `bud.chat.view` (`render`, `expand` for `@file`/`@selection`/`@project`/`@diff`, `code_block`). `bud.chat.store` reads Claude Code's `.jsonl` store (`project_dir` encodes a dir the way Claude Code does) and keeps titles and pins in `chat/history.json`. Sessions are keyed (`claude.session(root, { key = ... })`, `get`, `drop`), so chat runs beside the project sessions without counting against them. `bud chat [--resume]` (`internal/cli/chat.go`) launches nvim with `BUD_OPEN=chat`. `tests/lua/chat_test.lua` uses a fake claude that writes its own `.jsonl` history. **Inline actions** (`bud.ai.actions`, JGA-90): `<leader>ae`/`af`/`at` send explain/refactor/write-tests for the selection (`@file#La-b`) to the project session and open the chat pane, with edits arriving as permission diffs; `<leader>am` in a gitcommit buffer (or `:BudCommitMessage`) sends the staged diff and recent subjects and puts the `done` reply above git's comments. `tests/lua/actions_test.lua`. **Tools** (D54): `bud.tools` loads `tools/` (embedded, mounted like `languages/`, `paths.Tools`) and `user-tools/<name>/` after the first screen; `bud tools ls|enable|disable [--reason]|rm|promote` (`internal/cli/tools.go`) owns `tools.disabled` in `config.json` and `tools.json` in the state dir. Tests: `tests/lua/tools_test.lua`, `internal/cli/tools_test.go` (swap `runGit`). **Generator** (D55): `bud.gen.run(request)` (`:BudGen`, or `bud tools gen` via `BUD_OPEN=gen`/`BUD_GEN`) runs session key `gen` in `user-tools/` with `gen.prompt`, snapshots the dir, and after each `done` load-tests what `gen.changed` finds (`gen.load_test`, a headless nvim) and enables or disables it through the CLI. `tests/lua/gen_test.lua`. **Kit** (D56): `internal/kit` (`Load`, `MCP.Server`, `Sync` with a dry run, `Ledger`) syncs the embedded `kit/` (`bud.Kit()`); `bud kit sync [--dry-run]|status|ls` (`internal/cli/kit.go`, swap `kitFS` and `kitClaude` in tests), and `resyncKit` after an update when a ledger exists. Never run a real sync from tests: they use a temp HOME and a recorded `claude`. Secrets (D57): `internal/secrets` (`Get`, `Has`, `Set`, `Delete`; tests swap `run` and `goos`), `bud kit secret set|rm`, `bud kit env` (keychain-only secrets as JSON, which `claude.secret_env` passes to each session and `bud agent` to its exec), `askKitSecrets` in `bud install`. Editing the kit (D58): `kit.Repo` (`AddMCP`, `Scaffold`, `Remove`, `SetProfiles`, `Adopt`) works on a checkout's `kit/` (`kitRepo`: `--repo` or the dev link), `kit.Own` puts adopted items in the ledger, `kit.disabled` in `config.json` filters `Sync` (`Env.Disabled`), and `defaultKitFS` reads a dev-linked checkout's kit. An MCP entry's `requires` (bin + install hint) makes sync skip it until the binary is on PATH (`Env.HasBin` in tests). Plugins (D62) are `kit.json`'s `plugins` (name@marketplace), installed through `claude plugin` (`Env.InstalledPlugins` reads `claude plugin list --json`). `bud.ai.index` (D61) warms cocoindex-code's index in the background once per project, only after `ccc init`; `tests/lua/index_test.lua`.

**Installer.** `internal/installer` installs missing system deps through the package manager (D16): Homebrew on macOS; pacman, then apt, then dnf on Linux. `NewPlan(deps)` works out which of some deps are missing (`Needed(profile)` for the base set) and `Plan.Command()` the exact command line (with `sudo` unless running as root); `bud install` prints it, asks y/N (`--yes` skips), then `Plan.Run()` runs it on the terminal and re-checks. With no package manager, or no consent, it returns a `*MissingError` naming the deps and the command. It never upgrades anything, Neovim included (D19). Per-manager package names live in `Dep.Pkgs`, `Dep.Bins` lists alternative binary names (apt's `fdfind`), and `FullOnly` deps are skipped by the minimal profile. Language specs name binaries in `system`; `ForBins` turns them into deps, from `LanguageDeps` (go, python3, node with their package names) or as a package named after the binary. `bud install` asks profile and terminal, then languages (`internal/cli/install.go`, prompts in `prompt.go`), and only writes answers that differ from the defaults into `config.json` (no `languages` key means the profile's preset). The language question needs nvim to read the specs: with nvim present, every question comes first and one install covers base and language deps; on a fresh machine the base deps go in first, then the languages are asked and their deps installed. Under `curl | sh`, `install.sh` runs it with `</dev/tty` so the prompts read the terminal, not the script.

**`bud lang`** (`internal/cli/lang.go`, D34) lists specs and edits `config.json`'s `languages`; `enable` also installs system deps and runs the plugin restore. The user's specs live in `user-tools/languages/` (`userSpecDir`), read after bud's own and never part of a preset (`Spec.Builtin`, set from which dir a spec came from).

**Projects.** `internal/projects` owns `projects.json` (D36): `Load`/`Save` keep unknown keys and save atomically, `Add` canonicalizes paths and picks unique names, `Sorted` is pinned, then last opened, then name. `open` registers `ws.Root` when `Workspace.Project` is set (a dir arg, or files inside a `.git` repo) and only logs a failure, so a bad registry never blocks opening. `bud projects` (`internal/cli/projects.go`) edits it; Lua reads it through `bud.projects` (read-only).

**Dashboard.** `bud.dashboard` (D37) opens for bare `bud` from the VimEnter autocmd in `core/autocmds.lua`. `dashboard/view.lua` is a pure layout (`build(data, width, height)` returns lines and highlights) and is what `tests/lua/dashboard_test.lua` mostly covers; `dashboard/init.lua` gathers data, draws into a `bufhidden=wipe` scratch buffer with buffer-local keys, and runs git and `bud doctor --quick --json` in the background via `BUD_BIN`. Shared Lua modules: `bud.config` reads machine config, `bud.cli.bin()` finds the bud that launched nvim (`BUD_BIN`) for calling back into the CLI (the only writer of bud's state files), `bud.icons` holds the Nerd Font glyphs (the editor's accent with the robot; never emoji), and `bud.sessions` saves and restores per-project sessions. `bud.open` (D39) is the two-key open: `project()`, `file()`, `go(path)`; the dashboard's `p`/`f` and `<leader>p`/`<leader>f` all call it, and it reaches fzf-lua through `bud.pack.deferred["fzf-lua"]`.

**Languages from Go.** `internal/lang.Load(shipped, dirs...)` reads specs by running `nvim --clean --headless -l` on this binary's `lua/bud/lang/dump.lua` (extracted to a temp dir with the engine, so a synced copy never matters), which loads them with `bud.lang` and writes JSON. `shipped` puts the embedded specs first; an earlier dir wins on a name clash. `Set.Preset`/`Enabled` apply the same preset rule as Lua. `bud install` reads shipped plus `~/.config/bud/languages`; `bud doctor` reads the synced dir and fails only for a broken spec the manifest says bud shipped (D33). Its tests need nvim and skip without it, so CI runs them in the smoke job.

**Updater.** `internal/updater` asks GitHub for the channel's newest release (`Latest`, `Check`): `stable` is `releases/latest`, `nightly` is the rolling release tagged `nightly`, whose *name* is its version (`X.Y.Z-nightly.YYYYMMDDHHMM`). Versions compare with `version.Parse`/`version.Compare` (semver precedence). `bud update --check [--channel]` reports it. Plain `bud update` (`selfUpdate` in `internal/cli/update.go`) installs a newer release first, only for the binary `install.sh` recorded (else it names the right tool, D20): `updater.Fetch` downloads and checks it (the SSHSIG on `checksums.txt`, made by any of the pinned `ReleaseKeys`, D41/D44, then the SHA-256), `CheckBinary` runs it, `Swap` keeps the old one as `bud.prev` and renames the new one in, and the new binary is exec'd with `BUD_UPDATED_FROM` set to do the sync. It then runs the quick doctor checks (`finishUpdate`): if the sync fails, or a check fails that wasn't already failing before the swap (`BUD_FAILING_BEFORE`), it restores `bud.prev` and execs it with `BUD_ROLLED_BACK_FROM`, which syncs the old config and exits 1 with the reason. At launch, `open` first finishes a pending background update (`finishPendingUpdate`), then `startUpdateCheck` starts a detached `bud update --background` once a day (`updater.State` in `~/.local/state/bud/update.json`, log in `~/.cache/bud/update.log`; skipped with `--no-update` and for dev builds). On stable with `update.auto` it swaps the release in and records it as `installed`, so the next launch syncs it; otherwise (nightly, D42) it records `available`, which the dashboard shows as a banner (`update_banner`). Tests fake GitHub with `httptest`, which needs to bind a local port (blocked in the sandbox).

**Dev link.** `bud dev link [path]` (`internal/cli/dev.go`, `nvim.Link`) swaps the synced copy in `~/.config/bud` for symlinks into a checkout (each top-level entry of `nvim/`, plus `languages` and `layouts`) and a `.bud-dev-link` marker; `SyncConfig`, `Apply`, doctor and `RemoveConfig` see the marker (`nvim.DevLink`) and leave the links alone. `bud dev unlink` removes them and syncs the shipped config back.

**Migrations.** `migrations/NNNN_name.lua` (embedded, `bud.Migrations()`) run once each from `nvim.Apply`, after the sync and before the plugin restore: `internal/migrate.Run` records each in `~/.local/state/bud/migrations.json` as it succeeds and stops at the first failure, so it reruns next time. A fresh install (no sync manifest yet) marks them all done instead (`MarkAll`). Each runs in `nvim --clean --headless -l` with `BUD_CONFIG_DIR`/`BUD_DATA_DIR`/`BUD_STATE_DIR`/`BUD_CACHE_DIR`; `migrations/0001_example.lua` documents the contract. Never edit or renumber a shipped one.

**Version.** `internal/version.Version` is set by GoReleaser via `-ldflags -X`. Without it, `String()` falls back to the module version Go stamps into the build.

**Neovim config.** `nvim/init.lua` sets the leader (`<Space>`), then loads `bud.core` (options, keymaps, autocmds) and `bud.pack`, which adds plugins with Neovim's built-in `vim.pack` (D27, needs 0.12). Specs are lists returned by modules under `nvim/lua/bud/plugins/` (`{ src = "owner/repo", version = ..., config = fn }`, see the top of `pack.lua`); `plugins/init.lua` gathers them. Nothing updates plugins in place: versions change only by regenerating `nvim/nvim-pack-lock.json` and shipping a release. Generate that file with `vim.pack` itself and commit it byte for byte, or every sync will look like a change. Lazy loading is built into `bud.pack` (JGA-107): a spec with `event`, `ft`, `cmd` or `keys` stays off the runtimepath until its first trigger (commands and keys get stubs; the triggering event is replayed only to the autocmd groups the plugin just added), and `init` always runs at startup, for keymaps that should exist before loading (diffview's). A plugin that's on the runtimepath but slow to `require` can instead use `bud.pack.on_first_use(module, setup)` (fzf-lua). The smoke test loads every lazy and deferred plugin to check it, and `tests/lua/pack_test.lua` covers the loader with throwaway local git repos. Measure before making something lazy: `--startuptime` appends to its log file, so delete it between runs. The budget is 50 ms to the first screen, empty or opening a file of any language (D35); `bud doctor` measures both (`nvim.StartupTime`). Per-buffer work that's slow the first time (tree-sitter highlighting, `vim.lsp.enable`, linting) starts on `vim.schedule` in `plugins/lang.lua`, and Neovim's providers are off in `core/options.lua`. Keymaps go in each spec's `config`. A spec can also have a `restore` hook that runs (and may block) at the end of `bud.pack.restore()`, after the lockfile checkout; blink.cmp downloads its prebuilt matcher there. `bud install`/`bud update` start that restore with `BUD_PACK_RESTORE=1`, which makes `bud.pack.setup` skip every `config`. **Languages (D30).** `bud.lang` (`nvim/lua/bud/lang/`) reads each spec in the synced `languages/` (fields documented in `languages/_template.lua`, unknown fields are errors), picks the enabled ones from `config.json` (`languages`, else the profile's preset: all for full, `minimal = true` specs for minimal) and answers queries (`servers()`, `by_ft(field)`, `collect(field)`, `filetypes()`). The wiring lives in the plugin specs in `plugins/lang.lua`: nvim-lspconfig + `vim.lsp.enable`, mason.nvim, nvim-treesitter (`main`, highlighting on enabled filetypes), conform (format on save unless `format_on_save: false`, or when the spec's `format_markers` aren't found; prettier only with a Prettier config; `<leader>cf`), nvim-lint. Parsers and Mason packages install only in their `restore` hooks. `tests/lua/lang_test.lua` covers the engine with fixture specs. The smoke test enables no languages (installing their tooling takes minutes), so after changing a spec or `plugins/lang.lua` run `just lang-check`, which installs everything and checks each language on a sample project (`scripts/lang_check.lua`; add a case there for a new language). **Layouts (D45).** `layouts/*.lua` at the repo root (embedded and mounted like `languages/`) list panes; `bud.layout` (`nvim/lua/bud/layout/`) validates them, opens each pane through the provider registered for its kind (`layout/panes.lua`: `tree` and `git` are neo-tree sources; later modules call `bud.layout.register`), skips kinds with none, and sets `bud.terminal.height`. `bud <dir>` passes `BUD_OPEN=project` (`nvim.Launch`), and the VimEnter autocmd calls `layout.open_project` on `vim.schedule` for that or for files: the saved session wins unless `--layout` (`BUD_LAYOUT`) was given. `bud.open.go` does the same. `:BudLayout [name|reload]`. `layout.default(dir)` picks `BUD_LAYOUT`, then the project's `layout` in `projects.json`, then `config.json`'s, then `default`; `bud layout` (`internal/cli/layout.go`) lists them (descriptions read from the file's text) and sets the last two. `open` refuses a `--layout` the synced `layouts/` doesn't have. `tests/lua/layout_test.lua` uses fake providers. The statusline is mini.statusline driven by `bud.statusline`; modules add their own section with `require("bud.statusline").add(fn)`. `bud.marks` is bud's own pinned-files module (four slots per project, `~/.local/state/bud/marks.json`), tested headless in `tests/lua/`.

## Release and install

Pushing a `v*` tag runs `.github/workflows/release.yml` (GoReleaser): linux/darwin × amd64/arm64 archives plus `checksums.txt`. Archive names deliberately leave out the version (`bud_<os>_<arch>.tar.gz`) because `install.sh` downloads from `releases/latest/download/<name>`, so keep `.goreleaser.yaml` and `install.sh` in sync. `install.sh` must stay POSIX `sh` and shellcheck-clean. It verifies the signature on `checksums.txt` with `ssh-keygen -Y verify` against its pinned `RELEASE_KEYS`, one per line (D41/D44; a test keeps them equal to `updater.ReleaseKeys`), then the checksum, installs to `~/.local/bin`, and asks on `/dev/tty` before running `bud install`, because stdin is the script under `curl | sh`.


**Bootstrap.** `bud bootstrap [--config] user@host` (`internal/cli/bootstrap.go`) runs the install.sh one-liner over `ssh -t` with `--profile` (default minimal), `--yes` and `--version` of this bud (`releaseVersion`); `--config` pipes `config.json` into the remote state dir first. Tests swap `runSSH`.

**Nightly.** `.github/workflows/nightly.yml` runs daily (and by hand): when main moved since the `nightly` tag, GoReleaser builds a snapshot named `X.Y.Z-nightly.YYYYMMDDHHMM` (one patch past the newest stable tag, via `NIGHTLY_VERSION` in `.goreleaser.yaml`'s snapshot template) and the `nightly` prerelease is deleted and recreated with the same archive names, so `releases/latest` never sees it.

**Signing.** The release workflow runs `scripts/sign-release.sh` only when the `BUD_RELEASE_KEY` Actions secret is set; it signs `dist/checksums.txt` under namespace `bud-release`, refuses if the key isn't one of install.sh's `RELEASE_KEYS`, and uploads `checksums.txt.sig`.

## Tests

Tests swap package-level vars and restore them with `t.Cleanup`: `CommandRegistry`, `installer.Deps`, `installer.goos`, `version.Version`. Tests that need binaries on PATH use the `fakePath` helper in `internal/installer`. `App` tests build an `App` with a custom `Cmds` map and recorder commands instead of using the global registry.
