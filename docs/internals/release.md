# Release tooling

Bootstrap, the nightly build and release signing. The release flow itself is in CLAUDE.md.

**Bootstrap.** `bud bootstrap [--config] user@host` (`internal/cli/bootstrap.go`) runs the install.sh one-liner over `ssh -t` with `--profile` (default minimal), `--yes` and `--version` of this bud (`releaseVersion`); `--config` pipes `config.json` into the remote state dir first. Tests swap `runSSH`.

**Nightly.** `.github/workflows/nightly.yml` runs daily (and by hand): when main moved since the `nightly` tag, GoReleaser builds a snapshot named `X.Y.Z-nightly.YYYYMMDDHHMM` (one patch past the newest stable tag, via `NIGHTLY_VERSION` in `.goreleaser.yaml`'s snapshot template) and the `nightly` prerelease is deleted and recreated with the same archive names, so `releases/latest` never sees it. `.goreleaser.yaml`'s `git.ignore_tags` leaves the `nightly` tag out when GoReleaser picks the previous release, so a release's changelog starts at the last `vX.Y.Z`. Content releases tag main too (`content-YYYY.MM.DD.N`, `content-channel`), and GoReleaser's `ignore_tags` takes globs only in Pro, so `scripts/release-plan.sh` also outputs `previous`, the newest stable tag older than the one being built, and the release workflow passes it as `GORELEASER_PREVIOUS_TAG`.

**Signing.** Rotating the key is `scripts/rotate-release-key.sh start|finish` (D64), run by hand, never by you: it creates a real key, writes to 1Password and sets the Actions secret. `just rotate-test` covers it with fakes. The release workflow runs `scripts/sign-release.sh` only when the `BUD_RELEASE_KEY` Actions secret is set; it signs `dist/checksums.txt` under namespace `bud-release`, refuses if the key isn't one of install.sh's `RELEASE_KEYS`, and uploads `checksums.txt.sig`. It takes an optional namespace after the file (`bud-release`, the default, `bud-content` or `bud-channel`), which is how the content workflow signs with the same key.

**Content releases.** `.github/workflows/content.yml` (Suite D60, D61; build plan task 1.10) runs `scripts/content-release.sh` on a push to main that changes `content/`, after `go test ./...`, the leak check and `bud registry check`; a manual run picks `edge`, `promote` (with a version) or `resign`. The tags are the record: `content-<v>` is a release and `content-stable-<v>` a promotion. On every run `channel.json` is rebuilt from them (edge at the newest release, stable at the newest promotion) with `bud content channel`, signed under `bud-channel` and uploaded over the old pair, so nothing is carried forward from the published file: a run that stopped between uploading `channel.json` and its signature, which leaves syncs failing, is put right by the next run. `edge` numbers the day's cut from the tags (`YYYY.MM.DD.N`), packs `content/` from the commit (`git archive`, then `bud content pack`), signs `content.json` under `bud-content` and creates the `content-<v>` release. A commit that already has a content tag cuts nothing new, and neither does a stale one, whose history doesn't include the newest release's commit (a retried old run), so old content never goes out under a newer version; both just republish the channel. `promote <v>` reads the published `channel.json` with `bud content offered`, which refuses it unless the signature verifies, and promotes only the version edge offers now, so stable always takes something edge devices were actually given; then it pushes `content-stable-<v>`. `resign` rebuilds the bundles the channel names from their tagged commits (the pack is deterministic, so they're the same bytes), re-signs them and the channel with the current key and uploads them over the old ones; nothing it signs is read back from the release. Every release it makes is a prerelease, so none becomes the repo's latest and install.sh's `releases/latest/download` keeps finding the code archives. Nothing is published until `BUD_RELEASE_KEY` is set. `just content-release-test` covers the script with fake `gh`, `bud` and signer.

**Content and key rotation.** Devices check content signatures against `updater.ReleaseKeys`, so after `rotate-release-key.sh finish` drops the old key, content signed with it stops verifying on updated devices. Between `start` and `finish`, run the content workflow by hand with `resign`, so the channel and every version it offers carry the new key's signatures.
